## 0. 先做什麼：可直接開工的順序

這裡的「現在」不會重排三條正在進行的線。三值判準、階段出口表誠實化（含讓階段表參數生效）、撞號當場炸，先各自完成；它們是本設計的前置世界。研究裁決也明確把這三件排在 Graph runtime 前面，並指出單一節點曾燒掉 997,031 token、目前預算只在呼叫之間檢查（docs/研究/圖住哪一層的對抗綜合.md:47-82,296-322）。

## 1. Q1：研究型 worker 與 TDD 是不是同一個抽象？

**是。同一個 typed workflow／node runner 的兩個實例；唯一的抽象差異是執行形狀，不是「研究是一種比較自由的 TDD」。**

共用的部分如下：

|共用契約|TDD 現況|研究型 worker 的對應|
|---|---|---|
|任務與現況|任務有描述、工作目錄、前情（src/nova/契約/工作流.py:114-126）|同一個任務欄位，另外把研究狀態放入 typed payload|
|節點結果|目前步驟結果已有階段、終局、判準、證據、用量（src/nova/契約/工作流.py:137-155）|同樣的終局／出口／用量／provenance；內容換成 claims、coverage、gaps|
|停止|目前停止條件至少有步數與 token（src/nova/契約/工作流.py:158-198）|同一種政策，再加研究輪數、coverage、novelty 與引用驗證|
|轉移|現有狀態機由階段表驅動，含回頭邊（src/nova/迴圈/狀態機.py:20-80,125-142）|仍由有限的具名出口查表，不由模型文字決定|
|執行依賴|建TDD執行器已把角色表、判準注入（src/nova/迴圈/工作流.py:161-199）|研究搜尋、引用驗證、模型與記帳同樣由呼叫者注入|
|安全終局|未知與確定失敗已分開，未知預設不可重試（src/nova/契約/模型回應.py:41-84）|一樣；研究不得因為「可能還沒搜到」就把未知當空結果|

唯一差異是下列型別中的執行形狀：

~~~python
from collections.abc import Callable
from dataclasses import dataclass
from enum import StrEnum
from typing import Generic, TypeVar

輸入 = TypeVar("輸入")
輸出 = TypeVar("輸出")
合併輸出 = TypeVar("合併輸出")


@dataclass(frozen=True, slots=True)
class 序列形狀(Generic[輸入, 輸出]):
    """一次只有一個目前節點；TDD 的單游標形狀。"""

    執行下一個: Callable[[輸入], 輸出]


@dataclass(frozen=True, slots=True)
class 扇出形狀(Generic[輸入, 輸出, 合併輸出]):
    """同一輸入分成互不依賴的分支，回到屏障後才合併。"""

    產生分支: Callable[[輸入], tuple[輸入, ...]]
    合併: Callable[[tuple[輸出, ...]], 合併輸出]


type 工作流形狀[輸入, 輸出, 合併輸出] = (
    序列形狀[輸入, 輸出]
    | 扇出形狀[輸入, 輸出, 合併輸出]
)
~~~

TDD 是序列形狀：現在的 runner 明確只有一個目前游標（src/nova/迴圈/工作流.py:50-103）。研究是扇出形狀：N 顆腦共享同一研究問題，各分支互不等待，最後由 deterministic barrier／reducer 合併。研究文件也建議第一版先把多角度搜尋包在一個有硬上限的節點，等真的需要恢復與 partial result 再升 Graph（docs/研究/工作流的多種形狀.md:118-167）。

研究的 coverage、claims、乾輪與 TDD 的測試輸出不是第二個抽象；它們是泛型輸入／輸出／狀態的實例。若把研究另做一套 runner，token、未知結果、帳本與護欄會分叉，這正是研究已列出的錯誤抽象代價（docs/研究/工作流工廠該切在哪.md:383-403）。

## 2. Q2：節點怎麼單拆、又怎麼隨時組裝？

### 2.1 節點的正式介面

新增 src/nova/契約/節點.py。以下是第一版的完整契約形狀；使用 Python 3.13 語法，符合專案要求的 mypy strict（pyproject.toml:1-8,67-69）。

~~~python
from collections.abc import Callable
from dataclasses import dataclass
from enum import IntEnum, StrEnum
from typing import Generic, NewType, Protocol, TypeVar

from nova.契約.模型回應 import 用量, 失敗代碼
from nova.契約.工作流 import 任務

輸入 = TypeVar("輸入")
輸出 = TypeVar("輸出")
依賴 = TypeVar("依賴")

執行識別碼 = NewType("執行識別碼", str)
工作流識別碼 = NewType("工作流識別碼", str)
節點識別碼 = NewType("節點識別碼", str)
分支識別碼 = NewType("分支識別碼", str)
邊識別碼 = NewType("邊識別碼", str)
結構識別碼 = NewType("結構識別碼", str)


class 結果代碼(IntEnum):
    成功 = 0
    確定失敗 = 1
    結果未知 = 3
    護欄 = 4


class 護欄原因(StrEnum):
    預算 = "budget"
    步數 = "steps"
    逾時 = "timeout"
    無進展 = "stagnation"
    扇出超限 = "fanout-limit"
    輸出不合約 = "invalid-output"


@dataclass(frozen=True, slots=True)
class 停止政策:
    最多呼叫: int
    最多token: int
    最多秒: float
    最多無進展: int
    結果未知不重跑: bool = True


@dataclass(frozen=True, slots=True)
class 證據來源:
    執行: 執行識別碼
    工作流: 工作流識別碼 | None
    分支: 分支識別碼
    節點: 節點識別碼
    嘗試: int
    父邊: tuple[邊識別碼, ...]


@dataclass(frozen=True, slots=True)
class 邊包(Generic[輸入]):
    結構: 結構識別碼
    版本: int
    內容: 輸入
    來源: 證據來源


@dataclass(frozen=True, slots=True)
class 節點錯誤:
    代碼: 失敗代碼
    診斷: str
    可能已產生副作用: bool


@dataclass(frozen=True, slots=True)
class 證據項:
    識別碼: 邊識別碼
    類型: 結構識別碼
    摘要: str


@dataclass(frozen=True, slots=True)
class 節點成功(Generic[輸出]):
    產出: 邊包[輸出]
    證據: tuple[證據項, ...]
    用量: 用量 | None

    @property
    def 結果(self) -> 結果代碼:
        return 結果代碼.成功


@dataclass(frozen=True, slots=True)
class 節點確定失敗:
    錯誤: 節點錯誤
    證據: tuple[證據項, ...]

    @property
    def 結果(self) -> 結果代碼:
        return 結果代碼.確定失敗


@dataclass(frozen=True, slots=True)
class 節點結果未知:
    錯誤: 節點錯誤
    已知證據: tuple[證據項, ...]
    用量: 用量 | None

    @property
    def 結果(self) -> 結果代碼:
        return 結果代碼.結果未知


@dataclass(frozen=True, slots=True)
class 節點護欄:
    原因: 護欄原因
    已知證據: tuple[證據項, ...]
    用量: 用量 | None

    @property
    def 結果(self) -> 結果代碼:
        return 結果代碼.護欄


type 節點結果[輸出] = (
    節點成功[輸出]
    | 節點確定失敗
    | 節點結果未知
    | 節點護欄
)


@dataclass(frozen=True, slots=True)
class 節點上下文:
    任務: 任務
    執行: 執行識別碼
    工作流: 工作流識別碼 | None
    節點: 節點識別碼
    分支: 分支識別碼
    父邊: tuple[邊識別碼, ...]
    嘗試: int
    停止: 停止政策


class 節點(Protocol, Generic[輸入, 輸出, 依賴]):
    @property
    def 識別碼(self) -> 節點識別碼:
        ...

    def 執行(
        self,
        輸入: 邊包[輸入],
        *,
        上下文: 節點上下文,
        依賴: 依賴,
    ) -> 節點結果[輸出]:
        ...


def 執行節點[輸入, 輸出, 依賴](
    節點: 節點[輸入, 輸出, 依賴],
    輸入: 邊包[輸入],
    *,
    上下文: 節點上下文,
    依賴: 依賴,
) -> 節點結果[輸出]:
    return 節點.執行(輸入, 上下文=上下文, 依賴=依賴)
~~~

這個介面把四種失敗直接做成結果的代數資料型，禁止呼叫端拿一個 bool 或模型散文猜終態。現有模型層已把成功／確定失敗／結果未知分開，而且未知預設不重試（src/nova/契約/模型回應.py:41-84）；退出碼的 0／1／3／4 語意則是專案硬規則（CLAUDE.md:111-132）。

診斷與摘要只能供人查閱；下游轉移只能讀結果代碼、護欄原因、具名結構欄位。這符合「跨層一律 schema 化」的規則，避免把一個自由段落交給下一節點重新猜（CLAUDE.md:68-79）。節點成功才有可餵給下游的邊包[輸出]；未知與失敗故意沒有輸出，所以沒有安全的型別路徑把未知結果接到下一節點。

### 2.2 上下文與依賴：都由呼叫者明傳

節點不讀全域目前工作流、不找全域腦、不自己建立帳本。上下文是資料：有圖／工作流時填入 workflow、branch、parent edges；獨立跑時填：

~~~python
獨立上下文 = 節點上下文(
    任務=任務(描述=題目, 工作目錄=工作目錄),
    執行=執行識別碼(執行編號),
    工作流=None,
    節點=節點識別碼("對抗"),
    分支=分支識別碼("root"),
    父邊=(),
    嘗試=1,
    停止=停止政策(最多呼叫=1, 最多token=100_000, 最多秒=600, 最多無進展=1),
)
~~~

依賴是每個節點自己的窄型 frozen value object，例如：

~~~python
@dataclass(frozen=True, slots=True)
class 對抗依賴:
    腦: 語言模型
    呼叫選項: 呼叫選項
    寫事件: Callable[[事件], None]
~~~

實際模組需從既有語言模型／角色 Protocol 與呼叫選項延伸，不另造第二套模型介面（src/nova/契約/角色.py:41-116）。依賴是一次呼叫傳入的值，不是服務定位器、全域 singleton、decorator 註冊表或 DI 容器；這保留既有執行器已採用的依賴注入形狀（src/nova/迴圈/工作流.py:161-199）。

### 2.3 「單獨叫」的答案：Python API 與 CLI 都要有

**正式邊界是 Python API；CLI 是同一個節點的薄適配器。** 兩者都必須呼叫同一個執行節點，不能各自再包一套 prompt／預算／終局。

Python 形式：

~~~python
def 單獨執行[輸入, 輸出, 依賴](
    節點: 節點[輸入, 輸出, 依賴],
    輸入: 邊包[輸入],
    *,
    上下文: 節點上下文,
    依賴: 依賴,
) -> 節點結果[輸出]:
    return 執行節點(節點, 輸入, 上下文=上下文, 依賴=依賴)
~~~

CLI 形式選一組穩定、具名的節點子命令，例如：

    nova 對抗 "<題目>"

它在 src/nova/載體/剖析器.py 增加一個明確的對抗 parser，在 src/nova/載體/命令列.py 只做輸入解析、建立 root context、建立依賴、把結果代碼映射成 process exit code。現有 parser 只有問／工作流／跑與工作流旗標（src/nova/載體/剖析器.py:77-195,198-265），現有 CLI 會直接建四個 TDD 角色再跑 runner（src/nova/載體/命令列.py:855-937），所以這是明確的薄適配器新增，不是把任意字串動態解成節點。

不採用 nova 節點 <任意名稱> 的動態註冊入口。新增一個可公開的穩定節點時，明確加 parser／handler 並加真 CLI 契約測試；內部研究節點先只提供 Python API。這避免在 Graph runtime 尚未有 trace 前偷建節點註冊表，符合 CLAUDE.md:68-79 與研究裁決 docs/研究/圖住哪一層的對抗綜合.md:181-189。

### 2.4 組裝：表是資料，組合函式是程式碼；不造 DSL

組裝分兩層：

1. **表**：階段／具名出口／節點規格是 immutable tuple 或 Mapping，可以窮舉、落 journal、做開機完整性檢查。這延續現有階段定義與 TDD階段表的資料形狀（src/nova/契約/工作流.py:201-221、src/nova/迴圈/狀態機.py:20-80）。
2. **組合函式**：建TDD工作流(...)、建研究工作流(...)、建角色表(...) 是普通 Python 函式。函式把已知的節點物件、依賴、判準與表接起來；不解析字串程式、不執行模型生成的 Python。

不得新增 src/nova/圖/、YAML／JSON 編排語言、條件字串、任意 callback 名稱解析或 node registry DSL。當前 Graph 層故意不存在，且沒有 trace 就新增這些東西是專案明定的違規（CLAUDE.md:68-79）。未來是否升 Graph 只由實際 trace 證明有多個 active cursor、join、跨程序 resume 或恢復需求決定（docs/AGENT_ARCHITECTURE.md:157-179,224-245）。

### 2.5 邊上流動的 schema

所有跨節點資料都用邊包[T]，不能把上一節點的整段回答直接塞入下一節點的 prompt。至少要有結構、版本、typed 內容、來源四欄；來源要沿 execution／branch／node／attempt／parent edges 追溯。識別碼與 provenance 是節點獨立使用的前置問題，研究文件已列出 execution、branch、attempt、checkpoint、artifact、finding lineage 的需求，但目前只先定欄位、不建 Graph 儲存 runtime（docs/研究/識別碼與儲存.md:106-180）。

TDD 與研究 payload 的最小實例：

~~~python
@dataclass(frozen=True, slots=True)
class 測試證據:
    指令: tuple[str, ...]
    退出碼: int
    判準結果: 判準終局
    輸出摘要: str


@dataclass(frozen=True, slots=True)
class 研究發現:
    主張識別碼: str
    主張: str
    來源識別碼: str
    來源位置: str
    來源品質: str
    覆蓋格: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class 研究狀態:
    覆蓋: tuple[str, ...]
    主張帳: tuple[研究發現, ...]
    缺口: tuple[str, ...]
    連續乾輪: int
    已跑輪數: int
~~~

輸出摘要可以存在，但它是證據中的具名欄位，不是控制流程的唯一輸入；研究的完成仍要看 coverage、重要主張來源、來源品質、連續兩輪無新實質主張、獨立 completeness critic 與引用驗證（docs/研究/工作流的多種形狀.md:118-167）。現有步驟結果.證據是 str（src/nova/契約/工作流.py:137-155），所以這個契約落地時要保留 TDD 既有輸出，再加一個 typed envelope，不要讓新下游繼續依賴自由字串。

### 2.6 單獨跑的停止規則

單獨跑不等於沒有 stop rule。每一個節點都必須收到停止政策，至少具備：

- 最多模型／工具呼叫數；
- 最多 token；
- 最多秒數；
- 最多無進展次數；
- 結果未知不重跑；
- 輸出 schema 驗證與必要證據條件。

純函式節點若一次呼叫就完成，仍填最多呼叫=1；模型節點若內含搜尋輪，輪數也必須在節點政策內。成功的必要條件是 typed output 通過 schema 驗證且外部判準完成；模型回「完成」不是條件。這直接遵守七欄位 stop rule 與「不得以模型說完成」的硬規則（docs/AGENT_ARCHITECTURE.md:81-103、CLAUDE.md:111-132）。

結果處置固定如下：

|節點結果|CLI code|獨立執行器|
|---|---:|---|
|節點成功|0|才可產生可餵下游的邊包|
|節點確定失敗|1|記錄診斷並停；不把錯誤改寫成模型下一輪的 prompt|
|節點結果未知|3|不重跑、不把部分輸出當成功；保留已知證據|
|節點護欄|4|停在護欄；不自動提高預算、不自動修護欄|

這裡的 code 語意不是新發明：既有模型回應的三值與未知不重試在 src/nova/契約/模型回應.py:41-84，工作流終止的完成／護欄／中止在 src/nova/契約/工作流.py:91-112。

## 3. Q3：扇出如何掛進誠實階段表？

### 3.1 先把階段出口做成真正窮舉

~~~python
from __future__ import annotations

from collections.abc import Mapping
from dataclasses import dataclass

from nova.契約.工作流 import 結束, 種類, 階段代碼
~~~

扇出階段的列就是形狀=執行形狀.扇出且扇出非 None；序列階段則必須是形狀=執行形狀.序列且扇出 is None。因此同一張階段表同時描述 TDD 的序列與研究的 bounded fan-out，執行器只依這兩個 typed 欄位選序列 runner 或執行扇出，轉移仍統一查五標籤出口。

實際落點是現有 src/nova/契約/工作流.py:201-221，並同步修改 src/nova/迴圈/狀態機.py:85-142 的查表與終局分類；開機驗證需檢查每一列恰有五個標籤、沒有未知 target、同一工作流每個節點都有角色／執行器。這也修掉目前審查第三出口藏在特判的問題（src/nova/迴圈/狀態機.py:104-122）。

### 3.2 N 的決定：資料決定，但硬上限固定

**推薦：N 由 PlanWorker 的 typed 分派資料決定，host 給每個工作流固定最大分支數，兩者同時存在。**

~~~python
from collections.abc import Callable
from dataclasses import dataclass
from enum import StrEnum

from nova.契約.節點 import (
    節點上下文,
    節點結果,
    結果代碼,
    邊包,
    分支識別碼,
)

輸入 = TypeVar("輸入")
輸出 = TypeVar("輸出")
依賴 = TypeVar("依賴")


@dataclass(frozen=True, slots=True)
class 分支工作(Generic[輸入, 依賴]):
    分支: 分支識別碼
    輸入: 邊包[輸入]
    依賴: 依賴
    必要: bool


class 扇出模式(StrEnum):
    屏障 = "barrier"
    串流 = "stream"


@dataclass(frozen=True, slots=True)
class 扇出政策:
    最大分支數: int
    最大並行數: int
    最少成功數: int
    必要分支: frozenset[分支識別碼]
    每分支最多token: int
    階段最多token: int
    最多秒: float
    最多呼叫: int
    模式: 扇出模式 = 扇出模式.屏障


@dataclass(frozen=True, slots=True)
class 分支結果(Generic[輸出]):
    分支: 分支識別碼
    結果: 節點結果[輸出]


@dataclass(frozen=True, slots=True)
class 扇出結果(Generic[輸出]):
    分支結果: tuple[分支結果[輸出], ...]
    成功產出: tuple[邊包[輸出], ...]
    缺口: tuple[分支識別碼, ...]
    終局: 結果代碼


def 執行扇出[輸入, 輸出, 依賴](

    *,

        [分支工作[輸入, 依賴], 節點上下文],
        節點結果[輸出],
    ],
    上下文: 節點上下文,
    政策: 扇出政策,

    ...
~~~

這裡的 ... 只是設計簽章；實作不可把 N 無限地交給模型。執行前先拒絕 len(工作)>最大分支數、重複分支、缺必要分支、總預算不可容納或模式不是扇出模式.屏障的第一版輸入；拒絕不是偷偷截斷。N 可以因題目與 PlanWorker 輸出不同，但永遠受 host 政策限制。這符合 Graph 原則「扇出分支共享輸入、彼此獨立、明確必要分支與最低成功數」（docs/AGENT_ARCHITECTURE.md:187-209）。

固定 N 的替代方案只適合完全固定的 benchmark：它讓成本好算，但題目一變就不是少派就是浪費腦。資料決定 N 的替代方案若沒有 cap 會變成無界遞迴。分勝負的判準是回放 30 個研究題目：若固定 N 不能覆蓋題目所需角度，固定方案輸；若資料決定方案有任何一題產生超過最大分支數或總額超限的計畫，未經 host 拒絕就算資料方案輸。第一版採「資料決定＋固定 cap」。

### 3.3 屏障還是串流：第一版選屏障

**推薦屏障。** 屏障是可靠性模型，不只是等待所有 future 的同步技巧：研究的整合／去重／引用驗證需要知道必要分支是否都回來，才能把「沒有找到」與「那一顆還沒回來」分開。這正是規格對屏障的定義與研究對 partial failure 的要求（docs/AGENT_ARCHITECTURE.md:187-209、docs/研究/工作流的多種形狀.md:42-77）。

串流方案只有在下游能逐筆獨立驗證、每筆結果可單獨交付、而且沒有 quorum／cross-branch comparison 時才贏。分勝負實驗：

    uv run pytest tests/整合/test_扇出可靠性.py -q

測試用三個假的分支，分別延遲 0.01／0.10／0.20 秒，最後一顆回結果未知；若整合節點在 0.20 秒前被呼叫，串流方案輸；若屏障等到必要分支並將最後結果標成 3、不把前兩顆拼成成功，屏障方案輸出的可靠性條件成立。第一版不開串流；這個測試未來若證明下游全是獨立 reducer，才可新增另一個具名執行形狀。

### 3.4 分支失敗如何決定整個階段終局

第一版研究扇出的 N 個分支預設都是必要分支；若要 optional，必須逐項在分派單宣告，不能由失敗後的 reducer 臨時放寬。終局採風險優先順序：

1. 必要分支有逾時、結果未知或其他可能已產生副作用的未知：整個階段結果未知，process code 3，不重跑。
2. 沒有未知，但扇出政策／預算／逾時護欄先發生，且有分支未被叫出：整個階段護欄，process code 4，不去提高上限。
3. 沒有未知或護欄，但必要分支有確定失敗，或成功數低於最少成功數：整個階段確定失敗，process code 1。
4. 所有必要分支成功且 quorum 通過：階段成功；optional 分支若確定失敗，成功產出仍要帶缺口，不能靜默丟掉。

timeout 必須落在第 1 類，因現有轉接器已把被殺程序的結果標成 unknown 並保留部分輸出（src/nova/載體/模型/轉接.py:266-292）；模型回應也明確把 timeout／權限被擋／上游等可能副作用情況歸結果未知（src/nova/契約/模型回應.py:41-84）。這個順序保守地遵守 at-most-once：有未知時，不因另一顆確定失敗就假裝所有狀態都知道。

### 3.5 扇出成本上限住在哪裡

上限住在 **harness 的扇出 scheduler 與單節點政策**，不住在 PlanWorker prompt，也不住在每一顆腦自己說「我差不多了」。位置如下：

- 節點上下文.停止：限制單節點呼叫、token、時間與無進展；
- 扇出政策：限制 N、並行度、每分支 token、階段總 token、總呼叫與時間；
- src/nova/迴圈/扇出.py：出分支前做 admission，回來後累計用量，任何上限到達即停止再派；
- src/nova/載體/模型/轉接.py／程序層：負責逾時與殺子程序，將未知保留下來；
- src/nova/載體/帳本.py 與階段記帳：記每個 execution／branch／node／attempt 的開始、結束、用量與終局。

現有 runner 在下一次呼叫前才看預算，而且明白說擋不到當下正在發生的呼叫（src/nova/迴圈/工作流.py:50-103，尤其 :70-89）；所以在 adapter 沒有 token streaming 的前提下，不能宣稱最多token能中斷一個已出門的 CLI。這是本設計的未決項，不掩飾成硬上限。

兩個方案：

|方案|保證|推薦|
|---|---|---|
|A：維持呼叫間檢查|能保證不再派下一顆，不能保證正在跑的那顆不超支；改動小|只作第一個 characterization，不可在文件上稱 hard cap|
|B：每顆模型呼叫放進可殺的程序邊界，結合 timeout／call cap；若轉接器可提供流式 usage，再即時中斷|能把「超支後不再派」升成「到達可觀測上限就殺掉」；仍要承認 provider 不回 usage 的家只能以時間／呼叫數限制|**推薦 B**|

分勝負實驗：

    uv run pytest tests/整合/test_扇出預算.py -q

用假的 h：第一顆回報 997,031 token，第二顆睡眠；政策設階段最多token=100_000。若第二顆被啟動，A 失敗；若第一顆只能在回來後被發現超支，B 的「即時 token 硬停」也尚未成立，只能標 soft limit；只有能在上限到達前停止子程序、階段回 code 4、帳本留下第一顆的未知／護欄證據，B 才勝。未完成這個實驗前，路線圖不能把扇出成本寫成已完成。

## 4. Q4：PlanWorker 怎麼設計？

### 4.1 輸入不是一句話

一句話是目標，不是完整輸入。PlanWorker 至少吃目標、現況、限制、可用節點與既有 provenance；現有任務只有描述／工作目錄／前情（src/nova/契約/工作流.py:114-126），而研究狀態需要 coverage、claims、gaps、乾輪與輪數（docs/研究/工作流工廠該切在哪.md:323-381）。

~~~python
from __future__ import annotations

from dataclasses import dataclass
from pathlib import Path

from nova.契約.節點 import (
    節點識別碼,
    證據項,
    停止政策,
)
from nova.契約.節點 import 節點上下文, 邊包, 節點結果
from nova.契約.分派 import 分派單


@dataclass(frozen=True, slots=True)
class 工件參照:
    識別碼: str
    結構: str
    路徑: Path | None


@dataclass(frozen=True, slots=True)
class 工作現況:
    工作目錄: Path
    已有工件: tuple[工件參照, ...]
    已有證據: tuple[證據項, ...]
    目前節點: 節點識別碼 | None
    缺口: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class 執行限制:
    停止: 停止政策
    允許網路: bool
    允許編輯: bool
    可用節點: tuple[節點識別碼, ...]


@dataclass(frozen=True, slots=True)
class 規劃輸入:
    目標: str
    現況: 工作現況
    限制: 執行限制
    可用工件: tuple[工件參照, ...]

~~~

可用節點是本次 host 明確交給 PlanWorker 的能力清單，不是全域 registry；PlanWorker 只能從清單挑選，不能自行發明節點或工具。這延續依賴要由呼叫者傳入、而不是執行者偷摸載體狀態的規則（CLAUDE.md:81-95）。

### 4.2 輸出是可驗證的分派單，不是 Graph DSL

~~~python
from dataclasses import dataclass
from enum import StrEnum

from nova.契約.節點 import (
    節點識別碼,
    分支識別碼,
    結構識別碼,
    停止政策,
)


class 分派問題代碼(StrEnum):
    未知節點 = "unknown-node"
    輸入結構錯誤 = "input-schema-mismatch"
    依賴不存在 = "dependency-missing"
    重複項目 = "duplicate-item"
    循環前置 = "cyclic-predecessor"
    超出扇出上限 = "fanout-limit"
    超出預算 = "budget-limit"
    缺停止政策 = "missing-stop-policy"
    缺驗收條件 = "missing-acceptance"


@dataclass(frozen=True, slots=True)
class 分派項目:
    識別碼: str
    節點: 節點識別碼
    輸入結構: 結構識別碼
    前置項目: tuple[str, ...]
    分支: 分支識別碼 | None
    必要: bool
    停止: 停止政策
    驗收出口: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class 分派單:
    版本: int
    項目: tuple[分派項目, ...]
    最大分支數: int
    總停止: 停止政策
~~~

分派單可以有順序、前置、分支與停止政策，但**沒有**條件表達式、任意 Python、字串函式名稱、無界 loop 或「模型說完成」欄位。因此它是可落盤、可驗證的資料，不是另一種編排語言。

PlanWorker 的節點簽章：

~~~python
type 計畫結果 = 節點結果[分派單]


def 執行計畫員(
    輸入: 邊包[規劃輸入],
    *,
    上下文: 節點上下文,
    依賴: 對抗依賴,
) -> 計畫結果:
    ...
~~~

此處的模型可以提出候選分派單，但不可以把候選直接當執行結果。驗證分派單必須由 deterministic code 執行：

~~~python
@dataclass(frozen=True, slots=True)
class 分派單問題:
    代碼: 分派問題代碼
    項目: str | None
    診斷: str


def 驗證分派單(
    分派: 分派單,
    *,
    可用節點: frozenset[節點識別碼],
    可用結構: frozenset[結構識別碼],
    總限制: 停止政策,
) -> tuple[分派單問題, ...]:
    ...
~~~

驗證內容至少是：項目識別碼唯一；節點與輸入 schema 在 host 宣告清單；前置圖無循環、每項有停止政策與驗收出口；N 不超最大分支數；總呼叫／token／時間不超配額；所有依賴與權限明確。問題非空就不執行。

### 4.3 誰把分派單變成真的執行？

是 harness 的 deterministic dispatcher，不是 PlanWorker：

~~~python
from collections.abc import Callable


def 執行分派單[輸出](
    分派: 分派單,
    *,
    已驗證: tuple[分派單問題, ...],
    執行節點: Callable[[分派項目, 節點上下文], 節點結果[輸出]],
    上下文: 節點上下文,
) -> tuple[節點結果[輸出], ...]:
    ...
~~~

這個泛型簽章只表示單一 workflow adapter 的調度邊界；異質的 TDD／研究輸出不能硬塞成 object，應由各 adapter 各自實例化。執行流程是：

1. host 讀分派單，先驗證；有任何分派單問題就 code 1 或 4（輸出契約壞掉用 1；預算／安全護欄用 4），零節點啟動。
2. host 將每一項對應到已知的節點物件與明傳依賴，建立節點上下文，再呼叫共同 runner。
3. runner 管理 barrier、預算、逾時、帳本、exit code 與 provenance；節點只做自己的決策。
4. 執行失敗由 runner／harness 負責收場；PlanWorker 不負責重跑，也不能自行改分派單後再執行。

這個責任分界修補目前的斷點：現在 CLI 直接建 TDD 角色並進 runner（src/nova/載體/命令列.py:855-937），而 workflow runner 的角色檢查仍固定讀全域 TDD 表（src/nova/迴圈/工作流.py:145-158）。新的 dispatcher 必須在同一個共用開跑前檢查後選 workflow，不得另開一條秘密的研究執行路徑（src/nova/載體/命令列.py:824-852）。

### 4.4 PlanWorker 的停止條件

PlanWorker 的成功不是「模型說已經規劃好了」，而是：

- 只產生一份非空分派單；
- schema 與版本合法；
- 所有節點／結構／依賴／權限都在 host 清單；
- 沒有循環、無界扇出、無界 re-plan；
- 預算與停止政策可計算且在上限內；
- 每項都有驗收出口與 provenance 起點；
- 驗證分派單回傳空 tuple。

第一版採一次產生：最多規劃次數=1。唯讀規劃不需要為了「修正格式」盲重跑；驗證失敗是 code 1，呼叫逾時／結果未知是 code 3，護欄是 code 4。若日後要允許修計畫，必須把「新計畫嘗試」做成一個明確、另有預算與新 execution／attempt 的節點，不能由模型自行遞迴呼叫自己。

兩個方案：

|方案|做法|推薦與判準|
|---|---|---|
|A：PlanWorker 與 dispatcher 合一|模型輸出後立即依文字叫節點|不採；只要一個未知名稱或少一個停止欄位，就會繞過契約|
|B：PlanWorker 只產資料，dispatcher 驗證／執行|模型與執行分離，失敗由 host 收場|**推薦**；若 test_分派單.py 能證明任何無效計畫都在第一個副作用前被拒絕，B 勝|

### 4.5 PlanWorker 是不是會產生圖的節點？

**不是 Graph runtime 的圖產生器。** 它是一個輸出分派單的普通規劃節點；分派單只是有限資料，host 將它餵給既有的階段表／組合函式。它可以選擇 N 個研究分支，但不能生成任意節點類別、任意程式碼、無界 edge 或 scheduler。

這與「不造編排 DSL」相容，因為資料的語意由驗證分派單與既有工作流規格程式碼固定，而不是由資料本身成為一門可執行語言。只有未來 trace 證明要跨程序 resume、active cursor、join／reducer 時，才考慮把同一份 typed 計畫轉成真正 Graph；目前研究裁決是延後（CLAUDE.md:68-79、docs/研究/圖住哪一層的對抗綜合.md:16-23,296-322）。

## 5. Q5：角色工廠與重構能力

### 5.1 先校正現況

src/nova/迴圈/角色提示.py:10-47 有測試員、實作員、重構員三個主要提示常數；src/nova/迴圈/角色提示.py:50-64 還有審查員。因此實際是四個硬編碼角色提示，不是三個。角色的形狀目前是角色 Protocol，實作是固定系統提示加可換的腦（src/nova/契約/角色.py:84-116、src/nova/載體/角色.py:16-50）。

### 5.2 現在的最小角色工廠

現在只有 TDD 與研究兩套角色，不需要 DI 容器、decorator 註冊表或設定 DSL。新增 src/nova/迴圈/角色工廠.py，只做 immutable blueprint 到既有固定提示角色的純組合：

~~~python
from collections.abc import Callable, Mapping
from dataclasses import dataclass
from types import MappingProxyType

from nova.契約.派工 import 派法
from nova.契約.角色 import 權限, 角色, 語言模型
from nova.載體.角色 import 固定提示角色


@dataclass(frozen=True, slots=True)
class 角色藍圖:
    識別碼: str
    名稱: str
    系統提示: str
    派法: 派法
    權限: 權限
    逾時秒: float


type 建腦 = Callable[[派法], 語言模型]


def 建角色(藍圖: 角色藍圖, *, 建腦: 建腦) -> 角色:
    return 固定提示角色(
        名稱=藍圖.名稱,
        系統提示=藍圖.系統提示,
        腦=建腦(藍圖.派法),
        逾時秒=藍圖.逾時秒,
        權限=藍圖.權限,
    )


def 建角色表(
    藍圖們: tuple[角色藍圖, ...],
    *,
    建腦: 建腦,
) -> Mapping[str, 角色]:
    結果 = {
        藍圖.識別碼: 建角色(藍圖, 建腦=建腦)
        for 藍圖 in 藍圖們
    }
    return MappingProxyType(結果)
~~~

TDD 與研究各自提供 TDD角色藍圖: tuple[...]、研究角色藍圖: tuple[...]，再呼叫同一個建角色表。新增角色只加一個 blueprint 或新增 workflow 自己的資料列，不改 factory；腦的建立仍由呼叫者傳入。這保留目前派工表是資料、工作種類目前只有例行／推理的簡單邊界（src/nova/契約/派工.py:16-36、src/nova/載體/派工表.py:14-30），也不把兩個工作流硬塞進同一套提示。

先寫的紅測試 tests/單元/test_角色工廠.py::test_研究角色不改變_TDD_角色表 要建立兩組 blueprint，使用 fake 建腦，斷言兩張表的鍵與 system prompt 互不污染；再加 test_新增一個藍圖不需修改工廠。如果 factory 讀全域表或依角色名稱猜腦，測試就會紅。

### 5.3 出現第三個工作流時才升級

第三個 workflow 出現前，不做選擇器。出現後若 CLI／API 真的需要從識別碼選工作流，才加一個普通 typed constructor mapping，不做 decorator 註冊 DSL：

~~~python
from collections.abc import Callable, Mapping
from dataclasses import dataclass
from enum import StrEnum
from typing import Protocol

from nova.契約.節點 import 停止政策
from nova.契約.工作流 import 任務


class 工作流代碼(StrEnum):
    TDD = "tdd"
    研究 = "research"


@dataclass(frozen=True, slots=True)
class 結果摘要:
    結束碼: int


@dataclass(frozen=True, slots=True)
class 工作流依賴:
    工作目錄: str


class 可執行工作流(Protocol):
    def 執行(self, 任務: 任務, *, 停止: 停止政策) -> 結果摘要:
        ...


type 工作流建造器 = Callable[[工作流依賴], 可執行工作流]


def 建工作流(
    代碼: 工作流代碼,
    *,
    建造器們: Mapping[工作流代碼, 工作流建造器],
    依賴: 工作流依賴,
) -> 可執行工作流:
    建造器 = 建造器們[代碼]
    return 建造器(依賴)
~~~

這個 mapping 是程式碼內的有限選擇，不接受模型或設定檔傳來的 Python；它只有在第三個 workflow 讓兩個 if／明確函式選擇真的重複時才出現。第一版仍用建TDD工作流、建研究工作流兩個明確函式，因目前 CLI 根本沒有 workflow 選擇（src/nova/載體/剖析器.py:198-265），且研究文件要求未指定 workflow 時 fail-closed、不要默認 TDD（docs/研究/工作流工廠該切在哪.md:323-381）。

### 5.4 「重構能力加強」怎麼從懇求變成實線？

目前重構提示已經寫了「不改測試、不加功能、不修 bug」等規矩，但那仍是模型收到的散文（src/nova/迴圈/角色提示.py:31-47）。重構要可靠，規則必須包住執行者：

~~~python
from collections.abc import Sequence
from dataclasses import dataclass
from pathlib import Path

from nova.契約.節點 import 證據項, 節點護欄
from nova.契約.工作流 import 任務


@dataclass(frozen=True, slots=True)
class 重構基線:
    工作目錄: Path
    測試檔雜湊: tuple[tuple[Path, str], ...]
    公開契約雜湊: tuple[tuple[Path, str], ...]
    行為證據: tuple[證據項, ...]


@dataclass(frozen=True, slots=True)
class 重構政策:
    允許路徑: tuple[Path, ...]
    禁止修改測試: bool
    必須重跑判準: bool
    允許意圖: frozenset[str]


def 建立重構基線(
    任務: 任務,
    *,
    測試檔: tuple[Path, ...],
    公開契約檔: tuple[Path, ...],
) -> 重構基線:
    ...


def 驗證重構(
    基線: 重構基線,
    *,
    任務: 任務,
    政策: 重構政策,
    變更檔: Sequence[Path],
) -> tuple[證據項, ...] | 節點護欄:
    ...
~~~

落地分四道：

1. **基線**：重構階段開始前保存測試檔與公開 schema／API 的 hash，並跑一次全綠判準。這使用既有「驗證綠→重構→驗證重構」的拓撲（tests/單元/test_重構階段.py:31-62、src/nova/契約/工作流.py:17-30）。
2. **範圍閘**：重構員回來後，確定程式檢查 changed paths；碰 tests/、超出允許路徑、改宣告的 schema／出口或修改設定策略，就回 code 4。不要靠重構員自己報告「我沒有碰」。
3. **行為閘**：強制執行獨立的驗證重構判準；它紅時沿用既有「護欄、不准 fix-forward」語意，不回重構（src/nova/迴圈/狀態機.py:125-142、tests/單元/test_重構階段.py:43-62）。
4. **規則登記**：把重構禁止改測試、重構只准宣告意圖、重構必須有基線、重構後必須驗證登記到 src/nova/載體/規則表.py，由包住角色的 src/nova/迴圈/工作流.py:161-199 呼叫；閘本身保持 fail-closed 與可測（src/nova/載體/規則表.py:1-5,124-225、src/nova/載體/閘.py:50-103）。

研究裡的 AST rename／extract／move 可以作為允許意圖與 deterministic 檢查的候選；設計意圖、外部契約與跨系統語意不能假裝全由 AST 證明。characterization／golden baseline 是行為比較的地基，mutation testing 只驗測試敏感度，不能取代新舊行為比較（docs/研究/重構模式.md:36-143）。因此「不准 feature／bugfix／migration」要靠政策、diff、baseline 與獨立判準共同抓，不能宣稱一支 prompt 已經能辨認所有語意變更。

第一個整合紅測試必須是：

    uv run pytest tests/整合/test_重構閘.py -q

測試用 fake 重構角色實際改一個 tests/ 檔；期待 wrapper 在審查前回 code 4、沒有呼叫審查員、基線與變更檔都留下結構化證據。再用 fixture 改變一個 golden output 而不改測試，期待驗證重構紅並護欄；只有「未改行為」才可進審查。這些測試補的是規則目前只在 prompt 的實線缺口，不改既有狀態機已背書的回退語意。

## 6. Q6：系統架構師要不要存在？

**要，而且與 PlanWorker 是兩個節點／兩個角色。**

### 6.1 為什麼不是同一個

現在研究產出與可執行設計之間確實有接縫：研究文件把 TDD 與 research 視為兩個 adapter，但需要一個 typed 工作流／狀態／停止政策才能接上（docs/研究/工作流工廠該切在哪.md:323-381）；目前實際 CLI 則直接建 TDD 四角色與 runner（src/nova/載體/命令列.py:855-937）。如果讓同一個模型既裁決研究證據的架構意義，又替自己排可執行工作，它可以把沒有來源的設計當成合理，把不能執行的步驟當成已派工。

兩個角色的輸入／輸出分工：

~~~python
from dataclasses import dataclass

from nova.契約.節點 import (
    節點識別碼,
    節點結果,
    節點上下文,
    結果代碼,
    結構識別碼,
    停止政策,
    證據項,
    邊包,
)
from nova.契約.分派 import 分派單


@dataclass(frozen=True, slots=True)
class 未決實驗:
    問題: str
    指令: tuple[str, ...]
    觀察: str
    勝負判準: str


@dataclass(frozen=True, slots=True)
class 節點規格:
    節點: 節點識別碼
    輸入結構: 結構識別碼
    輸出結構: 結構識別碼
    允許結果: tuple[結果代碼, ...]
    停止: 停止政策
    需要權限: str
    可否扇出: bool


@dataclass(frozen=True, slots=True)
class 架構決策:
    依據: tuple[證據項, ...]
    工作流: 工作流代碼
    節點: tuple[節點規格, ...]
    出口表版本: int
    未決: tuple[未決實驗, ...]
    風險: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class 架構輸入:
    目標: str
    研究證據: tuple[邊包[研究發現], ...]
    現況: 工作現況
    限制: 執行限制


def 執行系統架構師(
    輸入: 邊包[架構輸入],
    *,
    上下文: 節點上下文,
    依賴: 對抗依賴,
) -> 節點結果[架構決策]:
    ...


def 執行PlanWorker(
    輸入: 邊包[架構決策],
    *,
    上下文: 節點上下文,
    依賴: 對抗依賴,
) -> 節點結果[分派單]:
    ...
~~~

系統架構師把研究 evidence 轉成「哪些節點、契約、出口、停止、風險、未決實驗」；PlanWorker 把這份決策加上最新工作現況轉成有限分派項目。PlanWorker 不應只收一句目標；實際正式輸入是架構決策 + 規劃輸入.現況 + 執行限制。

### 6.2 兩者各自的停止條件

系統架構師成功的判準：

- 每個決策都有證據項 provenance；
- 每個節點規格都有輸入／輸出 schema、四種結果處置、停止政策與權限；
- 出口表版本與五標籤完整性驗證通過；
- 所有轉移 target 存在且有限，沒有無界 retry／fan-out；
- 研究的矛盾或缺口沒有被抹平，而是列入未決實驗，每個實驗有指令、觀察與勝負判準；
- deterministic validator 回傳空問題。

沒有來源、schema 缺欄、轉移不完整或實驗沒有判準，架構師回 code 1；呼叫未知回 3；host 上限回 4。這不是「架構師覺得通順」；是能被程式驗證的停止。

PlanWorker 成功的判準就是第 4.4 節的驗證分派單為空；它不重新判斷架構真偽。這個分工讓系統架構師成為研究到工作流的橋，PlanWorker 成為工作流到執行的橋。

### 6.3 合併方案與採用方案

|方案|優點|致命問題|
|---|---|---|
|A：一個「架構規劃員」同時做 architect + planner|少一次模型呼叫，流程短|研究證據、設計正確性、可執行性混成一個輸出；沒有獨立邊界能抓「設計合理但不能跑」|
|B：系統架構師 → PlanWorker → dispatcher|每一段都有 typed output 與 deterministic validator；可分開換腦與測試|多一個只讀模型節點與少量 token 成本|

**推薦 B。** 分勝負判準是用至少 30 筆過去研究輸入回放：若 A 的架構決策有任何無 provenance、缺 stop rule 或無法通過分派驗證，A 輸；若 B 的兩段驗證不能在第一個副作用前拒絕同一份壞輸入，B 也輸，必須先補 validator。成本不是讓 A 勝的理由，除非實測證明 B 的額外呼叫在全局預算內且驗證沒有抓到任何額外錯誤；在那之前保留兩個角色。

### 6.4 角色權限與 Graph 相容性

系統架構師只讀：可以讀研究工件、repo 狀態與既有 trace，不可編輯目標檔案；PlanWorker 也只產生分派資料，不直接編輯。可編輯權限只授予真正需要改 code 的實作／重構節點，權限沿既有角色與呼叫選項傳入（src/nova/契約/角色.py:41-116）。

兩者的輸出都只是契約/中的 frozen dataclass，透過組合函式進現有 workflow table；沒有 src/nova/圖/、沒有 runtime graph、沒有模型產生的 DSL。等 trace 顯示線性／單游標真的無法承受 active cursor、barrier recovery 或跨程序 resume，再把架構決策的有限節點規格升成 GraphSpec；現在的結論仍是延後（CLAUDE.md:68-79、docs/研究/圖住哪一層的對抗綜合.md:16-23,181-189）。
