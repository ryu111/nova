# 01 · 機械化閘：把規則從提示詞層降到載體層

> 依 `AGENT_ARCHITECTURE.md` §12：寫程式之前先產出 harness 五問（§2.2）與 loop 契約（§3.2）。

## 為什麼

現在 nova 的行為約束住在 `~/.claude/CLAUDE.md` 與 `~/.claude/rules/*.md`——那是**提示詞**。
規格 §2.3 講得很直白：

> 長時間、跨 session 的工作靠 harness，不靠提示詞。
> 「人工核准掛鉤」與「請模型小心的指令」是不同的控制。這些是執行期屬性，不是提示詞美學。

提示詞層的規則有三個問題：換一個模型就失效、模型可以「忘記」、沒有證據說它到底有沒有遵守。
**能機械化的規則一律降到載體層**，由 nova 執行；模型變成可抽換的元件。

## v1 的邊界（不要建過頭）

nova v1 是**約束「任何在這個 repo 上工作的 agent」的閘**，不是 LLM 的執行器。
放入不同模型（Claude Code / codex / gemini-cli）時，它們共用同一組 nova 閘，
所以受同一套行為流程約束。**跑模型的迴圈是後面的事**（§10 建置順序第 2 階），
`src/nova/迴圈/` 現在誠實地留空。

## 保證 vs 加速器（分清楚，不然會高估防護）

| 執行點 | 性質 | 為什麼 |
|---|---|---|
| GitHub ruleset（伺服器端） | **保證** | 誰都繞不過，包括管理員（bypass 名單空的） |
| CI required check | **保證** | 任何模型、任何工具推的 code 都要過 |
| git pre-commit hook | 加速器 | `--no-verify` 一行就繞過，設計如此 |
| Claude Code PreToolUse hook | 加速器 | 只對 Claude Code 有效，換模型就沒了 |

加速器的價值是**早 10 分鐘知道**，不是防護。每條規則的真正兜底一定要落在保證欄。

## Harness 五問（§2.2）

| 問題 | nova v1 的答案 |
|---|---|
| **Context** | 規則表：每條規則的代碼、名稱、適用閘點、負責層、要跑的指令。**刻意排除**模型的自然語言指令——風格類規則留在提示詞層 |
| **Action** | 只能執行規則表裡登記的檢查指令（ruff／mypy／pytest／git）。不開放任意 shell |
| **State** | 結構化檢查結果；持久證據是 git 歷史與 CI run log |
| **Policy** | fail-closed：任一規則紅 → 擋下，不放行。禁令指令（`--no-verify`、`--admin`）直接拒絕 |
| **Evidence** | `nova 閘` 的結構化輸出：規則代碼＋通過與否＋負責層＋實際輸出。人和模型看到的是同一份 |

## Loop 契約（§3.2，七欄位）

閘是一個**驗證迴圈**（§3.1 verification loop），不是重試迴圈：

| 欄位 | 內容 |
|---|---|
| Trigger | 提交前、工具呼叫前、PR／push main |
| Goal | 該閘點所有適用規則 `通過 = True` |
| Memory | 上一輪紅掉的規則代碼（不重播全部輸出） |
| Action policy | 只准跑規則表裡的指令；**不准改檔**——閘只判定，不修理 |
| Evidence | 每條規則的 exit code 與輸出 |
| Feedback | 紅掉的規則代碼＋中文原因＋**哪一層擁有修復** |
| Stop rule | **一輪就停**。全綠→放行；有紅→擋下回報。閘不重試，修理是呼叫端的事 |

「閘不重試」是刻意的：§8 反模式三禁止用「繼續試」當 loop 規格。閘的職責是誠實判定。

## 規則盤點：哪些能機械化、兜底在哪

| 現行規則 | 規則代碼 | 執行點 | 現況 |
|---|---|---|---|
| 專案結構（src layout、三層測試、設定不散落） | （pytest 測試） | 閘 提交／ci | ✅ |
| 機密不進版控 | `no-secrets` | 閘 提交／ci | ✅ |
| ruff 靜態檢查 | `ruff-check` | 閘 提交／ci | ✅ |
| ruff 格式 | `ruff-format` | 閘 提交／ci | ✅ |
| 型別 strict | `mypy` | 閘 提交／ci | ✅ |
| 測試（單元／平行／序列） | `pytest-*` | 閘 提交／ci | ✅ |
| 不准 `gh pr merge --admin` | `禁令` | ruleset ＝ 保證；PreToolUse ＝ 加速器 | ✅ |
| 不准 `git commit --no-verify` | `禁令` | PreToolUse ＝ 加速器；CI required check ＝ 保證 | ✅ |
| 語言：繁體中文（簡體字＋日文新字體） | `lang-traditional` | 閘 提交／ci ＋ commit-msg（**訊息只有加速器**） | ⚠️ 見下 |
| 不准刪測試 | `test-count` | 閘 提交（基準 HEAD）＋ ci（基準 `origin/main`） | ✅ |
| 測試金字塔比例 | ⚠️ 可算但門檻主觀 | — | 不做 |
| 固定負控真的做過 | ⚠️ 要判斷 | — | 不做，留在提示詞層 |
| 回應風格（第一行是動作、編號、下一步） | ❌ 自然語言 | — | 留在提示詞層 |
| 寫程式階梯（取最短可動解） | ❌ 需判斷 | — | 留在提示詞層 |
| 報告：失敗與跳過明講 | ❌ 自然語言 | — | 留在提示詞層 |

**盤點結論中「不能機械化」的那幾條同樣是交付物**——寫下來才不會誤以為它們有防護。

### `test-count` 的基準 ref（已修）

原本比對 HEAD 與工作區。CI checkout 之後工作區就是 HEAD，前 == 後永遠成立——
整條規則在 CI 上空轉，而且是**全綠地**空轉。

現在 `檢查測試數(根目錄, *, 基準="HEAD")` 收一個基準 ref：

| 執行點 | 基準 | 為什麼 |
|---|---|---|
| 閘 提交（本地） | `HEAD` | 還沒 commit，跟上一版比才有意義 |
| 閘 ci | `origin/main` | PR 要跟 base branch 比，不然抓不到「這個 PR 刪了測試」 |

傳遞方式是環境變數 `NOVA_TEST_COUNT_BASE`（shell 變數名的 ASCII 例外）。
`gates.yml` 裡只放一個常數字串與一行 `git fetch`，判斷邏輯在 `規則表.決定基準()`——
薄轉接、厚 nova。**抓不到基準時 fail-closed 當場紅**，不默默退回跟自己比。

順帶修掉一個同源的舊 bug：基準原本走 `git ls-files`（工作區的 index），
所以 `git rm tests/某支.py` 之後那個檔案不在清單裡，前後一起變少 → 放行。
基準改走 `git ls-tree -r <ref>`，看的是**那一版真正有什麼**。

### 還沒補的缺口

**squash 合併的 commit 訊息繞過 commit-msg hook。** main 上的訊息是 GitHub
從 PR 標題組出來的，本地 hook 碰不到。commit 訊息的繁體檢查目前只在本地生效，
**只有加速器、沒有保證**。修法：CI 加一條檢查 PR 標題，或改用 merge commit。

## 設計原則：薄轉接、厚 nova

`.pre-commit-config.yaml`、`gates.yml`、`.claude/settings.json` 裡**只准放一行**呼叫 nova。
理由：JSON／YAML 裡的 shell 片段沒辦法測試，而最高原則第一條說沒有測試背書就等於沒有保證。
規則邏輯全部進 `src/nova/`，每條都有測試。

```
.pre-commit-config.yaml ─┐                    ┌─ 靜態階段：語言、機密、測試數、ruff
gates.yml ───────────────┼→ uv run nova 閘 ──┼─ 型別階段：mypy
.claude/settings.json ───┘   （規則表）        └─ 測試階段：pytest（平行／序列）
（未來：codex／gemini-cli 的 hook 也指到同一支）

階段由小到大、一次一條序列跑：快的先給回饋，重的後跑，
而且不同時吃滿 CPU——資源互搶造成的紅燈是雜訊不是訊號。
```

## 不做的事

- 不重建 user 層的 `nova` MCP server 設定。`.venv/bin/nova` 會存在，但那是 CLI，不是 MCP。
- 不動 `gates` 這個 job 名稱——它是 required check 的 context。
- 不碰 `docs/AGENT_ARCHITECTURE.md`。
