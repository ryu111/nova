# 本地腦能做什麼：TDD 七階逐階探針

> **這是本機真端點的實測紀錄。** 沒跑到的格子寫「沒測」，不填猜的值。
>
> - 日期：2026-08-31
> - 端點：`http://127.0.0.1:8000/v1`（oMLX，`127.0.0.1:8000`）
> - 量的東西：TDD 七階 × 四顆本地型號，每一格跑一次，共 28 格
> - 判定：只看 git 狀態、判準指令退出碼與帳本欄位，不用另一個模型當裁判

## 為什麼要有這份東西

[`10-目標長什麼樣.md`](10-目標長什麼樣.md) 第七節主張把建構那 91% 的成本搬到本地。
但 `src/nova/載體/派工表.py` 到現在只有 `例行`／`推理` 兩列、兩列都是雲，
`src/nova/載體/模型/本地.py` 的 `審查資格理由` 還明講 9B 不能當審查員。

**所以「派給本地」在這份文件之前是一句沒有數字背書的話。** 這裡是那些數字。

## 怎麼跑的

每一格都從對應的起點**重新複製一份**拋棄式目錄（`/tmp/本地探針/`），跑完不重用。
下文提到的 `計算.py`、`test_計算.py`、`tests/` 等等都在那份拋棄式目錄裡，**不是本 repo 的檔**。

```bash
uv run nova 工作流 --用 local --模型 <型號> --起點 <階段> --最多步數 1 \
  --工作目錄 <拋棄式目錄> --提示檔 <拋棄式目錄>/題目.md \
  --判準 "python -m pytest -q" --帳本目錄 <拋棄式帳本> --逾時 600
```

`--最多步數 1` 是關鍵：不加的話 `--起點` 會一路往下走，量到的是整條流程不是那一階。
`審查` 那一格另外加 `--審查用 local`，否則審查員會照派工表落到雲上。

### 三個起點

七階的前提不一樣，所以起點有三個。**起點對不上前提，量到的就是別的東西的數字**：

| 起點 | 工作區長相 | 判準 | 題目 | 給哪幾階用 |
|---|---|---|---|---|
| 紅起點 | `計算.py` 的 `平均` 引用了還不存在的 `加總` | 紅 | 加純函式 `加總(數列)`，讓 `test_計算.py` 變綠 | `驗證紅`／`實作`／`審查` |
| 綠起點・待重構 | `加總` 已寫好但用手寫 `while` 迴圈累加 | 綠 | 不改行為、不改測試，把 `加總` 清乾淨 | `重構`／`驗證重構`／`驗證綠` |
| 綠起點・待寫測試 | `加總`／`平均` 都寫好且乾淨，`最大值` **不存在** | 綠 | 新增一支測試檔替還不存在的 `最大值` 寫測試，不要實作它 | `測試` |

### 每一階的起始狀態與成功條件

成功條件**一階一條，不共用**。前一版用「工作區被動過」當所有模型階的共同條件，
結果把「只寫了一份 `回報.md`」也記成重構成功——**寬鬆的判準會把失敗畫成成功**。
下表是這一輪用的判準，先寫死再量：

| 階段 | 起始狀態 | 叫腦？ | 成功條件 |
|---|---|---|---|
| `測試` | 綠起點・待寫測試（判準綠） | 是 | 新增一支測試檔，且判準**由綠轉紅**，紅的原因是 `最大值` 不存在 |
| `驗證紅` | 紅起點（判準紅） | 否 | 判準跑完，帳本 `gate_green` 是 `false`，狀態機照這個判定走 |
| `實作` | 紅起點（判準紅） | 是 | 改到 `計算.py`，且判準**由紅轉綠** |
| `驗證綠` | 綠起點・待重構（判準綠） | 否 | 判準跑完，帳本 `gate_green` 是 `true` |
| `重構` | 綠起點・待重構（判準綠） | 是 | 改到 `計算.py`、判準**維持綠**、且 diff 不改行為（人看 diff） |
| `驗證重構` | 綠起點・待重構（判準綠） | 否 | 判準跑完，帳本 `gate_green` 是 `true` |
| `審查` | 紅起點 | 是 | 沒測到——呼叫在發出前就被 `審查資格理由` 擋掉（見〈結果：型號 × 階段〉） |

`測試` 那一階的成功條件是**「判準轉紅」而不是「有新檔」**。
只要求「新增測試檔」的話，空白的檔案跟永遠通過的斷言都會被記成成功——
**那量到的是「會不會建檔」，不是「會不會寫出驅動需求的紅測試」。**

`__pycache__` 與 `.pytest_cache` 一律從 git 狀態濾掉：那是判準自己跑出來的，
算進去的話每一格都「有動」，而那正好是要用來抓「模型根本沒動手」的訊號。

失敗分四種：`工具回合用完`（撞到 `最多工具回合 = 8`）、`輸出解析不出來`（帳本
`failure_code` 是解析類）、`工作區沒被動過`（跑完但 git 是乾淨的）、`逾時`。
CLI 退出碼 4 是 `--最多步數 1` 的護欄，不是失敗訊號，
所以判定看的是判準指令的退出碼、git 狀態與帳本欄位，不是 CLI 的退出碼。

怎麼讀這張表：

- **`成功（判準階；未叫腦）` 的格子不是本地腦的成績。** 那一階跑的是判準指令，
  紅綠判定見上面〈每一階的起始狀態與成功條件〉那一列。
  這些格子對「派給本地」的意義是「本來就不需要腦」，不是「本地腦做得到」。
- **`沒測` 是 `審查資格理由` 直接回退出碼 2**、
  訊息 `local 沒有審查資格：9B 本地模型不能當審查員`，一次呼叫都沒發生。
  **沒發生的呼叫量不出東西**，所以這一格不是失敗，是沒測。
- **9B-4bit 的 `測試` 格是失敗，即使產出物是對的。** 它在第 7 回合寫出了合格的紅測試、
  判準確實由綠轉紅，第 8 回合又去叫不存在的工具想自己驗一次，撞上 `最多工具回合 = 8`。
  分類寫成 `工具回合用完` 而不是「失敗」，就是為了不把「不會寫測試」跟「寫完了不收尾」
  混成同一個症狀（細節見〈量的時候踩到的三件事〉第三點）。

### 決策表為什麼比能力表保守

三件事讓「單次全過」撐不起派工：

- **每一格 n=1。** `docs/研究/本地腦能力邊界.md` 記過同一顆模型同一條能力
  在三輪之間從 0/3 跳到 3/3。單次結果分不出「這顆模型做得到」與「這一次剛好做到了」。
- **題目只有三個，而且都很小。** 一個 `sum` 的純函式量不到多檔案改動、
  量不到既有程式碼的相依，也量不到長上下文。
- **判準只有 pytest。** 沒跑機械化閘（`ruff`／型別／禁令），
  所以「本地腦寫出來的東西過不過得了閘」這件事完全沒被量到。

## 量的時候踩到的三件事

**一、起點要跟那一階的前提對齊。** 前一輪二十八格共用一個紅起點，於是：
`重構` 跑在紅工作區上，量到的是「改行為把測試弄綠」；
`驗證綠` 也跑在紅工作區上，帳本 `gate_green` 是 `false`，
那一格根本不是「驗證綠」該量的情境。
這一輪把 `重構`／`驗證重構`／`驗證綠` 移到綠起點、`測試` 移到另一個綠起點重跑，
本文件只列重跑後的數字。**前提錯了，量到的數字再精確也是別的東西的數字。**

**二、`__pycache__` 會把「工作區沒被動過」洗掉。** 判準階跑完 pytest 之後
`git status` 一定髒。第一版判定沒濾掉它，四顆的判準階全部被記成「有動」——
而那正好是本來要用來抓「模型根本沒動手」的訊號。**量法就是成因。**

**三、四顆全都幻想過不存在的工具，而 9B-4bit 的 `測試` 格就是這樣掛的。**
帳本裡叫過 `bash`（`{"command": "python -m pytest -q"}` 這類）與 `run_command`，
但 `本地工具.規格` 只給三把：`read_file`／`grep`／`write_file`。
**它對自己有什麼工具的認知是錯的，而那個錯誤要花掉一整個回合才發現。**
9B-4bit 的 `測試` 格工具序列是 `read_file`×3 →（不存在的）`bash` → `read_file` →
`grep` → `read_file` → `write_file` →（不存在的）`bash`：三個回合花在讀不存在的
`tests/` 下的 `test_計算.py`，最後一個回合去叫不存在的 `bash` 想自己跑一次 pytest，
回合 8 撞上限，帳本記 `outcome=failed`、`failure_code=usage`。
**沒收尾的成功不是成功**，但病因是路徑探索與收尾規則，不是它不會寫測試——
**把 `最多工具回合` 從 8 調大只會讓它多繞幾圈再叫一次不存在的工具。**
