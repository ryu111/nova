# 外面怎麼講載體工程：七項工作，與該拆哪一格

兩篇外部文章對照 nova 現況。**這份不是新規範**——沒有測試背書的文件不是保證
（`CLAUDE.md` 的判準）。它是一次外部校準，答三個問題：
哪些 nova 已經有了、哪些 nova 做得比外面嚴、**哪一格外面已經拆掉而 nova 還留著**。

## 0. 兩篇是什麼，關係是什麼

| | 出處 | 形狀 |
|---|---|---|
| A | Anthropic Engineering〈Harness design for long-running application development〉（Prithvi Rajasekaran，2026-03-24） | 一條產品線的實測帳，有秒數與美金 |
| B | rari（@0xwhrrari）〈Harness Engineering: How to Build AI Agents That Don't Fall Apart〉（2026-08-29） | 把 A、OpenAI 的 Codex 那篇、Dario 的說法組成一套框架 |

**B 引用 A。** 所以這不是兩個獨立佐證，是「實測報告」與「在它上面搭的框架」。
先講這件事，不然「兩篇都這樣說」會被高估。

兩篇的方向剛好相反，而那個相反是本文的重點：

```
B  加法：七項工作、檢查清單、LEVEL 0→3   缺時間軸——不會告訴你哪一格該拆
A  減法：每次模型升級就拆掉一格           缺通用清單——只有一條產品線的帳
```

## 1. B 的七項工作，落在 nova 的哪裡

七項 nova 全部有實作。**差別在形狀，不在有無。**

| # | B 說載體要做 | nova 的落點 | 差在哪 |
|---|---|---|---|
| 1 | 把請求變成合約（`done_when`） | `src/nova/契約/工作流.py` 的任務與判準終局 | nova 的 done_when 是**可執行的判準指令**，不是 JSON 欄位 |
| 2 | 給一張地圖，不是一本手冊 | `CLAUDE.md` ＋ `docs/設計/` ＋ `src/nova/載體/規範落點.py` | 一樣。CLAUDE.md 有行數上限 ratchet 守著 |
| 3 | 工具邊界（危險動作要核准） | `src/nova/載體/禁令.py`，各家自帶載體關到最小 | nova **更嚴**：禁令解析 shell 之後看真正會執行什麼，不是字串比對 |
| 4 | 記憶外部化成持久狀態 | `src/nova/載體/進度.py`、工作流任務的前情欄位 | nova **更嚴**：進度檔不准放在工作目錄，否則模型會替未來的自己種話 |
| 5 | 先裝感測器再給自主權 | `src/nova/載體/閘.py` ＋ `src/nova/載體/規則表.py` | 一樣。規則只登記一份，三個閘點各一行呼叫 |
| 6 | 權限在模型外面執法 | `src/nova/載體/禁令.py`、`src/nova/載體/熔斷.py`、`src/nova/載體/預算.py` | 一樣 |
| 7 | 留軌跡、本地復原 | `src/nova/契約/帳本.py`（事件）＋ `src/nova/契約/成果.py`（一次工作一筆） | 一樣，但收據欄位有缺，見第 3 節 |

### 1.1 兩處 nova 已經走得更遠

**（甲）「從來不紅的規則是刪除候選」——A 的減法，nova 已經機械化了。**

`src/nova/契約/帳本.py` 的規則開始／規則結束那兩種事件，註解寫的是
「這是哪條規則在守東西唯一的資料來源」。A 整篇在講「每次模型升級要重新檢視載體、
拆掉不再負重的部分」，但他們靠**人讀日誌**做。nova 的帳本讓這件事可以用查詢回答。
這是兩篇文章跟這個 repo 之間最尖的一個連結，而且它已經在了。

**（乙）四值退出碼，B 的框架裡沒有對應物。**

B 的迴圈草稿是「重試三次，還不行就轉人工」——只有一種出口。它分不出
「護欄按設計生效」與「東西壞了」，而 `src/nova/契約/工作流.py` 的結束代碼
docstring 已經說明為什麼那個分不出來很貴：自動修復迴圈看到「中止」會去修，
而護欄最省事的修法是把上限調高，那是自己拆執法點。

B 的清單裡也沒有「結果未知不准重跑」這一格。

## 2. A 的論點不是「他們做了三個 agent」，是減法

一般會把 A 讀成「Planner／Generator／Evaluator 三 agent 架構」。那是表面。
它的論點是：**每一個載體元件都編碼了一個假設——關於模型單獨做不到什麼，
而那些假設值得定期壓力測試。**

同一套載體在三代模型上長不一樣，三次都是**拆掉**：

```
Sonnet 4.5   context reset ✓    sprint 分解 ✓    Evaluator 每輪 ✓
Opus 4.5     context reset ✗    sprint 分解 ✓    Evaluator 每輪 ✓
Opus 4.6     context reset ✗    sprint 分解 ✗    Evaluator 只做一次末檢
```

拆的理由都一樣：那個元件當初補的是模型的缺，模型補起來之後，
它就從保護變成開銷。

### 2.1 那份帳說錢花在哪

A 的第二代（瀏覽器 DAW，約 3 小時 50 分、124.70 美金）逐階段：

| 階段 | 耗時 | 成本 | 佔比 |
|---|---|---|---|
| Planner | 4.7 分 | 0.46 | 0.4% |
| 建構（三輪合計） | 3h20m | 113.85 | 91% |
| QA（三輪合計） | 25 分 | 10.39 | 8.3% |

第一代（2D 遊戲製作器）是 6 小時、200 美金；同題目單 agent 是 20 分鐘、9 美金，
但核心功能是壞的（實體對輸入沒反應）。

**規劃 0.4%、審查 8.3%。** 這對 nova 有直接意義：如果排程實測到「每輪燒完前三階、
死在審查」，那不是「審查本來就貴」，要查的是**派工有沒有把審查丟進推理列**
（`src/nova/載體/派工表.py`）。A 的帳說審查在正常配置下便宜到可以忽略。

### 2.2 三個可以直接用的細節

1. **Evaluator 比 Generator 好調。** 讓生成者自我批判很難；讓獨立評分者不要太寬鬆
   只是提示工程。這正是硬規則「不得讓同一個對話自寫自評」的外部佐證。
   A 還多說一句：**預設狀態的模型當 QA 表現很差**——會先找到真問題、
   再自己說服自己那不嚴重，而且測試很淺。要靠讀 evaluator 的日誌、
   找它跟人判斷分歧的地方、改提示，跑好幾輪才調得起來。
   nova 對應的接縫是 `src/nova/迴圈/審查.py` 與 `src/nova/迴圈/角色提示.py`。

2. **每個階段開工前先協商驗收合約。** 生成者提「我要蓋什麼、怎麼算成功」，
   評估者審「你是不是在蓋對的東西」，兩邊迭代到同意才動工。他們某一個 sprint
   有 27 條驗收標準，失敗回報具體到檔名行號與條件式該怎麼改。

3. **評分標準的措辭會改變輸出。** 在標準裡加一句「最好的設計是博物館等級」，
   視覺結果整個收斂過去。這是提示工程沒被預期的槓桿。

## 3. 缺口：一次執行結束該留一張收據

B 主張每次執行留一張收據，理由是三件事：**模型升級可比較、回歸可歸因、稽核可做**。

`src/nova/契約/成果.py` 現在落盤十欄：
run_id、task、outcome、exit_code、started_at、ended_at、steps、tokens、cost_usd、source。

對照 B 的收據，差這幾樣：

| B 的欄位 | nova 現況 | 補起來的成本 |
|---|---|---|
| policy_version | 沒有 | **最便宜**：規則表的 git hash，`src/nova/載體/git查詢.py` 已經在了 |
| rollback_point | 沒有 | 執行前的 commit sha，同上 |
| accepted_artifact | 沒有 | PR 號或 commit sha |
| tests: {passed, failed} | 只有判準綠這個布林 | 要解析 pytest 輸出，較貴 |
| human_corrections | 沒有 | 要先定義什麼算「人介入」，最貴 |
| retries、tools_used | 在**事件帳本**，不在成果上 | 只是把彙總數字搬過去 |

前兩格特別值得：沒有它們，「這次跑爛了是因為上禮拜改了規則表」這個問題事後問不出來
——而那正是規則表天天在改的期間最會發生的事。

**這一節是待辦，不是已完成。** 要動的時候照規矩走：先寫會紅的測試。

## 4. 三個待決，不是決定

1. **審查要不要條件化。** A 把 Evaluator 從每輪改成一次末檢，判準是
   「任務相對於模型可靠能力的位置」——落在能力邊界上才值那個錢。
   nova 現在每輪必審。注意兩者管的層次不同：硬規則管的是**誰來審**
   （不准自寫自評，這條不動），A 說的是**要不要審**。
   放寬閘是人的決定；真要動，可動的形狀是「頻率跟著階段走」
   （重構階段仍每輪審，因為它最容易假綠），不是拿掉審查。

2. **reset 是 by construction，但它仍然是一個假設。**
   A 對比 compaction（原地摘要、同一個 agent 繼續，消不掉 context anxiety）
   與 context reset（清空重開、靠交接檔接續）。nova 每階段開新的 CLI 子程序、
   靠任務的前情欄位交接，**天生就在 reset 那一側，沒有選擇成本**。
   A 在 Opus 4.5 把 reset 拆了；nova 保留合理（它餵的是本地模型與三家 CLI）。
   但照第 2 節的邏輯，這是**該定期重測的假設**，不是永久設施——每換一顆腦問一次。

3. **收據補哪幾欄。** 見第 3 節的表，由人挑。

## 5. 這份文件跟 07 的分工

`docs/設計/07-節點是一等公民.md` 決定的是節點、扇出、計畫員、角色工廠的**形狀與順序**。
這一份不決定形狀，只做外部校準：它唯一的新主張是第 2 節那條——
**載體要定期拆一格，而 nova 已經有拆的依據（帳本）卻還沒有拆的習慣。**
