# 並行跑很多條要注意什麼

2026-08-31 一天之內用 `nova 工作流` 並行跑了九條線、收了八個 PR。
這份記的是**那天撞到才知道的東西**——規劃的時候一條都沒想到。

## 三種互撞，各要一種解法

並行的線會在三個不同的地方互相踩，而且它們**看起來都像「測試壞了」**：

```
   ①  寫同一個檔      後寫的靜默蓋掉先寫的，兩邊的提示都不提對方
   ②  搶同一顆 CPU    對時間敏感的檢查逾時 → 假紅
   ③  合併同一條 main  每合併一個，其他分支都要 rebase 並重跑 CI
```

| | 解法 | 住哪 |
|---|---|---|
| ① 寫檔 | 宣告寫入範圍，開跑前擋相交；再加 worktree 真隔離 | `迴圈/扇出.py`、`迴圈/計畫.py` |
| ② CPU | 跨程序的鎖，鎖是**機器的**不是專案的 | `載體/閘鎖.py` |
| ③ 合併 | 沒有解法，序列收。那是 required check 的固有成本 | — |

②最危險，因為它產生的紅**看起來像真的**。負控執行器對每把刀的
`最多秒` 是 2.0，機器超載時刀跑不完被殺，判成「這把刀沒被殺掉」——
一支好好的測試被報成壞的，而下一步通常是有人去把它「修好」。

## 全域瓶頸：所有線都要改的那個檔

`tests/負控/登記.py` 是一個大 tuple，**每條線都要在檔尾 append 自己的變異刀**。
那天六條線，同一種 append 衝突解了四次。

代價不是「解衝突很煩」，是**它讓所有線序列化**：
並行度再高也沒用，瓶頸不在算力，在那個檔。

判準可以一般化：**找出「每條線都要碰」的那個檔，那就是並行度的上限。**
沒有它，六條線就是六條線；有它，六條線等於一條。

## 派工描述要寫什麼

那天九份任務描述試出來的，每一條都是踩過才加的：

1. **寫入範圍**（哪幾個檔可以動）——不寫的話它會順手改別條線正在改的檔。
2. **哪幾個檔明確不准動**——比只寫「可以動什麼」有效，因為它會為了讓閘綠而去改。
3. **要登記變異刀**——漏寫的話交回來的東西沒有負控，得自己補。
4. **交件前跑哪幾道閘**——寫了它也可能沒跑（那天有一條宣稱跑過但 mypy 是紅的），
   所以**收的時候一定要自己跑一次**。
5. **不要做什麼**——「不要做合併回主線的機制」這種話很有效，
   它會自動把範圍收在該收的地方。

## 收的時候一定要自己跑閘

那天一條線的審查回 PASS、宣稱「交件前自己跑過 `nova 閘 ci`」，
但 mypy 是紅的（測試 monkeypatch 的名字沒被明確 re-export）。

**這就是硬規則第 2 條的實例**：不得以「模型說完成了」當停止條件。
模型說跑過閘，跟閘真的綠，是兩件事。

## 判準要配合任務的形狀

`--判準` 預設是 `uv run pytest -q`，但那不是每種任務都適用：

| 任務形狀 | 判準 |
|---|---|
| 一般 TDD | `uv run pytest tests/<那支>.py -q` |
| 產出是文件不是程式碼 | `test -f docs/設計/<那份>.md` |
| 從實作階段接手（測試已寫好） | 指向那支測試，並加 `--起點 impl` |

## 端到端測試被自己的護欄擋住時

那天要測「收尾時真的去跑驗收」，端到端測試一直紅：假 CLI 只吐實錄、不寫檔，
所以 TDD 前六階全部被「工作區沒被動過」判成結果未知。

**那是護欄在正確工作**，只是擋在要測的東西前面。解法是從 `--起點 review` 進去
——審查階段不動工作區，走得完，而收尾那一段是所有起點共用的。

一般化：**要測收尾，就找一條走得到收尾又不觸發前面護欄的最短路徑**，
不要為了讓測試通過去放寬護欄。
