# 05 測試怎麼跑最快

> 量測環境：macOS 26.6、Apple Silicon 16 核、Python 3.13、pytest 8 ＋ pytest-xdist。
> 2026-08-29 量的。下面的曲線那節是同一天稍晚重量的（套件已長到 506 支收集）。
> 這一節的舊數字是 319 支那時候的，保留是因為機制的推論踩在它上面。
> **換機器、換套件大小，下面每個數字都會變**——
> 所以每一節都寫了「什麼時候要重量」。

## 為什麼有這份文件

閘的門檻是**秒數，不是工具名**。commit 前的預算抓 10 秒，塞不進去的往後放。
理由很現實：閘慢到讓人想用 `--no-verify`，繞過一次，閘就等於不存在。

但「怎麼把測試跑快」這件事的知識，原本散在四個地方的程式碼註解裡。
**使用者不看 code。** 散在註解裡的知識等於沒有記錄——所以集中在這裡一份。

## 現在的數字

```
單元層  178 支   0.07 秒   ← 純函式，零子程序
整合層   89 支   5.60 秒   ← 會 fork（假 CLI、巢狀 pytest）
驗收層   52 支   1.38 秒   ← 使用者那句話成不成立
────────────────────────
全部序列 319 支  5.81 秒
全部 -n 4        2.34 秒

nova 閘 提交（7 條）  1.25 秒   ← 大頭是 test-count 的 0.79 秒（git 操作，不是測試）
nova 閘 ci（8 條）    4.77 秒   ← CI 上 7.0 秒（4 核只開 3 個 worker ＋ mypy 冷快取）
```

## 做法一：假 CLI 怎麼做，差 100 毫秒一支

三家 LLM CLI 不能在 CI 上真的跑（燒 token、要認證），所以用**假 CLI**：
一支印出預錄 envelope 的小腳本。做法有四種，速度差很多。

| 做法 | 一支測試的成本 | 抓得到什麼 | 抓不到什麼 |
|---|---|---|---|
| A. 每支測試重寫一份執行檔 | ~112 毫秒 | argv 形狀、旗標順序 | 真 CLI 收不收這組旗標 |
| B. **session 共用一份，行為靠環境變數切** | ~14 毫秒 | 同上 | 同上 |
| C. monkeypatch 掉 `subprocess.run` | ~0 毫秒 | 解析邏輯**與 argv 形狀**（見訂正） | **程序邊界**——執行檔有沒有 +x、shebang 對不對、逾時有沒有真的殺、工作目錄有沒有真的套用 |
| D. 真的呼叫 CLI | 30–600 秒＋token | **旗標真的有效嗎** | — |

A 跟 B 差的那 **98 毫秒**是這樣量的（n=15 取中位數）：

```
新寫出來的執行檔，第一次執行   112 毫秒
同一支重複執行                14 毫秒
                             ──────
每支測試白付                  98 毫秒
```

那 98 毫秒是 macOS 對「剛出現的新執行檔」的第一次檢查（簽章／隔離屬性）。
**同一份內容換個路徑就要再付一次**，所以「每支測試 `tmp_path` 一份」是最貴的做法。

B 的關鍵是：**行為靠環境變數切，不靠重寫檔案內容**。

```python
@pytest.fixture(scope="session")
def 假CLI群(tmp_path_factory):        # 整個 session 一份
    ...
@pytest.fixture
def 做假CLI(假CLI群, tmp_path, monkeypatch):   # 每支測試只換環境變數
    monkeypatch.setenv(f"NOVA_FAKE_{家}_TRANSCRIPT", ...)
```

**B 的缺點**（要寫出來，不然下一個人會踩）：

1. session 共用＝**平行時每個 xdist worker 各建一份**，不是全機一份。
2. 環境變數是**跨程序的全域狀態**，一定要用 `monkeypatch.setenv` 讓它自動還原。
3. 假 CLI 的檔名變成識別身分的東西（`fake-codex` 知道自己是 codex），
   換名字會靜默壞掉——所以檔名的意義要寫在 fixture 的 docstring 裡。

**C 為什麼不用**——這一段第一版寫錯了，訂正如下。

第一版寫的是「它連指令都沒組，`--add-dir` 打錯字它照樣綠」。**那要看替身裝在哪一層。**
實測把替身裝在 `src/nova/載體/模型/執行.py` 的 `subprocess.run` 接縫（轉接器**下方**）：
monkeypatch 收到的 argv 與真的 fork 收到的**逐字元相同**——`--tools`、`--setting-sources`、
旗標順序全都還驗得到。

C 真正瞎掉的是**程序邊界**，五條負控實測全部驗證：

| 破壞什麼 | fork | monkeypatch |
|---|---|---|
| 執行檔沒有 `+x` | 紅（`PermissionError`） | **綠** |
| shebang 指到不存在的直譯器 | 紅（`FileNotFoundError`） | **綠** |
| 子程序卡住要被殺 | `unknown`／timeout | **success** |
| 工作目錄有沒有真的套用 | 印出真 cwd | 印出預錄字串 |
| 環境變數有沒有真的到子程序 | 有 | 沒有 |

所以 `test_逾時會被殺掉並標成timeout`、`test_工作目錄真的傳下去`、
`test_執行檔不存在要當場炸` 這幾支的**主題就是程序邊界**——改成 monkeypatch
不是加速，是刪掉它們要驗的東西。

而「真 CLI 收不收這組旗標」是 **B 跟 C 一起**抓不到的：把 `--tools` 打錯成 `--tool`，
假 CLI 不解析旗標，兩條路都綠。那一格只有 `-m 真cli` 守得住。
**墊片證明的是轉遞形狀，不是可達性**——這句沒錯，錯的是我把它掛在錯的地方。

**D 為什麼非有不可**：只有它抓得到「真 CLI 收不收這組旗標」。
所以留一組 `真cli` 標記的測試，兩個閘都排除，手動 `-m 真cli` 跑。

實測收益：`test_委派給其他llm.py` 從 A 換成 B，**3.02 秒 → 1.41 秒**（19 支）。

## 重量：套件長 1.6 倍之後，轉折點沒有動

2026-08-29 稍晚重量。同一台、`-p no:randomly -m "not serial"`、單次。
套件從 319 支長到 **506 支收集／471 支跑**：

```
序列   8.67 秒
-n 2   4.84 秒
-n 4   3.73 秒  ← 最快，跟 319 支那時候同一格
-n 8   4.90 秒
-n 12  4.99 秒
-n 16  5.75 秒
```

**這排除掉候選表的第一項（xdist 的 IPC 與排程開銷）。** 那一列自己指定的驗法是
「把測試數灌到十倍，看轉折點會不會右移」——套件長了 1.6 倍、序列時間長了 1.5 倍，
**轉折點還在 n=4**。如果瓶頸是「測試量少時 IPC 攤不掉」，它該右移。沒有。

### 分堆之後才看得出來：兩條相反的曲線

把假 CLI 重的那七個檔跟其餘分開量（同上條件，單次）：

```
假 CLI 那組（112 支）  序列 4.01   n2 3.32   n4 3.71   n8 4.85
單元＋驗收（320 支）    序列 2.00   n2 1.38   n4 1.11   n8 1.57
```

- **假 CLI 那組平行度幾乎買不到東西**（最好 1.21 倍），而且**過了 n=2 就單調變壞**，
  n=8 比序列還慢。
- 其餘拿到 1.80 倍，轉折在 n=4。

**兩條相反的曲線混在一起，才會看起來像「平行到 4 就見頂」。**

機制對得上（**但這是假說，沒有隔離證明**）：`tests/conftest.py` 的 `假CLI群` 是
`scope="session"` ＋ `tmp_path_factory`，所以**一個 worker 一份、一份三支**——
n 個 worker 就是 3n 支「新路徑的執行檔」，每支付一次 macOS 那 ~98 毫秒的首次執行檢查。
n2→n8 多 18 支，上界 1.79 秒；實測那組退化 1.53 秒。同一個量級。

**要把它從假說升級成結論，只有一個實驗**：把 `假CLI群` 改成全 worker 共用的
固定路徑（或建完先預熱執行一次），再量同一條曲線。**還沒做。**

## 做法二：worker 開幾個——不是越多越快

同一套測試，3 次取中位數：

```
序列    5.81 秒  ████████████████████
-n 2    3.52 秒  ████████████
-n 4    2.34 秒  ████████            ← 最快
-n 8    2.79 秒  █████████
-n 12   3.43 秒  ███████████         ← 0.75 × 16 核，原本的設定
-n 16   3.69 秒  ████████████        ← -n auto，吃滿
```

**worker 越多越慢**——這是量到的，曲線在上面。

**但機制沒有量到，別把它當結論。** 第一版寫「因為每個 worker 都要自己 import
整套測試，那筆固定成本不會因為核心多就變便宜」，這條推理有漏洞：
**worker 是各自的程序，import 是同時發生的**，不是一筆一筆加上去。
（這一條是把文件派給 agy 審查時抓到的，見那次的 commit 訊息。）

現在能說的只有：**這套測試不是 CPU-bound**（全程只用到 213% CPU），
而且 4 個以上就開始變慢。為什麼變慢有三個候選解釋，一個都還沒量：

| 候選 | 怎麼驗 |
|---|---|
| xdist 的 IPC 與排程開銷（測試量少時攤不掉） | 把測試數灌到十倍，看曲線的轉折點會不會右移 |
| **Apple Silicon 的大小核**——16 個「核心」不是同一種核，第 13～16 個 worker 落在能效核上 | 在核心同質的機器（Linux／x86）上重量一次 |
| 每個 worker 的固定啟動成本重疊得不完全 | 量單一 worker 的啟動到收第一支測試的時間 |

**所以 `最多worker = 4` 是這台機器調出來的數字，不是通則。**
換機器就要重量——那正是下面「什麼時候要重量」那節在講的事。

所以旋鈕不是「吃幾成核心」，是**上限**：

```python
平行成數 = 0.75      # 不吃滿：留 1/4 給作業系統與 pytest 主控
最多worker = 4       # 不超過這套測試攤得掉的量
平行度 = max(1, min(最多worker, int(核心 * 平行成數)))
```

**上限只會往下壓，不會把小機器補上去**——CI 是 4 核，算出來還是 3，一點都沒變。

**缺點與失效條件**：套件長大之後這個上限會變成瓶頸。
**重量的時機是「序列時間超過 ~15 秒」**——那時每個 worker 分到的工作量才攤得掉
自己的啟動成本。在那之前調高只是多付啟動費。

（這一節推翻了自己上一版的結論。上一版寫「調低是拿這台機器的最佳值換掉在別台機器
也合理」，那個推論有洞：慢下來的原因不是「這台機器」，是 import 成本，
那在任何機器上都存在。）

## 做法二之二：`--lf` 會**綠著漏**——這條最危險

`--lf`（只跑上次紅的）是 TDD 內圈最省時間的按鈕：有紅時 5.87 秒 → 0.14 秒，**42 倍**。
`CLAUDE.md` 也把它列在常用指令裡。

**但它會綠著漏，而且是可重現的。** 實驗（在乾淨快照上做的）：

```
1. 讓 test_模型回應.py 有一支紅 → 跑全套，記進 cache
2. 同一次改動裡：修好那支紅，並且讓 tests/單元/test_角色.py 整個 import 失敗
3. pytest --lf   →  1 passed，退出碼 0，全綠
   pytest tests/單元  →  0.06 秒抓到 Interrupted: 1 error during collection
```

原因：`--lf` 會**跳過收集**「沒有已知失敗」的檔案，那個壞掉的檔根本沒被 import 過。

> **`--lf` 是重播工具，不是驗收工具。** 絕不能拿它當「可以 commit 了」的判準——
> 那是提交閘的工作，而提交閘跑的是完整的 `pytest tests/單元`。

`--sw`（stepwise）有兩個坑：這個 repo 裝了 pytest-randomly，`--sw` 三次 deselect 數
是 277／261／339 **每次都不同**（語義直接壞掉，要配 `-p no:randomly`）；
而且它續跑時會 deselect 掉上一輪在紅點之前跑過的測試——**那些沒對著修正後的程式碼跑過**。

`--ff` 是**排序**工具不是**篩選**工具，全部測試照跑，三次實測 5.87／6.06／6.61 秒，
跟全套基準 5.81 秒一樣。沒省到任何東西。

## 做法二之三：為什麼不導入 testmon

testmon 用 coverage.py 追每支測試碰到哪些 code block，改動後只跑受影響的。
**在這個 repo 有兩條系統性盲點，而且都打在最貴、最要緊的測試上。**

1. **子程序盲。** coverage.py 官方明說**預設不量子程序**。而 nova 有 5 個測試檔、
   60 支測試靠 fork 跑，佔幾乎 100% 的執行時間。最尖銳的一例：
   `tests/整合/test_命令列.py` **一個 nova 模組都沒 import**——它對原始碼的所有相依
   都穿過 `nova` 執行檔這個子程序。在 testmon 眼裡它的相依集合是**空的**。
   於是改了 `規則表.py`，testmon 會說「沒有受影響的測試」，
   而 `test_提交閘在本repo上是綠的`——那支證明整套閘還活著的元測試——**不會跑**。
2. **靜態檔盲。** testmon 不追非 Python 檔，而這裡有一批驗收測試的輸入正是那些：
   `test_文件即事實.py` 掃 CLAUDE.md 與 `docs/設計/*.md`、
   `test_CI接線.py` 讀 `gates.yml`、`test_機密不進版控.py` 問 `.gitignore`。

**而且它能省的上限是 0.02~0.07 秒**（提交閘 1.25 秒的不到 6%，人的反應閾值都到不了）——
因為 `pytest tests/單元` 的 0.182 秒裡有 0.16 秒是啟動與收集的地板，
178 支測試自己的執行時間在 `--durations` 裡合計是 **0.00 秒**。

> 拿兩條系統性漏測，換一個沒人感覺得到的加速。

**真要壓提交閘的時間，槓桿在 `test-count` 的 0.79 秒**（佔 64%，而且它是 git 操作不是測試）。

## 做法三：分層是時間預算，不是分類學

```
tests/單元/   純函式、零 I/O、零子程序   →  0.07 秒 / 178 支
tests/整合/   跨模組、真的 fork          →  5.60 秒 / 89 支
tests/驗收/   使用者說的那句話成不成立    →  1.38 秒 / 52 支
```

一支會 fork 的測試混進單元層，單元層就從毫秒級掉到秒級，而**內圈的價值全在毫秒級**。
所以這條有機械背書，不是口頭約定：

```python
# tests/驗收/test_專案骨架.py::test_單元層不准fork子程序
_會fork的痕跡 = ("import subprocess", "S_IEXEC", "跑cli(")
```

實測收益：把 fork 的測試搬出單元層之後，**提交閘 7.10 秒 → 1.18 秒、
單元層 5.91 秒 → 0.10 秒**。

## 做法四：`serial` 標記——會搶資源的單獨跑

有些測試自己會啟動 pytest 或 ruff（例如「提交閘在本 repo 上是綠的」）。
這種東西跟別的測試平行跑會**互相搶 CPU**，然後隨機紅。

```
pytest -m "not serial" -n 4 --dist worksteal   # 平行這一批
pytest -m "serial"                              # 再序列跑這一批
```

**資源互搶造成的紅燈是雜訊不是訊號。** 雜訊會訓練人忽略紅燈，那比慢更貴。

## 四個閘點各跑多少

| 階段 | 跑什麼 | 實測 | 由誰執行 |
|---|---|---|---|
| 內圈（寫 code 時） | `pytest -k <關鍵字> -x` | < 0.2 秒 | 你自己，隨時 |
| commit 前 | `nova 閘 提交`（7 條，含單元層） | 1.28 秒 | pre-commit hook |
| PR／push main | `nova 閘 ci --全部跑完`（8 條） | 4.77 秒（CI 上約 15 秒） | GitHub Actions |
| 手動 | `pytest -m 真cli` | 分鐘級、燒 token | 人 |

原則：**慢的往後放，快的往前放**，而門檻是秒數不是工具名。
mypy 在這個專案 < 1 秒，所以它留在 commit 前；整合測試 5.5 秒，所以往後放。

## CI 那一層：15 秒裡有 8 秒不是在做事

一趟 job 中位數 15.0 秒（n=30）。拆開來只有兩塊：

```
約 8 秒  開一個 job 的固定成本
         set up job 1.0 ＋ checkout 1.0 ＋ 裝 uv 2.0 ＋ uv sync 2.0
         ＋ git fetch 0.5 ＋ 排程收尾 1.5
約 7 秒  閘本身（本機 4.8 秒。差在 CI 只有 4 核 → -n 3，以及 mypy 冷快取）
```

一個確定的浪費、已經修掉：`setup-uv` 的 `cache-python` 預設是 `false`，
所以**每一趟都重新下載 33.2 MiB 的 CPython**（log 原文
`Downloading cpython-3.13.15-linux-x86_64-gnu (download) (33.2MiB)`）。
版本由 `.python-version` 釘死，根本不會變。由 `test_CI要快取python安裝檔` 背書。

### 分 job 平行：不值得，而且會賠

固定成本是**每個 job 各付一次 8 秒**，而總工作量只有 7 秒。二分之後每個 job
約 8＋3.5 = 11.5 秒，再加一個聚合 job 約 3 秒 → 牆鐘 14-15 秒，**等於沒賺**，
計費分鐘卻翻倍。**閘本身長到 30 秒以上之前，這條路都不划算。**

### 而且分 job 有一個會產生假綠的陷阱

`gates` 是 required check 的 context 名，它來自 **job 的 display name**。兩個做法會弄壞它：

| 做法 | 後果 | 方向 |
|---|---|---|
| 用 matrix | 名字變成 `gates (x)`，required context 永遠不回報 → merge 被卡死 | fail-**closed**，卡住但安全 |
| 聚合 job 沒寫 `if: always()` | 上游紅 → 聚合 job 變 `skipped`，而 **skipped 在 required check 上算通過** | fail-**open**，**假綠** |

同樣的 skipped 陷阱也適用於「只在相關檔案改動時才跑某些檢查」。
**假綠是這個 repo 判準二最危險的方向**——宣稱有把關卻沒有，比沒有把關更糟。

## 什麼時候這份文件會過期

| 條件 | 該重量什麼 |
|---|---|
| 序列時間超過 ~15 秒 | `最多worker` 的上限 |
