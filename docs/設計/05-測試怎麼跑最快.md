# 05 測試怎麼跑最快

> 量測環境：macOS 26.6、Apple Silicon 16 核、Python 3.13、pytest 8 ＋ pytest-xdist。
> 2026-08-29 量的，314 支測試。**換機器、換套件大小，下面每個數字都會變**——
> 所以每一節都寫了「什麼時候要重量」。

## 為什麼有這份文件

閘的門檻是**秒數，不是工具名**。commit 前的預算抓 10 秒，塞不進去的往後放。
理由很現實：閘慢到讓人想用 `--no-verify`，繞過一次，閘就等於不存在。

但「怎麼把測試跑快」這件事的知識，原本散在四個地方的程式碼註解裡。
**使用者不看 code。** 散在註解裡的知識等於沒有記錄——所以集中在這裡一份。

## 現在的數字

```
單元層  178 支   0.07 秒   ← 純函式，零子程序
整合層   85 支   5.50 秒   ← 會 fork（假 CLI、巢狀 pytest）
驗收層   52 支   1.38 秒   ← 使用者那句話成不成立
────────────────────────
全部序列 314 支  5.68 秒
全部 -n 4        2.27 秒

nova 閘 提交（7 條）  1.28 秒
nova 閘 ci（8 條）    4.77 秒
```

## 做法一：假 CLI 怎麼做，差 100 毫秒一支

三家 LLM CLI 不能在 CI 上真的跑（燒 token、要認證），所以用**假 CLI**：
一支印出預錄 envelope 的小腳本。做法有四種，速度差很多。

| 做法 | 一支測試的成本 | 抓得到什麼 | 抓不到什麼 |
|---|---|---|---|
| A. 每支測試重寫一份執行檔 | ~112 毫秒 | argv 形狀、旗標順序 | 真 CLI 收不收這組旗標 |
| B. **session 共用一份，行為靠環境變數切** | ~14 毫秒 | 同上 | 同上 |
| C. monkeypatch 掉 `subprocess.run` | ~0 毫秒 | 解析邏輯 | **argv 形狀**（沒有真的組指令） |
| D. 真的呼叫 CLI | 30–600 秒＋token | **旗標真的有效嗎** | — |

A 跟 B 差的那 **98 毫秒**是這樣量的（n=15 取中位數）：

```
新寫出來的執行檔，第一次執行   112 毫秒
同一支重複執行                14 毫秒
                             ──────
每支測試白付                  98 毫秒
```

那 98 毫秒是 macOS 對「剛出現的新執行檔」的第一次檢查（簽章／隔離屬性）。
**同一份內容換個路徑就要再付一次**，所以「每支測試 `tmp_path` 一份」是最貴的做法。

B 的關鍵是：**行為靠環境變數切，不靠重寫檔案內容**。

```python
@pytest.fixture(scope="session")
def 假CLI群(tmp_path_factory):        # 整個 session 一份
    ...
@pytest.fixture
def 做假CLI(假CLI群, tmp_path, monkeypatch):   # 每支測試只換環境變數
    monkeypatch.setenv(f"NOVA_FAKE_{家}_TRANSCRIPT", ...)
```

**B 的缺點**（要寫出來，不然下一個人會踩）：

1. session 共用＝**平行時每個 xdist worker 各建一份**，不是全機一份。
2. 環境變數是**跨程序的全域狀態**，一定要用 `monkeypatch.setenv` 讓它自動還原。
3. 假 CLI 的檔名變成識別身分的東西（`fake-codex` 知道自己是 codex），
   換名字會靜默壞掉——所以檔名的意義要寫在 fixture 的 docstring 裡。

**C 為什麼不用**：它連指令都沒組，`--add-dir` 打錯字它照樣綠。
這個 repo 被咬過——**墊片證明的是轉遞形狀，不是可達性**。

**D 為什麼非有不可**：只有它抓得到「真 CLI 收不收這組旗標」。
所以留一組 `真cli` 標記的測試，兩個閘都排除，手動 `-m 真cli` 跑。

實測收益：`test_委派給其他llm.py` 從 A 換成 B，**3.02 秒 → 1.41 秒**（19 支）。

## 做法二：worker 開幾個——不是越多越快

同一套測試，3 次取中位數：

```
序列    5.81 秒  ████████████████████
-n 2    3.52 秒  ████████████
-n 4    2.34 秒  ████████            ← 最快
-n 8    2.79 秒  █████████
-n 12   3.43 秒  ███████████         ← 0.75 × 16 核，原本的設定
-n 16   3.69 秒  ████████████        ← -n auto，吃滿
```

**worker 越多越慢**，因為每個 worker 都是一個新的直譯器，要自己 import 整套測試。
那筆固定成本不會因為核心多就變便宜；而這套測試不是 CPU-bound（全程只用到 213% CPU），
瓶頸是子程序啟動與 I/O 等待。

所以旋鈕不是「吃幾成核心」，是**上限**：

```python
平行成數 = 0.75      # 不吃滿：留 1/4 給作業系統與 pytest 主控
最多worker = 4       # 不超過這套測試攤得掉的量
平行度 = max(1, min(最多worker, int(核心 * 平行成數)))
```

**上限只會往下壓，不會把小機器補上去**——CI 是 4 核，算出來還是 3，一點都沒變。

**缺點與失效條件**：套件長大之後這個上限會變成瓶頸。
**重量的時機是「序列時間超過 ~15 秒」**——那時每個 worker 分到的工作量才攤得掉
自己的啟動成本。在那之前調高只是多付啟動費。

（這一節推翻了自己上一版的結論。上一版寫「調低是拿這台機器的最佳值換掉在別台機器
也合理」，那個推論有洞：慢下來的原因不是「這台機器」，是 import 成本，
那在任何機器上都存在。）

## 做法三：分層是時間預算，不是分類學

```
tests/單元/   純函式、零 I/O、零子程序   →  0.07 秒 / 178 支
tests/整合/   跨模組、真的 fork          →  5.50 秒 / 85 支
tests/驗收/   使用者說的那句話成不成立    →  1.38 秒 / 52 支
```

一支會 fork 的測試混進單元層，單元層就從毫秒級掉到秒級，而**內圈的價值全在毫秒級**。
所以這條有機械背書，不是口頭約定：

```python
# tests/驗收/test_專案骨架.py::test_單元層不准fork子程序
_會fork的痕跡 = ("import subprocess", "S_IEXEC", "跑cli(")
```

實測收益：把 fork 的測試搬出單元層之後，**提交閘 7.10 秒 → 1.18 秒、
單元層 5.91 秒 → 0.10 秒**。

## 做法四：`serial` 標記——會搶資源的單獨跑

有些測試自己會啟動 pytest 或 ruff（例如「提交閘在本 repo 上是綠的」）。
這種東西跟別的測試平行跑會**互相搶 CPU**，然後隨機紅。

```
pytest -m "not serial" -n 4 --dist worksteal   # 平行這一批
pytest -m "serial"                              # 再序列跑這一批
```

**資源互搶造成的紅燈是雜訊不是訊號。** 雜訊會訓練人忽略紅燈，那比慢更貴。

## 四個閘點各跑多少

| 階段 | 跑什麼 | 實測 | 由誰執行 |
|---|---|---|---|
| 內圈（寫 code 時） | `pytest -k <關鍵字> -x` | < 0.2 秒 | 你自己，隨時 |
| commit 前 | `nova 閘 提交`（7 條，含單元層） | 1.28 秒 | pre-commit hook |
| PR／push main | `nova 閘 ci --全部跑完`（8 條） | 4.77 秒（CI 上約 15 秒） | GitHub Actions |
| 手動 | `pytest -m 真cli` | 分鐘級、燒 token | 人 |

原則：**慢的往後放，快的往前放**，而門檻是秒數不是工具名。
mypy 在這個專案 < 1 秒，所以它留在 commit 前；整合測試 5.5 秒，所以往後放。

## 什麼時候這份文件會過期

| 條件 | 該重量什麼 |
|---|---|
| 序列時間超過 ~15 秒 | `最多worker` 的上限 |
| 換到 Linux／換 CPU | 那 98 毫秒（那是 macOS 特有的執行檔檢查） |
| 整合層超過 10 秒 | 分層的切法：是不是有東西該降到單元層 |
| CI 閘超過 10 分鐘 | 整條策略 |

數字都是量出來的，不是抄的。**要推翻上面任何一條，先貼出你的量測。**
