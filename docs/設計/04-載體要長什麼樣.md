## 為什麼現在寫這份

`CLAUDE.md` 開頭那條公式 `nova = harness engineering[loop engineering[llm]]` 一直是
借來的說法——borrowed 得夠久了，該去看原文到底說了什麼，然後決定 nova 的載體
下一格要補哪裡。

這份文件做三件事：

1. 把六份原始材料攤開，標清楚哪些有數據、哪些只是主張、哪些是二手轉述
2. 拿五套不同的分類法對照 nova 現況，找出**整格空的那幾格**
3. 從空格裡挑**一格**動手，其餘只留在盤點表上

第 3 點是刻意的。§8 反模式一是「還不理解工作就先畫圖」，同一條邏輯用在這裡就是
**還沒有呼叫端就先造載體**。七大組成一次做完等於造一個雜物抽屜，而規格 §2.3
明講「不要把 harness 當雜物抽屜」。

OpenAI 那篇**從頭到尾沒有定義 harness**。它是一份經驗報告，最接近定義的是結語：
他們最困難的挑戰集中在「設計環境（environments）、回饋迴圈（feedback loops）
與控制系統（control systems）」。

### 造詞的人怎麼定義

Mitchell Hashimoto 是唯一自稱造這個詞的人，而且姿態很低：

> "I don't know if there is a broad industry-accepted term for this yet, but I've grown to
> calling this **"harness engineering."**"

定義只有一句：

> "anytime you find an agent makes a mistake, **you take the time to engineer a solution
> such that the agent never makes that mistake again**."

他列的做法只有兩類：**更好的隱式提示（AGENTS.md）**，與**真的寫出來的工具**
（截圖腳本、篩選過的測試指令之類）。

這一句對 nova 的意義比七大組成表大得多——**它就是 nova 一直在做的事**。
`CLAUDE.md` 那張「已做過的固定負控」表格，每一列都是一次
「發現它會犯這個錯 → 工程化一個會紅的測試 → 它再也犯不了」。
差別在 Mitchell 停在 AGENTS.md（提示層，可以被忽略），nova 走到測試與閘（殼層，違反不了）。
那正是 `docs/設計/01-機械化閘.md` 說的**保證與加速器的分界**。

## 五套分類法擺在一起

同一件事有五種切法。**它們不是競爭關係，是不同的切面**——攤開比較才看得出 nova 缺哪裡。

### 甲：規格 §2.1 的六大組成（nova 的正典）

Context 注入 / 行動面 / 持久化 / 執行控制 / 安全與治理 / 可觀測性。

### 乙：sharktech 的**六**大組成（二手整理，但整理得不錯）

工具管理 / 狀態持久化 / 環境約束 / 反饋迴路 / 多 Agent 協作 / 可觀測性。

跟甲高度重疊，但**兩邊的比對原本都寫錯了**（2026-08-29 對原文逐字重查）：

- **「多出來的是多 Agent 協作」錯。** 文章第五項逐字是「多 Agent 協作：任務分解、
  Agent 間的交接機制」，而那兩個關鍵詞規格都有位置——「子 agent 生成」在
  `docs/AGENT_ARCHITECTURE.md` 的執行控制格、「交接(handoff)」在 §2 定義句。
  它不是規格外的第七格，是**規格已經涵蓋的東西被切在別的格子裡**。
- **「少掉的是執行控制」只講了一半。** 文章六項裡也沒有任何一項對應 Context 注入，
  而規格連 context 壓縮都算進 harness。兩邊的分層方向相反：文章把 context
  放在 harness 之外的另一層。

順帶：文章把「人工審查介入點」放在**可觀測性**，規格把「人工簽核」放在
**安全與治理**。同一件事在兩份材料裡不同格，引用時要指名是誰的分類。

> **這裡原本寫「七大」，多算了一項「架構知識」。已更正。**
>
> 更正的過程本身值得記，因為它把這份文件自己的證據分級規則走了一遍：
>
> 1. 第一版逐字讀過原文，記成七大。
> 2. 2026-08-29 用 WebFetch 再抓一次，摘要只回六項——**當下沒有改**，

### 丙：LangChain 的六部件（從「想要什麼行為」倒推）

| 部件 | 想要的行為 |
|---|---|
| Filesystem ＋ Git | 持久儲存、把裝不下 context 的東西卸載、跨 session 保住工作 |
| Bash ／ Code Execution | 不必人預先設計每一個工具，模型當場造自己的工具 |
| Sandbox（＋預設工具） | 安全地動手、觀察結果、自我驗證 |
| Memory ＆ Search | 記得看過的東西、拿得到訓練時不存在的資訊 |
| Context Management | 工作變長時效能不要衰減（compaction、工具輸出卸載、Skills 漸進揭露） |
| Planning ＆ Self-Verification | 長時程、自主、做對 |

它的定義最乾脆：**"If you're not the model, you're the harness."**

### 丁：Fowler 的 2×2（這一套對 nova 最有用）

兩個**彼此獨立**的軸交叉——注意不是上下層關係，這點很容易看錯：

```
                 computational（確定性，毫秒到秒）   inferential（語意判斷，慢且不確定）
  Guides         code mods、LSP、bootstrap 腳本      AGENTS.md、Skills、規格
  （事前引導）    ── 提高「第一次就做對」的機率
  ─────────────────────────────────────────────────────────────────────────────
  Sensors        測試、linter、型別檢查、            LLM as judge、AI code review
  （事後回饋）    structural test、mutation testing
                 ── 讓它自己發現做錯了
```

她對 Sensors 的一句話直接可以拿來當設計準則：

> 訊號要**為 LLM 消費而最佳化**，例如自訂 linter 訊息裡直接寫上該怎麼自我修正——
> **一種好的 prompt injection**。

以及一句反模式，只有一邊的控制迴圈：

> 分開來看，你會得到一個**不斷重犯同樣錯誤的 agent（只有 sensor）**，
> 或一個**寫了一堆規則卻永遠不知道規則有沒有用的 agent（只有 guide）**。

還有一句值得每次擴充載體時自問的——**原本這裡寫「沒人回答得了」，錯了，
原作者後來自己答了**（見下）：

> **如果 sensors 從來不觸發，那是品質高，還是偵測機制不夠？**

### 戊：Anthropic 的兩篇（最具體，直接給了檔案格式）

篇一把角色拆成 **initializer agent**（開場，建環境）與 **coding agent**（每一輪，做增量），
並明講兩者「除了第一句 user prompt 不同之外，system prompt、工具集、整個 harness 完全一樣」。
環境有四件產物：feature list（JSON，每項有 `passes` 欄位與 `steps` 清單）、
進度筆記檔、git commit 紀律、`init.sh`。

篇二把角色拆成 **planner / generator / evaluator**，並加了一個 **sprint contract**：
每個 sprint 開工**前**由 generator 與 evaluator 協商「done 長什麼樣」，寫成可測行為，
兩邊反覆改到同意為止。

篇二還有一句話，是整份材料裡最該貼在 nova 牆上的：

> **harness 裡的每一個元件都編碼了一個「模型自己做不到什麼」的假設，
> 而那些假設值得反覆壓力測試——因為它們可能本來就錯，也因為模型一進步它們就過期。**

### 兩個空格其實是同一個空格

持久化與可觀測性看起來是兩格，但缺的是同一件事：**nova 跑完之後什麼都不剩**。

- 「這一輪走了哪五步、每步花多少 token」——印過了，沒存。
- 「上一次為什麼停在 verify-red」——沒存。
- 「codex 這個月被叫了幾次、多少次結果未知」——沒存。

### 但要小心不要移動球門

`docs/設計/01-機械化閘.md` 對規格 §2.2 五問的回答是：State 是結構化結果加 git 歷史
加 CI log，Evidence 是結構化的閘輸出。**照那個標準，這兩格不是空的。**

所以這裡要說清楚多出來的是什麼門檻，而不是假裝 01 沒說過：

| | 01 的回答 | 這裡多要求什麼 |
|---|---|---|
| State | git 歷史、CI run log | 那兩份是**外部系統的副產物**，只涵蓋「有 commit 的那些改動」。工作流跑了五步、第三步退回重做過一次、每步花多少 token——git 一個字都沒有 |
| Evidence | 結構化的閘輸出 | 閘的輸出是**當下**的，跑完就沒了。問不出「上禮拜那次為什麼停在 verify-red」 |

一句話：**01 的答案涵蓋 repo 的狀態，涵蓋不了 nova 自己的執行過程。**
而執行過程正是規格 §11 要量的東西（重試次數、升級頻率、時間、token、成本）。

## 2026-08-29 的重查：四個查證屬實的缺口

這一輪用 `/workflow-authoring` 跑了 14 個 agent（166 萬 token、59 分鐘）重讀原文
與 code。交回 51 條，**這裡只收我自己逐條對 code 查證過的**，其餘留在 workflow 輸出裡。
（上一次委派審查三條裡有一條是假的，所以不照單全收。）

### 一、派去別的 repo 會注入錯的規矩

`src/nova/迴圈/角色提示.py` 的測試員與實作員提示**寫死**「專案規矩：繁體中文命名
與註解，不准簡體字。測試放在 tests/ 底下」——那是 **nova 這個 repo 自己的規矩**。

而 `隔離設定` 預設 True，nova 主動關掉目標 repo 的規範來源（claude 的
`--setting-sources ""`、codex 的 `--ignore-user-config`），卻**沒有任何接縫
把目標 repo 的規範讀進來再注入**。派去別的 repo 就是錯的 context，
而且**看不出來**——模型照規矩做了，只是照錯專案的規矩。

可實作的形狀（迴圈層）：`任務` 多一個「專案規範」欄位，由 CLI 從工作目錄讀，
讀不到就留白，**不要硬塞 nova 的規矩**。

### 二、審批閘與人工簽核整項空，卻被標成滿分

規格 §2.1 的執行控制列了**審批閘**、安全與治理列了**人工簽核**。
04 原本兩格都給滿分——不是宣稱它們存在，是**盤點時把子項漏掉了**。

`src/nova/契約/工作流.py` 的 `種類` 只有 `模型／判準／審查` 三值，
**沒有人類節點可以住的位置**；`_挑權限` 給了 `--全開` 就一路走到各家的
`dangerously-*` 旗標，中間沒有任何確認步驟。

規格 §9 問「操作者能暫停、檢視、續跑一次執行嗎」——檢視有（帳本），
**暫停與續跑都沒有**。

### 三、「sensors 從來不觸發」那句，原作者後來自己答了

04 原本把 Fowler 那句寫成「沒人回答得了」。她的後續文章直接答了，逐字：

> "So I started **logging a history of sensor states every time they were checked**,
> to get some data."

而且列出這份歷史回答得了什麼：觸發頻率的趨勢、**從來不紅的感測器＝不必要的訊號**、
常紅的規則＝該補指引的地方。

nova 幾乎是現成的——`src/nova/載體/帳本.py` 已經 append-only、
`src/nova/載體/階段記帳.py` 已經記判準紅綠、`src/nova/載體/帳本讀取.py` 已經有
`收斂`。**缺的只有一格：`src/nova/載體/閘.py` 完全不寫帳本**（本輪 grep：0 筆）。
所以 9 條規則一條都沒有觸發率資料。

補上之後就得到**第一個「因為帳本裡的東西而改變行為」的呼叫端**：
長期觸發率為零的規則是刪除候選，高觸發率的是補自我修正指引的候選。
那也是「Evidence 變成 State」的第一步。

見上面路線圖第 2 列。這是 04 說「沒有任何一行程式碼會因為帳本裡的東西改變行為」
的第一個**可量測後果**：真數字在帳本裡逐顆落盤了，停止規則卻用記憶體那份殘缺的。

## 導出：下一步做什麼

> **這一節被改過一次，而且是被另一顆腦改的。** 過程留在下面，因為它比結論值錢。

### 第一版的結論（錯的）

第一版寫的是「下一步只做一格——帳本」，理由四條，其中第三條是
**「帳本是預算、熔斷、防止重犯的前提」**。

把這份文件丟給 `codex --模型 gpt-5.6-sol`（唯讀、讀得到整個 repo）審查之後，
那條被拆掉了：

- token 已經在每次 `回應.用量` 裡，工作流在**記憶體**累計就能在下一次呼叫前擋下，
  不必先落盤。
- 單次執行的熔斷只要連續失敗計數。只有**跨執行**熔斷才需要耐久狀態，
  而且需要的是「讀」，帳本只寫。
- 文件自己一邊說「測試與閘已經讓同一個錯誤不能再犯」，一邊說「沒帳本就做不到」——前後矛盾。

它同時指出理由一（唯一整格空）與理由二（一格補兩個空）也有問題：
「空」不等於「該先做」，而 write-only 的 jsonl 是 Evidence，**不是可恢復的 State**
（沒有 reader、沒有 checkpoint、沒有 resume）。

### 它抓到的東西比那三條理由都重要

同一次審查裡，它指著 `src/nova/迴圈/狀態機.py` 的行號說：

> 目前 `回應.終局` 只代表 CLI 是否跑完，不代表任務正確。但狀態機對所有模型階段
> 一律視為達標，審查階段的綠邊直接是 `done`。**所以審查員回覆「設計有重大問題，
> 不通過」，只要 CLI exit 0，Nova 仍會說「全綠且通過審查」。帳本只會忠實保存
> 這個假結論。這比沒有歷史 trace 更急。**

查證屬實。**這已經修掉了**——見 `docs/設計/03-角色與工作流.md` 的
「審查的驗收權在判定上」一節，以及 `test_審查沒給判定一律中止`。

這件事本身是硬規則 4（不得讓同一個模型自寫自評）的實證：同一顆腦寫的文件與
程式碼，換一顆腦來看就看到了。也是 Fowler 說的 **inferential sensor** 的用途——
機械閘（computational sensor）看得出 ruff 與 mypy，看不出「這個狀態轉移在說謊」。

### 修正後的順序

| # | 做什麼 | 為什麼是這個順序 |
|---|---|---|
| 1 | **結構化的審查判定** | 假成功會汙染後面每一格的資料。先修這個，帳本才不會忠實保存假結論。**已完成** |
| 2 | 執行期的預算與熔斷 | 規格 §5 把 token budget 列成必要邊界。**這一列的立論一度是錯的**：`回應.用量` 在接力鏈上只帶最後一顆的數字，前面幾顆的 token 憑空消失，上限比宣稱的鬆。已修（`接力腦.詢問` 回傳前整條鏈加總）。**token 預算已完成；跨執行熔斷已接線但預設關閉**（明講 `nova 問 --熔斷` 才啟用；見下） |
| 3 | 帳本（有 start／end、可關聯、有 schema 版本） | 做完 1、2 之後，它記的才是可信的資料。**已完成**——成對事件靠 `呼叫編號` 關聯；schema 版本還沒有（只有一個版本，等真的要改欄位再加） |
| 4 | 最小的讀取端（reducer 或 checkpoint） | **沒有讀取端就不准宣稱補了 State**，只能說補了 Evidence。**reducer 已完成**（`src/nova/載體/帳本讀取.py` 的 `收斂`、CLI `nova 帳本`）；checkpoint 沒有 |

### 帳本已能影響行為，但預設關閉；checkpoint 仍然沒有

`收斂` 把一次執行折成摘要：各家幾次、成功／失敗／未知分開算、總 token、
走過哪些階段、**沒收尾的呼叫**（有開始沒有結束＝發出去了但沒寫下結果，
可能做了一半）、**讀不動的行數**（證據不完整不准長得跟「事情沒發生」一樣）。

帳本影響行為的路徑已經存在了，跨執行熔斷是第一條：但預設被旗標鎖住，明講
`nova 問 --熔斷` 才啟用。帳本仍繼續記、繼續讀，讀不到帳本時 fail-open 不熔斷；
**checkpoint 仍然沒有**。因此不能寫成 State 已補完：熔斷的行為路徑存在，但預設仍不影響行為。

第 4 列是審查逼出來的措辭修正。原本第一版打算「只寫不讀」還宣稱補了 State——
那是自己給自己發及格證。

### 第 2 項做完之後：預算有了，跨執行熔斷已接線但預設關閉

`停止條件` 現在有兩個旋鈕，因為那是**兩個不同的洞**：

```
最多步數   擋「來回幾次」        ← 原本就有
最多token  擋「花多少」          ← 補預算那次加的
                                  一步可以很貴，光有步數上限對成本沒有任何保證
卡住了()   擋「來回但沒在動」    ← 補 stuck 偵測那次加的
                                  前兩個是硬上限，這個是「發現沒進展就提早停」
```

**三個是不同的洞。** 光有步數上限的話，同一個判準吐出一模一樣的紅可以合法
燒到第 20 步——中間那些步全是白花的錢。`卡住了` 是純函式，只看**判準階段**
（證據是 pytest 的輸出，確定性的），而且只看**紅的**（連綠三次是重跑確認，不是卡住）。
門檻 3 是配 nova 的迴圈長度調的，不是抄 OpenHands 的 4——那套掃最後 20 個事件，
而 nova 整輪上限就是 20 步，回頭邊一來一回算 2 步，等到第 4 次已經燒掉 8 步。
由 `test_同一個判準紅三次就停不要燒完步數` 與 `test_有進展就不要停` 背書
（後者防的是**太早停**：少了它，`卡住了` 可以寫成「紅三次就停」而照樣綠）。

預算是**累計式**的：每一步回來把 `回應.用量.新鮮token` 加進去，**下一次呼叫之前**
比對上限。擋不到「這一次會花多少」——那要等它回來才知道——所以最後一步一定會
超出一點。**誠實的上限，不是精準的上限**，文件與 docstring 都要這樣寫，
不要讓人以為它精準。

預設是 3,000,000，理由寫在 `契約/工作流.py` 的常數旁邊（實測一輪重構＋審查就花掉
1,053,486 token，其中 input token 佔 87–98%）。**忘了傳不等於沒有上限**——
沒有預設的保證是懇求，不是保證。

跨執行熔斷已經存在：純函式在 `src/nova/載體/熔斷.py` 的 `該跳過嗎`，連續失敗 3 次
進入熔斷，冷卻 30 分鐘；「未知」既不推進計數也不歸零。接線在
`src/nova/載體/命令列.py` 的 `_這個專案誰熔斷了` 與 `_濾掉熔斷的`，已接進 `nova 問` 的接力鏈；
只讀最近 10 次執行，讀不到帳本時 fail-open 不熔斷。

但這條路徑預設被旗標鎖住：要明講 `nova 問 --熔斷` 才啟用。看帳跟關流程是兩件事——
帳本繼續記、繼續讀；預設不因帳本裡的歷史就不去叫某一家腦。checkpoint 仍然沒有。

**單次執行內的熔斷仍然刻意沒做**，理由沒有變：它已經以更嚴的形式存在——任何模型階段
`終局.確定失敗` 就直接中止，`終局.結果未知` 更是一律停（at-most-once）。
「連續失敗 N 次才熔斷」比現在**寬鬆**，寫了是退步不是進步。這次補的是**跨執行**那一半。

### 為什麼不是別格

| 別的候選 | 為什麼不是現在 |
|---|---|
| Context Management（compaction、卸載） | 一次呼叫就是一次子程序，**還沒有 context 塞爆的實例**。但要記一筆：`docs/設計/02-統一LLM介面.md` 量到十來字的提示造成 codex 17341、agy 14515 個輸入 token，自帶 system prompt 還沒關掉——那是**成本**與**換腦一致性**的真實痛點，只是不是「塞爆」。它屬於缺口 4 不是這裡 |
| 多 Agent 協作 / 子 agent 生成 | 工作流已經有兩條鏈。要更多之前先看 trace，而 trace 是第 3 項 |
| Graph 層 | `CLAUDE.md` 已經寫死：看過真實 trace 才畫。同上 |
| computational guide（LSP、code mods） | 有價值，但沒有呼叫端在痛。等某個錯誤重複三次再說（Fowler 的 steering loop 也是「重複出現才動手」） |

## 那 `IHarness` 到底要怎麼做

原始要求是「讀完那些文章，再加上我們一開始的文件，就知道 `IHarness` 要怎麼做」。
讀完六份原文之後的答案分兩層，**而且第二層是「現在不要做」**。

### 第一層：IHarness 的六個面，以及 nova 的落點

規格 §2.1 的六大組成就是那個介面該有的面。不是我發明的分類，是正典：

```
                    ┌─────────────────────────────────────────┐
                    │  IHarness（概念上的介面，不是一個類別）    │
                    ├─────────────────────────────────────────┤
   ① Context 注入   │ 迴圈/角色提示.py、載體/角色.py 的 組提示   │ ✅
   ② 行動面         │ 載體/模型/轉接.py（三家＋工具白名單）      │ ✅
                    │ 載體/模型/接力.py（fallback 鏈）          │
   ③ 持久化         │ 載體/帳本.py ＋ 載體/帳本讀取.py          │ ⚠️ 沒人依它決策
   ④ 執行控制       │ 呼叫選項.逾時秒、契約/工作流.py 的 停止條件 │ ✅
                    │ （步數上限＋token 上限）、接力鏈、回頭邊    │
   ⑤ 安全與治理     │ 權限三級、三家沙箱、載體/禁令.py、機密     │ ⚠️ 缺人工簽核
   ⑥ 可觀測性       │ 載體/模型/記帳.py、載體/階段記帳.py       │ ✅ 缺遮罩
                    └─────────────────────────────────────────┘
```

**判別法**（也是 `CLAUDE.md` 寫的那條）：把模型從圖上刪掉，還站著的全部都屬於載體。
六個面裡沒有一個需要「模型很聰明」才成立——這正是宿主反轉的意思。

### 第二層：為什麼現在不寫 `class IHarness(Protocol)`

因為**只有一個實作**。

`寫程式.md` 與 `軟體工程.md` 對這件事的分工很清楚：
沒有第二個實作時 YAGNI 說了算，出現第二個才輪到 SOLID 決定它長什麼樣。
現在硬抽一個 `IHarness`，十次有九次抽錯地方，而抽錯的抽象比重複更難拆。

而且**這六個面根本不該擠進同一個 Protocol**——那會違反介面隔離（I）：
呼叫端要的是「跑一次模型」或「跑一輪工作流」，不是一個逼你實作
`記一筆帳`、`檢查預算`、`注入 context` 的大介面。實作裡一半方法是 `pass` 就是徵兆。

nova 現在的做法是**把六個面拆成各自最小的接縫**，而且都已經是 Protocol 或參數：

| 面 | 接縫長什麼樣 | 在哪 |
|---|---|---|
| 行動面 | `語言模型` Protocol（`詢問(提示, 選項) -> 回應`） | `契約/角色.py` |
| Context | `角色` Protocol（`做(提示, 工作目錄) -> 回應`） | `契約/角色.py` |
| 執行控制 | `執行器` 是**參數**不是內建；`停止條件` 是資料 | `契約/工作流.py` |
| 治理 | `權限` 三值 ＋ 規則表（資料，不是分支） | `契約/角色.py`、`載體/規則表.py` |

**這就是 IHarness。** 它不是一個名字叫 `IHarness` 的類別，是這幾條接縫的總和。
`跑工作流(任務, 執行一步=..., 停止=...)` 這個簽章本身就是「高層決定需要什麼形狀，
低層去符合」——依賴反轉在 Python 裡最常見的正確形式就是**把相依當參數傳進來**。

### 這六個面對過五篇原文了：沒有漏

上面那六個面是從規格 §2.1 抄下來的，不是我發明的。但「規格的六個面**夠不夠**
涵蓋五篇原文講的所有 harness 能力」是另一個問題——沒驗過之前那只是假設。

驗了。派一顆腦讀 `fowler`／`lc`／`a1`／`a2`／`mitchellh` 五篇全文，
問「有沒有哪一項能力是這六個面沒涵蓋的」，要求**每一項都引出原句**。
回答是**沒有漏**，六個面各自的原文根據（引文逐條 grep 覆核過）：

| 面 | 原文根據 |
|---|---|
| ① Context 注入 | `mitchellh`「Better implicit prompting (AGENTS.md)」；`lc`「compaction intelligently offloads and summarizes the existing context window」；`a2`「criteria that encode design principles and preferences」 |
| ② 行動面 | `mitchellh`「read files, execute programs, and make HTTP requests」；`lc`「Bash + code exec is a big step towards giving models a computer」 |
| ③ 持久化 | `lc`「Filesystems for Durable Storage」「Git adds versioning to the filesystem」；`a1`「claude-progress.txt file alongside the git history」 |
| ④ 執行控制 | `a2`「three-agent architecture—planner, generator, and evaluator」；`lc`「The Ralph Loop is a harness pattern that intercepts the model's exit attempt」；`a2`「negotiated a sprint contract」 |
| ⑤ 安全與治理 | `lc`「harnesses can allow-list commands and enforce network isolation」；`fowler`「check for violations of module boundaries」 |
| ⑥ 可觀測性 | `mitchellh`「fast, high quality tools to automatically tell it when it is wrong」；`fowler`「Sensors (feedback controls)」；`a2`「tuned a standalone evaluator to be skeptical」 |

**引文一律 grep 覆核過才寫進來。** 九條裡九條都在對應的檔案裡找得到
（最後一條在純文字轉檔時被斷行拆開，所以要分兩段搜）。
這條規矩不是形式：模型引原文引錯的成本，正是這份文件開頭那一整節在講的東西。

一個誠實的紀錄：**這題原本派給 codex `gpt-5.6-sol`，25 分鐘逾時、0 token 回來。**
nova 判 `結果未知`（不准自動重跑）——那是對的行為。改派 agy、把題目窄化成一題，
94,742 → 12,374 token、幾分鐘就回來了。**「換更強的模型」不是第一修復**（§12）；
這次真正有效的是**把題目變小**。

### 什麼時候會出現真的 `IHarness`

**出現第二個載體的那天。** 具體的觸發條件寫在這裡，免得下次又靠感覺決定：

1. 有人要把 nova 的迴圈接到**不是子程序 CLI** 的東西上（HTTP API、本地權重）——
   那時 `語言模型` 這條接縫會被第二個實作撐開，形狀由它決定。
2. 或者出現第二種**帳本 sink**（記憶體、遠端），那時 §4 那條 `Callable` 別名
   才依三次法則抽成 Protocol。

在那之前，「IHarness 要怎麼做」的答案是：**六個面各自最小的接縫，
其中第 ③ 面現在是空的**——那正是下一步要補的東西。

## 帳本的形狀（提案 → 已落地）

**這一節原本全部是提案。現在已經實作，落點如下：**

| 提案講的 | 落在哪 |
|---|---|
| 事件 schema、中文欄位 → ASCII 鍵的對應表 | `src/nova/契約/帳本.py` |
| 落盤、失敗模型、寫失敗的終局 | `src/nova/載體/帳本.py` |
| 記帳腦（包在接力鏈**裡面**） | `src/nova/載體/模型/記帳.py` |
| 記帳執行器（每個階段一對事件） | `src/nova/載體/階段記帳.py` |

**兩件提案時沒答、實作時才定的事**：

1. **帳本自己寫失敗的終局。** 分界線是副作用發生了沒——開檔失敗（還沒叫過模型）
   當場炸；寫入失敗（模型已經跑完）不准往上丟，印一行 stderr 就繼續，而且只吵一次。
   往上丟會讓呼叫端以為呼叫失敗而重跑，那正是 at-most-once 要擋的事。
2. **誰發配對用的編號。** 接力鏈上每顆腦各包一層記帳，各自數自己會撞號，
   所以發號的權責歸帳本——它是那一格唯一從頭活到尾的東西。

下面保留原提案的推理過程，因為那些「為什麼不那樣做」的理由還有效。

### 一個 Protocol，一個方法，而且只有寫

一條時間線，能被追加、能被事後讀。介面上只有「記一筆」——讀由測試自己開檔做，
因為還沒有「讀」的呼叫端（nova 帳本 這個子命令還不存在）。

事件分兩種，各自指得出呼叫端：

| 事件種類 | 誰記 | 記什麼 |
|---|---|---|
| 模型呼叫 | 一個包在每顆腦外面的記帳腦 | 哪一家、終局、失敗代碼、用量 |
| 階段結束 | 一個包在執行器外面的記帳執行器 | 哪個階段、終局、判準紅綠、證據摘要 |

**記帳腦要包在接力鏈的裡面，一顆腦一層。** 包在外面只看得到最後一顆的答案，
「換了幾次腦、哪一家最常掛」就量不到——而那正是接力鏈存在的理由。
（`src/nova/載體/模型/接力.py` 一遇到成功就直接回傳，所以包在外面連前面掛掉的那幾顆
都看不到。）

**只有「結束」事件是不夠的**，這是審查抓到的另一條：nova 如果在模型回來之前被殺，
帳本上連「哪一家正在跑」都沒有——而那正是帳本最該回答的情境。
所以要成對的開始／結束事件，加上把兩者串起來的識別碼（哪一次呼叫、
接力鏈的第幾顆、哪個階段）。只靠一個全域序號去猜相鄰行，一遇到平行或巢狀就對不起來。

### 落盤那一行

一次執行一個檔，檔名就是執行識別碼，append-only jsonl。
每一行是「事件」加上帳本自己補的三格：執行識別碼、序號、時刻。

序號不是裝飾：同一毫秒可能兩筆，序號讓「發生順序」在檔案裡是**資料**，
而不是靠讀檔順序推出來的。

欄位名走 ASCII（`CLAUDE.md` 的跨程序例外條款）——它要能被別的程式讀、被 grep。
中文識別字對應到 ASCII 欄位名的那張表要是**單一來源**，而且用一支窮舉測試背書：
少對應一個欄位就紅。

### Callable 別名，不是 Protocol（這一條也被審查改掉了）

第一版寫的是 Protocol，理由是「檔案帳本有狀態（路徑、序號、時鐘），
Callable 別名會把狀態藏進 closure，而 `docs/設計/03-角色與工作流.md` 反對那樣」。

**那是誤讀。** 03 反對的是**把控制流程藏起來**（Rx 的 `retryWhen` 那類），
不是反對所有 closure——它自己就用工廠函式回傳 closure，`建判準` 與 `建TDD執行器`
都是這樣寫的，而且都測得動。

而且那個理由自相矛盾：一個只有「記一筆」的 Protocol **也沒有**暴露路徑、序號或時鐘。
兩種寫法在「看不看得到狀態」這件事上是一樣的。

所以照 repo 既有慣例：**先用 Callable 別名**。等真的出現第二種 sink
（記憶體帳本、遠端帳本）或呼叫端需要檢視那些屬性，再依三次法則抽 Protocol。

### 三件刻意不做的事

| 不做 | 理由 |
|---|---|
| 不記模型講的全文 | repo 是 public。全文落盤要先有遮罩，遮罩現在沒有 |
| 不做讀取 API | 沒有呼叫端。**但那就不准宣稱補了 State**——只能說補了 Evidence |

**「先記第一行、上限 200 字」這個做法被審查否掉了。** 第一行完全可能就是
token、路徑或私密內容——截斷不是遮罩。改成只記**白名單的結構化欄位**
（失敗代碼、終局、用量）加上內容的長度與雜湊；要保留全文就等遮罩做好，
存成獨立的 artifact 再從帳本指過去。

同一條理由也適用「證據摘要」：一段自由文字會把 §4.3 反對的東西重新請回來
（下游得重建上游語意）。帳本上該有的是 reason code 與 artifact reference，不是散文。

**「每筆開檔寫關檔＝耐久」也被否掉了。** `close()` 只清掉語言層的緩衝，
OS crash 之後照樣可能什麼都沒有；而長開 handle 每筆 `flush()` 同樣防得住
「程序被殺掉」。要決定寫法之前得先寫下**失敗模型**：防的是程序被殺、
還是機器斷電？要不要 `fsync`？半行怎麼辦？併發 append 怎麼辦？磁碟滿了怎麼辦？

還有一條第一版整個漏掉的：**帳本自己寫失敗時的終局是什麼。**
模型可能已經產生副作用了，記帳才失敗——fail-open 會丟掉證據，直接丟例外又可能
誘發人工重跑。依 at-most-once 的原則這必須有明確答案，而第一版沒有。

帳本路徑是參數，**預設不落在任何 repo 裡**。派工會讓可編輯的模型在目標 repo 裡工作，
帳本若寫進工作目錄會被受測模型自己 commit 進去。同源理由見
`docs/設計/02-統一LLM介面.md` 的「執行檔路徑是參數，不信 PATH」。

### 它不改任何既有簽章

這是這個提案最強的 YAGNI 證據。記帳腦自己就滿足 `語言模型` 這個 Protocol，
記帳執行器自己就滿足執行器的形狀——所以：

```
接力腦(腦們=(記帳腦(codex腦, 帳), 記帳腦(agy腦, 帳)))
記帳執行器(既有的執行器, 帳)
```

`語言模型`、`固定提示角色`、`跑工作流`、`跑閘` 一個字都不用改。
新增一整格能力，既有簽章零變動。

## 這份文件自己的壓力測試

篇二那句話對這份文件同樣適用：**每個元件都編碼了一個「模型自己做不到什麼」的假設。**
帳本編碼的假設是：**模型記不住上一次發生什麼**。

那個假設會不會過期？會——各家 CLI 都已經有持久對話（`docs/設計/02-統一LLM介面.md`
的「持久對話」一節，實測過 codex 與 agy 的 sid ＋ resume）。

但持久對話存的是**那一家 CLI 自己的對話**，不是 nova 的執行紀錄：
換一家就沒了、跨兩條接力鏈就對不起來、而且問不出「這個月結果未知幾次」。
**廠商的持久化是廠商的載體，依 `docs/設計/02-統一LLM介面.md` 的分界，
廠商載體能力一律歸在加速器欄，永遠不能是保證。**

所以這個假設現在成立。哪天不成立了，這一節就是回來刪掉它的入口。
