# 目標長什麼樣

09 講**接下來往哪走**（五階路線）。這一份講**要走到哪**——
路線是會變的，這份不太會。

## 一句話

> 給 nova 一個目標，它自己把目標拆成可執行的工作、自己派出去做、
> 自己驗收、做錯了自己退回重做，三天不用人管，做完的時候拿得出證據。

現在拿 nova 做 nova。**做得起來之後，換一個工作目錄就是幫別的專案做它的目標**
——所以底下每一條都不准依賴「這是 nova 自己」這個事實。

## 一、規劃不是一次做完的

一次規劃到目標，中間那些點沒有證據背書，**寫出來的計畫看起來完整，其實是空談**：
規劃第 5 步的時候第 1～4 步還沒跑，第 5 步憑什麼那樣寫？憑猜。

所以 pipeline 是 **append 出來的**，不是一次畫好的：

```
    ┌──────────────── 已經有證據的區間 ────────────────┐ ┌─ 還沒有 ─┐
    ●────────●────────●────────◐                      ?          ★
   點1       點2      點3      點4（正在跑）        待摸索      目標

    └── 已完成，不准改 ──┘         └─ 規劃到這裡為止 ─┘
                                          ▲
                            規劃只准伸到「證據還夠用」的地方
```

## 二、四個階段錯開跑，所以沒有一段在等

一輪是「找資料 → 理解 → 規劃 → 實作」。**三天不停的來源不是跑得快，
是四個階段錯開**——任何一刻四段都有事做：

```
        找資料   理解    規劃    實作
  t1  │   ①                              │
  t2  │   ②      ①                       │
  t3  │   ③      ②       ①               │
  t4  │   ④      ③       ②       ①       │  ← 從這裡開始，四段同時有事做
  t5  │   ⑤      ④       ③       ②       │
        └─ agy ─┘└─ 雲 ─┘└─ 雲 ─┘└─本地─┘     （分工見第七節）
```

`①②③` 是輪次。第 4 個時間格之後**產線滿載**：agy 在找第 5 輪的資料，
同時雲在理解第 4 輪、規劃第 3 輪，本地在實作第 2 輪。

## 三、修正也是一種規劃

第 3 輪找到的資料，可能證明第 1 輪做錯了。這時候**不回頭改**——

```
   ●───────●───────●───────●          ●
  點1     點2     點3     點4  ...   點7 ← 修正點1的那個點
   ▲                                   │
   └──────── 錯的留在帳本上 ────────────┘
```

**修正是往後 append 一個新的點，不是回去改舊的。** 兩個理由：

1. 改了舊的點，帳本上那次執行的證據就對不上它——而「證據對得上」
   是這整套唯一的驗收方式。
2. **修正不需要另一套機制。** 發現做錯了就是下一輪規劃的輸入，
   規劃器不必分「正常規劃」與「錯誤處理」兩種模式，它只有一種模式。

（跟 git 同一條：`revert` 是新 commit，不是 rewrite。）

## 四、四層：pipeline → 點 → task → step

```
pipeline   整條路。append-only
  └─ 點     一個屏障。點裡面的 task 並行，點與點之間循序
      └─ task   一件可以獨立派出去的工作（一輪工作流）
          └─ step   工作流裡的一階（TDD 七階的一階）
```

**點就是屏障**，所以「點」的邊界不是主題而是**同步需求**：
下一批工作要等這一批全做完才知道怎麼做，那裡就是一個點。

現況：`src/nova/迴圈/扇出.py` 已經是「點」的實作——屏障、必要分支、
以及 #171 加的假獨立檢查（兩個分支寫同一個地方就不准並行）都在。

## 五、什麼叫「完整的點」

> 點線面全都連起來，這樣才是一個完整的點，不然實作的人會不知道怎麼實作。

機械化成四欄，**缺一欄就不准派**：

| 欄 | 答的問題 | 缺了會怎樣 |
|---|---|---|
| **輸入** | 要讀哪些工件／檔 | 執行者自己去翻，翻到什麼算什麼 |
| **輸出** | 會寫到哪些路徑 | 兩個 task 靜默覆蓋彼此（#171 擋的就是這個） |
| **驗收** | 什麼指令回 0 才算做完 | 只能靠「模型說完成了」——硬規則第 2 條擋的東西 |

**驗收現在只走到「宣告」那一半。** 收件匣會擋下沒帶驗收的自主票，
但沒有人在收尾的時候**跑**那條指令——所以今天的保證是
「票必須宣告驗收」，不是「驗收說了算」。差別很大，別把它當成後者。

跑起來之後那條路是現成的：驗收紅 → 不進 `已處理/` → `接著排` 回收件匣，
而 `最多輪次 = 3` 已經是那個重試迴圈的停止規則。
**「做錯了讓他退了再做」就是這條路，不必發明新機制。**
| **停止** | 撞到什麼就停（步數、token、卡住） | 不是迴圈，是成本漏洞（規格 §3.2） |

四欄都在 `src/nova/契約/分派.py` 的 `分派項目` 裡（輸出那欄還在 `契約/扇出.py`），
驗證器在 `src/nova/迴圈/計畫.py` 的 `驗證分派單`。

## 六、廣度受限、深度不受限

兩條要求看起來相反，其實管的是不同軸：

```
              淺（欄位不齊）        深（四欄齊全）
        ┌──────────────────────┬──────────────────────┐
  近    │ ✗ 執行者不知道怎麼做  │ ✓ 這一格才准派       │
 （有   │                      │                      │
  證據）│                      │                      │
        ├──────────────────────┼──────────────────────┤
  遠    │ ✗ 兩種病一起犯        │ ✗ 空談：欄位很齊，   │
 （沒   │                      │   但那些值是猜的     │
  證據）│                      │                      │
        └──────────────────────┴──────────────────────┘
```

右下角最危險：**它看起來最像一份好計畫**。防它的方法是機械的——
一個 task 的輸入工件還不存在，它就不准進 pipeline，只能進「待摸索」。

## 七、錢：91% 在建構

分工對應第二節那條產線的四段：

Anthropic 實測一次長跑的成本分佈是 Planner 0.4%、建構 91%、QA 8.3%
（出處見 [`08-外面怎麼講載體工程.md`](08-外面怎麼講載體工程.md)）。
所以分層不是省小錢，是把那 91% 搬走：

```
  規劃 0.4%  ──▶ 雲、高階         量少，錯了最貴
  研究       ──▶ agy              讀滿 repo 是它的長處
  建構 91%   ──▶ 本地             ★ 錢全在這裡
  審查 8.3%  ──▶ 雲，且必須換腦   硬規則第 2 條本來就不准自評
```

留在雲上的兩塊剛好是**非留不可**的：難推理（規劃）與不准自評（審查）。

兩個邊界要講清楚：

1. **「派給本地」是逐階段看探針，不是整包搬。** 實測 27B 在測試員那一階撞過
   「工具呼叫超過 8 回合還沒收尾」。熔斷已經在了，但派工前要有探針背書。
2. **「做錯了退回重做」只對退出碼 1 與閘紅合法。** 退出碼 3（結果未知）不准重跑
   ——三天無人值守也一樣，那條路要落票、換腦或等人。
   退得回去靠成果帳的 `rollback_point`（起點 commit）。
