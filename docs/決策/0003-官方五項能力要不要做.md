# 0003 — 官方有而 nova 沒有的五項能力

- **狀態**：已採用
- **日期**：2026-08-30
- **格式**：MADR 精簡版；五項判斷彼此獨立，可各自採用或拒絕。

## 脈絡

本文件只決定五項差異要做、不做或延後，不含實作。判準以 `CLAUDE.md` 為準；結論已核對指定研究、現有原始碼、測試與實際呼叫端。

已確認的工作邊界：不新增 `src/nova/圖/`、節點註冊表或編排 DSL；不以文件提醒、skill、換模型或通用全掃變異測試充當保證；除本檔外不修改任何檔案。

已確認的採納判準：

- 保證只能落在閘、型別或會失敗的測試；prompt／文件只是提醒，不能算保證。
- 跨層資料要 schema 化，但「已經有型別」不等於每個實際 handoff 都經過它。
- 驗收權必須留在包住模型的程式碼，不能以模型自報完成或自寫自評為停止條件。
- 新保證必須能做一次固定負控；會 fork 子程序的測試只能放 `tests/整合/`，不能拖慢提交閘的純單元層。
- 跨程序只可靠顯式、可序列化的資料；退出碼 `3` 是結果未知且不得自動重跑，`4` 是護欄生效而非一般失敗。
- YAGNI：沒有真實 trace 或呼叫端，不先建立 graph 層或抽象編排。

指定研究目前確認的外部事實（只作比較證據，不直接當 nova 的設計）：

- 官方 7 支 workflow 有 15 個 schema object、18 個 logical dispatch site，18/18 傳 schema；但研究拿不到 `agent()` runtime，因此不能斷言 schema-invalid 究竟會重試、回 null 或 throw。
- 官方的算術在 controller：`built` 會被 clamp 成 `built && buildRan`，2/3 build rate、inventory 完整性與三票門檻也由程式計算。
- 官方 partial-failure 的可續跑形狀是把 `remainingUnits`、`failedUnits`、`blockedUnits` 與 error/gap 回傳給 calling session；process 內的 `Map`、array、promise queue 則不能直接搬到 nova 的獨立子程序模型。
- 官方三票只用在 security finding：REACHABILITY、IMPACT、DEFENSES 三票全回且至少二票為真；缺票的 candidate 被丟棄並記為未完成。這不是所有 workflow 的一般驗收規則。
- 官方至少三支 workflow 會把上游模型欄位 fence 起來並移除內嵌 marker，明確把跨角色文字視為 untrusted data。
- 官方 agent metadata 的路徑粒度是 0/34；即使 verifier 未配 Write/Edit，仍可能有 unrestricted Bash。其硬隔離形狀來自 scratch workspace／clone 與 staged diff，不是 agent 自守的「唯讀」提示。
- 可原樣跨程序的是 JSON／檔案／patch 這類顯式資料；不能原樣搬的是同一 JS runtime 的 typed `agent()` ABI、promise queue、共享 `Map`、token ledger 與統一 falsey failure。
- 7 支官方腳本本身沒有 durable checkpoint 或「半個 invocation 原地續跑」；`uplift-migrate` 只能在正常 return／circuit-break 後把三種 unit 清單交給 caller 重呼叫。持久 state／checkpoint 只存在參考文件的 pattern，不可寫成官方七支已具備。
- 官方甚至有「排兩票、只回一張贊成票仍通過」的 P0 panel；因此第 4 項若採用，必須把「預期票數」與「實收票數」做成 controller invariant，不能只照搬 `every()`。
- 官方腳本多數對單支 null 採局部隔離，但 nova 的 OS 子程序還有 exit code、signal、timeout、空輸出與 parse/schema failure；不能把它們無差別壓成同一個 null 狀態。

nova 現況核對：

- `契約/節點.py` 已有泛型 `邊包[輸入]`（結構、版本、內容、來源）、泛型節點 Protocol 與四種窮舉終局；`迴圈/節點.py` 的 runner 也會把不合法的輸出 envelope／provenance 降成 `輸出不合約` 護欄。故第 1 項的「每條邊都有共同 contract」不是缺口。
- 現有 runner 只檢查結構名非空、版本為正整數、來源吻合；它沒有拿「此節點預期的結構名／版本／內容 validator」比對輸入與輸出。`分派單` 雖宣告 `輸入結構` 且 host 會查是否在可用集合，仍不是每個實際 handoff 的 payload schema validation。這是第 1 項尚缺的小塊。
- `契約/模型回應.py` 已把三家 CLI 正規化成 `回應`，含三值終局、失敗碼、用量、對話識別碼與 optional `結構化輸出`；`nova 問 --json` 只是把這個 dataclass（排除巨大原始事件）序列化到 stdout。它保證 invocation envelope，不保證某角色的 domain payload。
- CLI adapter 目前沒有 provider-neutral schema 參數；Claude／agy parser 只在供應商 envelope 本來帶 `structured_output` 時抄入，Codex parser沒有設定該欄。故不能宣稱 `--json` 已等價於官方 `agent(...,{schema})`。
- 第 2 項不是整體缺失：現行 TDD runner 已在模型外判 pytest 紅綠、審查 marker 缺失即 fail-closed、累計／預估 token、步數與重複紅證據；扇出 runner 也自己持有呼叫、並行、時間、token、必要分支與最少成功數。nova 已採用的原則就是「模型產資料，host 判出口」。
- 現有 `步驟結果.判準綠` 是 host 跑命令後填，不採模型自報；相反地，模型階段只以 CLI 終局判「有沒有跑完」，並不宣告任務成功。若未來新增 build-rate／vote workflow，算式應在那個真實 controller 呼叫端補，而不是先造通用算術框架。
- 第 3 項在目前線性 TDD 已有符合其自身需求的形狀：每步 `步驟結果`、三值終局、完整軌跡、進度檔／接續票，以及 code 4 才自動排下一輪；結果未知（code 3）與確定失敗（code 1）不重排。它沒有 dependency-wave 所需的「未試／失敗／被依賴擋」三份 item 清單，但目前也沒有 dependency-wave production caller。
- `契約/扇出.py` 已有 per-branch 結果、成功產出、缺口、必要分支與最低成功數；然而 `執行扇出` 目前只有單元測試呼叫，沒有 production panel。它計的是「子程序成功數」，不是 domain verdict 的票數，因此不能冒充已具備第 4 項的 2-of-3 驗收。
- 第 5 項有立即可達的真實通道：`迴圈/工作流.py::_提示` 把 `任務.前情` 與上一個 `步驟結果.證據` 原樣插入下一角色提示；兩者都可含先前模型輸出。現有程式沒有 untrusted fence 或 marker 清除。

## 決策

總結如下；這是採用順序，不是原研究的排序：

| 原項次 | 判斷 | 現在要付出的實作成本 | 一句話結論 |
|---|---|---:|---|
| 5 | **做，並排到第一** | 約 40～60 行；CI 增量估計 `<0.05s` | 已有真實 prompt-injection 通道，且有下游可寫角色。 |
| 2 | **不做** | 0 行；`0s` | host-owned 算術與判準已經是 nova 的現況；不能為尚未出現的公式造框架。 |
| 1 | **延後** | 0 行；`0s` | 共同 envelope／型別已經有；只延後尚無呼叫端的 domain payload runtime validator。 |
| 3 | **延後** | 0 行；`0s` | 線性 TDD 已有自己的續跑形狀，沒有 dependency-wave caller。 |
| 4 | **延後** | 0 行；`0s` | 屏障與缺必要分支 fail-closed 的底座已有，但沒有值得花三次呼叫的 domain panel。 |

換句話說，這輪唯一應進實作佇列的是第 5 項。第 1、2 項不是「nova 完全沒有」；
第 3、4 項則不能把現有底座誤報成完整能力。

### 1. 每個 handoff 都有 schema contract

| 欄 | 決定 |
|---|---|
| **判斷** | **延後**。延後的是「模型 domain payload 的 runtime schema validation」，不是重做 nova 已有的共同 handoff contract。 |
| **為什麼／觸發條件** | `邊包[輸入]`、四種終局、`步驟結果`、`回應` 與 runner 的 provenance／envelope 驗證已涵蓋共同形狀。真正缺口是：runner 沒有拿預期的結構名、版本及內容 validator 比對輸出；三家 adapter 也沒有共同 schema 參數。現在沒有 production controller 讀 `回應.結構化輸出` 再據欄位分支，立刻補會是沒有呼叫端的程式碼。**觸發條件**：第一個 production caller 要讀模型產生的結構化欄位來分支，或 `執行節點` 第一次成為 production handoff 且需要特定內容 schema。屆時只補該 caller 的契約，不先鋪 18 個官方式 dispatch 或通用 DSL。 |
| **落在哪** | 現在不改。觸發後從既有 `src/nova/契約/節點.py`／`src/nova/迴圈/節點.py` 的邊界補「預期結構、版本、內容 validator」；若真實 caller 走模型 adapter，則契約放該 caller，解析後在 parent process 驗證。不得新增 `src/nova/圖/`、節點註冊表或編排 DSL。 |
| **保證形狀** | 現有是**型別＋閘＋會 fail 的測試**：`邊包`／終局型別，runner 的 `輸出不合約` 護欄，以及 `test_輸出來源不合上下文契約時回輸出不合約護欄`。觸發後新增的內容 validator 也必須 fail-closed 成 `輸出不合約`，不能把「請回 JSON」的 prompt 當保證。 |
| **第一支紅測試** | 觸發後先加 `tests/單元/test_節點單獨執行.py::test_輸出內容不合節點宣告的schema時回輸出不合約護欄`。現在不先建立這支無 caller 的測試。 |
| **跨程序搬得過來嗎** | 官方同一 runtime 的 `agent(..., {schema})` ABI **原樣搬不過來**。JSON-compatible schema、payload 與 validation error 搬得過來；必須由 nova 的 parent 在 CLI 輸出解析後驗證。Python 的 Protocol／泛型本身不會穿過程序邊界。 |
| **成本** | 本決策現在是 0 行、CI `0s`。觸發後，若只補既有節點邊界，粗估 production 30～60 行、單元測試 30～50 行，純 validator 的 CI 增量估計 `<0.05s`；三家 provider-neutral schema 支援要依真實 caller 另估，不能綁在這個無 caller 的缺口上偷渡。 |

### 2. 模型之外的算術閘

| 欄 | 決定 |
|---|---|
| **判斷** | **不做**。這項原則 nova 已經有，不建立一個名為「算術閘」的新抽象。 |
| **為什麼／觸發條件** | pytest 紅綠、review marker、token／步數／停滯、扇出呼叫數／必要分支／最少成功數，以及分派預算，都是模型外的程式在算。`步驟結果.判準綠` 由 host 跑命令後填；模型沒有自報「任務通過」的權力。**未來觸發條件**：某個真實 controller 新增 build-rate、vote-rate 或其他派生量。公式必須就地使用 host 可驗證的原始事實，並在該 caller 補測試；這不會推翻本項「不造通用框架」的決定。 |
| **落在哪** | 不新增、不修改。未來公式只落在擁有該原始事實的真實 controller，不落在模型 prompt、`CLAUDE.md` 或共用無語意的計數工具。 |
| **保證形狀** | 現有**閘＋會 fail 的測試**。代表性保證是 `tests/單元/test_工作流.py::Test判準不是角色::test_驗證階段不會呼叫任何角色`、`Testtoken預算::test_擋在下一次呼叫之前不是事後補救`，以及 `tests/單元/test_扇出.py::test_階段最多token累計到上限就不再派下一顆`。 |
| **第一支紅測試** | **不適用：沒有新實作。** 上述既有測試就是會 fail 的保證；若日後新增 build-rate，第一支紅測試必須在那個 caller 的既有測試檔證明「模型自報 built、但 host 沒有成功 build 證據時，不得計入分子」。在 caller 出現前不虛構檔名或模組。 |
| **跨程序搬得過來嗎** | 官方 process 內的共享計數器原樣搬不過來；**原始事件可搬、算式可重做**。nova 應讓每個子程序回結構化事實，由 parent process 自己累計。現在的 pytest exit、usage 與分支結果正是這個形狀。 |
| **成本** | 0 行、CI `0s`。未來每個 caller 的局部公式通常約 5～15 行、測試 10～25 行，純單元 CI 增量估計 `<0.05s`；沒有 caller 就沒有這筆成本。 |

### 3. 可續跑的 partial-failure state

| 欄 | 決定 |
|---|---|
| **判斷** | **延後**。不把官方單一 `uplift-migrate` 的 batch recovery 先泛化成 nova 全域狀態機。 |
| **為什麼／觸發條件** | 現在的 production TDD 是線性的：有逐步結果、三值終局、軌跡、進度檔與接續票；只有 code 4 護欄會自動接著排，code 3 結果未知不會冒險重跑。它不需要「未試／失敗／被依賴擋」三份清單。`扇出` 與 `分派單` 雖有資料形狀，尚無 production dependency-wave runner。**觸發條件**：出現一個 production caller，會一次處理至少兩個有依賴的 item，且第二次獨立程序必須保留已完成 item、不重做，只重送可重試 item；或實際 trace 證明程序中斷後重做成本不可接受。 |
| **落在哪** | 現在不改。觸發後狀態型別與持久化要貼著那個 batch caller 放；若它採既有扇出，才擴充 `src/nova/契約/扇出.py` 的 per-item 終態。不能因此先建 graph、checkpoint framework 或編排 DSL。 |
| **保證形狀** | 觸發後要有**型別＋讀入閘＋整合測試**：窮舉 `未試／確定失敗／被依賴擋住／已完成／結果未知`，manifest 帶版本與來源；缺欄、未知狀態、base 不合一律拒絕續跑。code 3 只保存，仍不得自動重試。 |
| **第一支紅測試** | 觸發後先加 `tests/整合/test_分批續跑.py::test_第二個程序只重送未試與可重試失敗且保留被依賴擋住`。它必須真的啟動第二個程序，所以不能塞進 `tests/單元/`。現在不建立空殼測試。 |
| **跨程序搬得過來嗎** | 官方的 `Map`、promise queue、閉包與半途 process memory **搬不過來**。版本化 JSON manifest／檔案搬得過來；若第一個程序在 atomic write 前死亡，仍沒有可恢復資料，不能宣稱 durable checkpoint。 |
| **成本** | 現在 0 行、CI `0s`。觸發後粗估 production 80～150 行、測試 60～100 行；一支真的跨兩程序的整合測試估計增加 1～3 秒。這筆成本要由 batch caller 的重做損失來支付。 |

### 4. 多票驗收＋缺票 fail-closed

| 欄 | 決定 |
|---|---|
| **判斷** | **延後**。不把每次 TDD review 都升成三票。 |
| **為什麼／觸發條件** | 官方三票是 security finding 的局部政策，不是七支 workflow 的共同規則。nova 已有屏障、必要分支與缺口，因此「三個必要分支必須收齊」的調度底座可重用；但它只算子程序成功，不懂 `TRUE_POSITIVE` 等 domain verdict，不能當成已完成多票驗收。現在沒有 production panel caller，也沒有證據顯示一般 TDD 的錯判成本高於多兩次模型呼叫。**觸發條件**：出現一個高風險 claim 的 production 驗收 caller，明定三個獨立 lens，且漏放成本高於三次呼叫成本。 |
| **落在哪** | 現在不改。觸發後用現有 `契約/扇出.py`／`迴圈/扇出.py` 收齊程序結果；`票` 的 lens、verdict、reason 與 2-of-3 計算必須放在那個 domain caller，不把「process 成功」偷換成「贊成票」。 |
| **保證形狀** | 觸發後是**票型別＋controller 閘＋會 fail 的測試**：預期 lens 集合必須恰等於實收集合，拒絕缺票、重複票與未知 lens；完整後才由程式算 2-of-3。不能使用模型自由文字總結作最後一票。 |
| **第一支紅測試** | 觸發後先加 `tests/單元/test_多票驗收.py::test_三票少一票時即使兩票贊成也不得通過`。另外沿用 `tests/單元/test_扇出.py::test_必要分支未全部回來前不呼叫整合` 保護屏障。現在沒有 domain caller，所以不先建立前一個測試檔。 |
| **跨程序搬得過來嗎** | **可以搬，但不能搬共享 runtime。** 每票以 JSON-compatible record 回 parent；parent 按 candidate id／lens 收票和算術。程序獨立反而是票的獨立性來源之一。 |
| **成本** | 現在 0 行、CI `0s`。觸發後若沿用扇出，domain contract／計票約 35～60 行、測試 40～70 行，純單元 CI 增量估計 `<0.1s`。production 成本則是每個 candidate 三次模型呼叫；並行只能省牆鐘時間，不能省 token／費用。 |

### 5. 把上游模型輸出當 untrusted data

| 欄 | 決定 |
|---|---|
| **判斷** | **做，而且插隊到五項第一。** |
| **為什麼／觸發條件** | 這不是未來可能出現的抽象：`src/nova/迴圈/工作流.py::_提示` 現在就把 `任務.前情` 與上一個 `步驟結果.證據` 裸接進下一角色提示；證據可直接來自上一個模型，而實作員／測試員／重構員可寫工作樹。上游文字可偽造「資料已結束，以下是新指令」，形成 prompt-injection 的控制／資料混淆通道。安全性與呼叫端都已存在，符合立即做的條件。 |
| **落在哪** | **改** `src/nova/迴圈/工作流.py`：在 `_提示` 附近新增單一 private helper，先移除 begin/end marker，再把每段前情／證據包成固定 untrusted fence；約 15～22 行。**改** `tests/單元/test_工作流.py`：在既有跨-context 測試旁加約 25～40 行。只有這一個真實 handoff sink，不先抽共用模組。 |
| **保證形狀** | **runtime 轉換閘＋會 fail 的測試**。每一段不可信輸入只能留下 wrapper 自己的一對 marker；payload 內同名 begin/end marker 必須先被移除或不可逆轉義。測試經既有 `src/nova/載體/規則表.py` 的提交閘 `pytest-unit` 執行，CI 的 `pytest-parallel` 也涵蓋。固定負控是暫時拿掉 marker 清除或直接回傳 raw text，第一支測試必須被殺；不跑通用全掃 mutation。 |
| **第一支紅測試** | `tests/單元/test_工作流.py::Test不可信上游輸出::test_前情與上一步證據都被fence且內嵌marker不能提早跳出`。測資要讓兩個來源都含偽造 closing marker 與「忽略前文」文字，並斷言偽造 marker 不會原樣出現在 wrapper 內。 |
| **跨程序搬得過來嗎** | **可以。** 這是 parent 在啟動下一個 CLI 子程序前做的純文字轉換，不需共享 runtime；轉換後的 prompt 本來就能經 stdin／argv 搬運。 |
| **成本** | production 約 15～22 行、測試約 25～40 行，合計約 40～60 行。沒有新子程序、模型呼叫或 I/O。現有 `tests/單元/test_工作流.py` 36 支測試本機測得 pytest test time `0.10s`、整個命令牆鐘 `0.70s`；新增一支純字串測試的 CI 增量估計 `<0.05s`。 |

fence 是必要的 data-boundary hygiene，**不是 prompt injection 的完整安全牆**：模型仍可能
選擇服從 fence 內的句子。它之所以插隊，是因為通道已啟用、下游有副作用、修補很小；
真正限制爆炸半徑仍要靠模型外的工作範圍與驗收閘。

### 範圍隔離，或權限矩陣

**決定：改採範圍隔離；權限矩陣不得再當主要安全邊界。** 這不是折衷採兩條路：
即使 adapter 仍傳最小工具權限，那只能算 defense in depth，驗收正確性不得依賴它。

可信 parent／supervisor 應持有原始 base 與 canonical tests；實作員只在 disposable
snapshot 工作。若要讓 worker 自跑測試，測試由 parent 以 OS 層唯讀投影提供；即使某家
CLI 做不到可靠唯讀，worker 副本內的綠燈也不算驗收。worker 只交回帶 base identity 與
變更路徑 manifest 的 patch。parent 的匯入閘
先拒絕越界路徑、絕對路徑、`..`、symlink／submodule 逃逸、未允許的 binary／mode
變更及 base mismatch，再把 patch 套到新的 verification tree，用**未經 worker 修改的
canonical tests** 驗收。通過後才把同一 patch 提升到權威工作樹。即使 worker 在自己的
副本竄改測試並跑出綠燈，那個綠燈也完全不被採信。

選範圍隔離的理由是三家 CLI 的工具能力不對稱：nova 自己的 adapter 已承認 agy 的
read-only 沒有可靠 filesystem boundary，官方材料也顯示「沒有 Write/Edit」仍常帶一般
Bash。權限矩陣的失效模式是漏掉一個 provider／工具／shell 寫法，agent 就先改到權威
repo；事後再抓，已經污染本輪判準。它還有政策漂移與 TOCTOU：檢查的是宣告，執行的是
另一條工具路徑。

範圍隔離自己的失效模式也要明列：snapshot 可能過期而衝突；patch importer 若沒處理
symlink、rename、binary、mode 或 submodule 就可能越界；若 parent 在 worker 污染過的
副本內跑「驗收」，隔離等於失效；程序在 patch 完整落盤前死亡則沒有可交回產物。這些
都能在 trusted boundary fail-closed，最壞結果是拒收／重跑，不是悄悄讓 worker 改掉
驗收規則。

這條已有真實 caller：TDD 的實作員、測試員與重構員現在就在權威 repo 工作，所以不受
「沒有呼叫端不寫」阻擋。第一支紅測試應是
`tests/整合/test_範圍隔離.py::test_實作員改自己副本的測試也不能影響可信驗收`；它會
fork worker，故必須留在整合層。這是另一個後續實作決策，本文件不寫任何程式。

### 哪些其實已有，只是形狀不同

| 項目 | 已有的形狀 | 還缺的精確小塊 |
|---|---|---|
| 1 | `邊包`＋四終局＋typed TDD handoff＋runner output guard | caller-specific domain payload runtime validator；現在無 caller。 |
| 2 | host 跑 gate、算 budget／上限／必要分支，模型不持有停止權 | 沒有通用缺口；未來只會有 caller-specific 公式。 |
| 3 | 線性 TDD 的軌跡、進度、接續票與 code 3／4 分流 | dependency-wave 的可序列化 per-item resume manifest；現在無 caller。 |
| 4 | 屏障、必要分支、缺口與最少 process-success 數 | domain 票型別、完整 lens 集合與計票 caller；現在無 caller。 |
| 5 | 跨輪前情已有 secret mask | 同一提示內跨角色資料的 fence 與內嵌 marker 清除；真實 caller 已存在。 |

## 後果

- 五項差異中的立即工作只有第 5 項：改一個 production sink、一個既有純單元測試檔，
  不新增架構層；範圍隔離則取代另一路正在考慮的權限矩陣方案，另立後續實作工作。
- nova 不追求「官方 18/18 長得一模一樣」；它保留跨 provider／跨程序可驗證的資料形狀，
  只在真實 caller 需要 domain 欄位時才加 runtime schema。
- 第 2 項維持現狀：每個新驗收量都要回到 host 可觀察的原始事實，不能接受模型自報。
- 在觸發條件出現前，nova 明確接受兩個限制：batch dependency failure 不能跨 invocation
  精準續跑；一般 TDD 只有一次 review，不宣稱三票共識。
- 第 5 項落地後仍不能把 fence 寫成「已消滅 prompt injection」。範圍隔離、canonical
  tests 與 patch import gate 才是限制副作用的硬邊界。
- 改採範圍隔離會增加 snapshot、patch validation 與 fresh verification 的磁碟／時間成本，
  也會讓衝突 fail-closed；代價換來的是 worker 無法在同一權威工作樹裡同時改實作與判準。
- 本文件沒有新增任何 `src/nova/圖/`、註冊表、DSL、skill、CLAUDE 提醒或全掃 mutation，
  也沒有把換模型當成任何一項的解法。
