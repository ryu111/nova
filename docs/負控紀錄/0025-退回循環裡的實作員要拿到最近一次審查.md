# 退回循環裡的實作員要拿到最近一次審查

## 現場

審查同時開 `[test-design]` 與 `[impl]` 時，路由整包退測試員（`狀態機.下一步`，
那一格是對的：`[test-design]` 實作員動不了）。但兩階之後的實作員上一步是
`驗證紅` 的 pytest 輸出，審查的 `[impl]` 條目**沒有任何機制**走得到它——
`工作流._看階段才帶的段落` 只把 `_上次審查與其後回報` 接給審查階。
於是實作員順著紅做出反方向的最小綠，第二次審查再開同一批意見，
兩輪撞上「審查意見連續要求修改 2 次」護欄（實測：e023f9 兩輪同五條）。

同一條路上還有第二個缺口：讀取策略的 `被退回` 只看 `是回頭邊(軌跡[-1].階段, 實作)`，
而 `是回頭邊(驗證紅, 實作)` 是 False，所以退回循環裡的實作員拿到的是首輪那段
「不要自己跑全套測試」。`是回頭邊` 的定義沒錯（去處排在來源前面），
退回循環是另一個概念，住在 `工作流._在審查退回循環裡`。

## 固定負控

登記在 `tests/負控/登記們/退回循環帶審查.py`（四把刀），下面是**親手下刀**看到的實際輸出。

| 破壞什麼 | 預期 | 實際 |
|---|---|---|
| 把 `迴圈/工作流.py` `_這一階要接審查回顧` 的 `if 定義.代碼 not in (階段代碼.實作, 階段代碼.測試):` 改成 `if True:`（＝回顧只剩審查階接得到） | `test_退回循環裡的實作員看得到最近一次審查的impl條目` 要紅 | 紅：`AssertionError: 實作員拿不到審查的 [impl] 條目——它只看得到驗證紅那份 pytest 輸出`；`test_退回實作接線.py::test_混合審查退回測試員之後送出去的提示帶著審查全文與退回策略`、測試階那支一起紅 |
| 同一格只收窄成 `if 定義.代碼 is not 階段代碼.實作:`（＝只有實作階接得到、測試階不接） | `test_驗證紅意外綠再退一次之後的測試員仍拿得到審查全文` 要紅，實作階那兩支照樣綠 | 紅：`AssertionError: assert '邊界案例沒寫' in '…你現在的階段：寫一支會紅的測試\n\n上一步（verify-red）的結果：\n<<<UNTRUSTED 假判準 UNTRUSTED>>>'` |
| 把 `被退回` 改回只看 `是回頭邊(軌跡[-1].階段, 定義.代碼)`（拿掉 `or _在審查退回循環裡(軌跡)`） | `test_退回循環裡的實作員拿到的是被退回那一輪的讀取策略` 要紅 | 紅：`AssertionError: assert '這一輪是被退回來的' in '…上一次審查：…**不要自己跑全套測試**…'`（審查全文帶到了，讀取策略仍是首輪那段；引的是回顧裡那個**區塊標籤**，不是那一段的標題——標題的措辭是實作的自由，抄進紀錄只會再漂一次） |
| 把 `_在審查退回循環裡` 的 `return 軌跡[位置].審查結論 is 審查判定.要求修改` 改成 `審查結論 or 讀審查判定(證據)`（＝欄位沒填就回頭猜自由文字） | `test_沒填審查結論的審查步不算要求修改` 要紅 | 紅：`AssertionError: 沒填 審查結論 卻被當成要求修改——證據的自由文字被當成第二個語意來源了`（提示裡出現「**這一輪是被退回來的**」） |

四把刀分開砍，因為每一把單獨修好都能讓其餘三支照樣綠：
第一把留著 `_在審查退回循環裡`（策略對、審查全文沒帶到）、第二把只差測試階那一格
（實作階那組全綠）、第三把留著審查全文（帶到了、還在禁它跑全測試）、
第四把在正常軌跡上跟結構化欄位同結論（只有「審查步沒填 `審查結論`」那種軌跡看得見）。

錨點跟著實作走：`_這一階要接審查回顧` 的排除條件、`被退回` 那一行、
`_在審查退回循環裡` 的 return。實作換寫法時錨點對不上會是 `RUN_ERROR`，不是靜默通過。
