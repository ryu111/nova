# 連續兩輪要求修改但條目在減少，就不算不收斂

## 固定負控

`連續審查要求修改` 原本**只數次數**：連著兩個審查步的 `審查結論` 是要求修改就收，
一個字都沒看審查內容——5 條 ISSUE 變 1 條，跟 5 條原封重複，在它眼裡完全一樣。
現在「有沒有在收斂」由**條目數**這個可數的鍵決定：`讀審查問題列` 讀出來的條目數
比上一輪少就是有進展，連續計數重置為 1；門檻仍是 2。
收場也拆出來自己一格 `review-not-converging`，不再借 `stagnation`——
兩者處置不同（去看那批 ISSUE vs 換策略縮題目），借誰的格子就是說了誰的事。

| 破壞什麼 | 該紅的測試 | 親眼看到 |
|---|---|---|
| 把「條目數變少就重置為 1」改回「一律加 1」（條目數照算、識別碼照印，只是沒人拿進展做決定） | `tests/單元/test_狀態機.py::Test審查條目在減少就不算不收斂::test_五條變一條不收護欄` | KILLED |
| 把工作流審查那條的 `護欄原因=護欄種類.審查不收斂` 改回 `護欄種類.無進展` | `tests/單元/test_工作流.py::Test審查不收斂自己一格::test_審查連續要求修改落的是review_not_converging` | KILLED |

變異登記在 `tests/負控/登記們/審查不收斂.py`；本輪兩把都手動跑過，各為 1 failed（KILLED），已還原。

錨點更正（20260903T004500Z）：兩把刀原本抄的錨點在目標檔各出現 0 次，
runner 會直接報 `RUN_ERROR`、刀根本套不上去。已改成逐字的實際程式行——
`狀態機.py` 的 `連續次數 = 1 if len(下一輪) < len(上一輪) else 連續次數 + 1`
與 `工作流.py` 的 `收尾 = 結束(結束代碼.護欄, 審查不收斂原因, 護欄原因=護欄種類.審查不收斂)`，
兩者在各自檔中皆恰好出現一次。改完由負控 runner 重跑

`審查不收斂借回無進展那一格` 兩格），兩筆皆 KILLED。
