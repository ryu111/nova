# PR 在不在要用查的，不是拿 `gh pr create` 撞出來的

## 固定負控

`_提交推送並開PR` 收尾前那一步：先問 `gh pr list`（借 `收尾現場` 那份查詢與解析），
恰好一筆就跳過 `gh pr create` 直接往等 CI 走。撞出來的那條路（無條件 create）在
08:56 那格死過一次：`a pull request … already exists` 之後整趟停住，人得手工接完。

| 破壞什麼 | 該紅的測試 | 親眼看到 |
|---|---|---|
| 把 `有PR, 原因 = _這條分支有沒有PR(根目錄, 分支)` 換成 `False, ""`（不查，無條件建 PR） | `tests/整合/test_收推派工開的分支.py::test_PR已經存在時收不呼叫create` | 紅（2026-09-03T01:20Z）：`Left contains one more item: ['pr', 'create', ...]`；改回來即綠 |
| 把「查不出來就回不知道」摺成「沒有 PR」（`if 有PR is None:` 改成 `if 有PR is None and False:`） | `tests/整合/test_收推派工開的分支.py::test_問不出這條分支有沒有PR時收停在未知不建也不合併`（四種現場） | 紅（2026-09-03T01:20Z）：空輸出那格 `收到 0`、`gh pr create` 被呼叫；改回來即綠 |

兩格都已經進 `tests/負控/登記們/派工開分支.py`（識別＝「PR在不在退回不查一律建」、
「PR查不出來摺成沒有PR」）。fail-open 那一半原本沒有刀，
`test_問不出這條分支有沒有PR時收停在未知不建也不合併` 落地之後補上了：假 gh 的
`pr list` 掛 `NOVA_收推PR清單原樣` 就原樣吐空字串／半截 JSON／清單裡混著讀不成 PR 的
項目／同一條分支兩筆並回 0，斷言 `收` 回 3 且 create 與 merge 都沒發。

## 還沒有刀的那一格：查詢沒指名分支

`gh pr list` 不帶 `--limit` 只吐前 30 筆。查詢少了 `--head <分支>`，目標 PR 排在別人
後面就比不到，「有」被讀成「沒有」而去 create——跟 08:56 那格同一種死法，只是成因
從「不查」變成「查得不準」。假 gh 的 `pr list` 這一輪已經照真的 gh 補上這兩個行為
（吃 `--head`、預設截 30 筆），清單上永遠先擺滿 30 筆別條分支的 PR，
`test_PR已經存在時收不呼叫create` 因此在 `--head` 落地之前是紅的。等實作補上篩選、
這支轉綠，再把「拿掉 `--head <分支>` 這個參數」登記成一列固定負控。

順帶一提：這支還紅著的期間，`tests/負控/test_登記的變異會被殺` 裡「PR在不在退回不查
一律建」那一列也會失敗——負控刀要求變異前是綠的，而這裡的基準線本來就紅。
`--head` 一落地它就跟著恢復；「PR查不出來摺成沒有PR」那一列現在是綠的
（2026-09-03 這一輪實跑）。

「有 PR」的門檻同時被釘成兩道：清單比得到分支名只是候選，還要拿那筆的 `number` 去
`收尾現場.查收尾現場`（走 `gh pr view`）把編號、網址、head SHA、mergeStateStatus
取齊，取不齊就是「不知道」。少了 view 那一道，`收.py` 等於自己重寫了一份只看分支名
的查詢——那份查不出要合併的是哪一個 PR，卻已經在往 merge 走。
