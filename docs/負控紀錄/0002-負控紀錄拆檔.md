# 負控紀錄拆檔（一主題一檔）

## 為什麼拆

硬規則 4 要求每條線做完固定負控都往同一張表尾巴 append 一列，於是
「線甲加一列 → 合併；線乙加一列 → rebase 撞在同一行」——三列內容毫不相干，
git 卻報衝突，因為它們在同一行的前後。代價不只是解衝突的時間：
`mergeStateStatus=DIRTY` 的 PR GitHub 根本不跑 CI，於是
「衝突 → CI 沒跑 → 看起來卡住」會被誤診成 CI 壞了。

形狀照 `tests/負控/登記們/` 抄：**新線只加一個檔，收集時 glob 起來，零衝突。**
硬規則 4 沒有放寬，「補一列」還是要補，只是補到
`docs/負控紀錄/<主題>.md`，不再是同一個檔尾。

## 動手前先回答的兩題

1. **這份紀錄是給誰看的？** 查詢用，不是流水帳：CLAUDE.md 說「那些不必重推——
   懷疑某條防護時照著『破壞什麼』那欄做一次就好」。查詢靠的是 grep，
   `rg '<關鍵字>' docs/負控紀錄/` 跟 grep 單一檔一樣好查（而且 2281 行的單檔本來就
   得靠 grep，沒有人從頭讀）。所以拆檔不會讓它更難查。
2. **有沒有東西在機械讀它？** 有，一個：`tests/驗收/test_文件即事實.py`
   的 `_要檢查的文件()`。它原本把搬家前那個單一檔寫死在清單裡，
   現在改成掃整個目錄。其餘出現的位置（`src/nova/載體/豁免登記.py`、
   `docs/研究/` 那幾份）都是註解與引用，沒有人 parse 它。

既有那 2281 行**原封不動**搬成 `docs/負控紀錄/0001-既有紀錄.md`
（只改兩個相對連結的深度，因為檔案往下移了一層）：改寫歷史紀錄跟解決衝突是
兩件事，混在一起 diff 會大到沒人看得出哪裡是真的改動。

## 這一格的固定負控

照新形狀做：把 `_要檢查的文件()` 從 glob 改回寫死一份清單
（只列 `docs/負控紀錄/0001-既有紀錄.md`），等於「新丟進去的主題檔沒被收走」。

| 破壞什麼 | 哪支該紅 |
| --- | --- |
| `_要檢查的文件()` 把負控紀錄目錄改回寫死清單，漏收新主題檔 | `test_每個主題檔都被文件檢查收走` |
| 同上，且新檔宣稱的測試名從此不受檢 | `test_新增主題檔不改任何程式就受檢` |
| 把 `docs/負控紀錄/` 收回單一檔案 | `test_負控紀錄已經一主題一檔` |

實測：改成寫死清單後，`tests/驗收/test_負控紀錄拆檔.py` 三支裡的前兩支紅
（`test_負控紀錄已經一主題一檔` 只看目錄形狀，那一刀動不到它），改回 glob 後全綠。

第一版的 `test_每個主題檔都被文件檢查收走` 其實驗不出上面那一刀：預期清單跟
實際收集結果都來自 `_要檢查的文件()` 用的同一支 glob，兩邊一起漂就永遠相等，
「漏收」出不來。現在測試自己 `rglob` 數一次目錄當 oracle——**oracle 不准跟被驗的
東西共用實作**，否則那支測試量的是「它等於它自己」。

## 補上「歷史一列都不能少」那支（2026-09-01 撿回來時加的）

票明文要求：「要有一支測試守住歷史沒少，**不要只數檔案數，要數『破壞什麼』
那一欄的列數**」。原本沒有——**只數檔案數會恆真**：把 2,500 行歷史清空、
留兩個空檔，檔案數照樣是 2，三支測試全綠。

`test_拆檔不准弄丟任何一列負控紀錄` 數的是表格資料列（`|` 開頭結尾、
扣掉分隔線與 `| 破壞什麼` 表頭），地板是拆檔當下的 **518**。
用 `>=` 不用 `==`：歷史只會長不會縮，新線補的列也算進來。

| 破壞什麼 | 哪支該紅 |
| --- | --- |
| `0001-既有紀錄.md` 砍成前 200 行（521 列 → 167 列） | `test_拆檔不准弄丟任何一列負控紀錄`（實測紅：`assert 167 >= 518`） |
