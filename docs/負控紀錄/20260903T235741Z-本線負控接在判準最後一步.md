# 本線 diff 動過的那幾把負控刀，線內就跑

## 固定負控

判準的最後一步是 `uv run nova 閘 本線`，那條閘（`registered-mutation-diff`）只跑
「這條 diff 動過的 `tests/負控/登記們/` 模組」裡登記的刀。三處保證各配一把刀。

| 破壞什麼 | 該紅的測試 | 親眼看到 |
|---|---|---|
| 從 `規則表.動過的登記檔們` 拿掉 `git ls-files --others --exclude-standard` 那一段 | `tests/整合/test_本線負控吃得到新增檔.py::test_還沒add的新登記檔也算本線動過` | 紅（AssertionError） |
| 把 `本線負控.判定選到的刀` 那格「動過的檔非空卻選到 0 把」改成回 `(True, …)` | `tests/單元/test_本線負控篩選.py::test_只選這幾個登記檔的刀_選不到就不是綠` | 紅（AssertionError） |
| 從 `判準.預設判準步驟們` 拿掉新加的第三步 | `tests/單元/test_判準別跑變異刀.py::Test本線負控接在最後一步::test_預設判準最後一步是nova閘本線` | 紅（AssertionError） |

第一把守的是本票最貴的假綠：**新增一把刀＝新增一個 `登記們/<主題>.py`，而新檔不在
`git diff` 裡**。只看 diff 的話「新增刀」這個最常見的情形會選到 0 把、一路綠到 CI。

第二把守的是 fail-closed 本身，不是「有跑到那段程式」：檔名打錯、模組改名或 deselect
邏輯壞掉時，一把都沒跑卻全綠，那是唯一一種看起來完美的假綠。

第三把守的是「這一步真的掛在判準上」，而且它排在**最後**——排前面的話 `驗證紅` 那階
會跑到它，那階全測試本來就該紅，刀必然 `BASELINE_RED`，整條線會停在一個假的紅上。

三把都是本輪逐一破壞、親眼看到紅之後改回來的（改回來後三支重跑皆綠）。
刀的登記檔住 `tests/負控/登記們/` 底下（一線一檔），由測試員補上——
`tests/` 整棵樹在實作階段會被快照還原，實作員寫在那裡的檔案留不住。
