# `收` 建 PR 時標題只取第一行，本文是其餘

## 現場

`收.py` 過去把整段訊息同時當 `--title` 與 `--body`：

```python
("gh", "pr", "create", "--title", 訊息, "--body", 訊息),
```

收訊息按規矩一定有負控段、一定多行，於是每一條收 0 的線在 **push 成功之後**才吃到

```
pull request create failed: GraphQL: Title is too long (maximum is 256 characters)
```

閘九條全過、commit 進去了、分支也推上去了，只掛在最後一格——人手上是一個做了一半的
現場，只能自己 `gh pr create` 把 PR 補出來（#243 就是這樣進去的）。

治法是照訊息本來的結構切，不是把訊息截到 256：收訊息是 git 慣例的
「第一行標題＋空行＋本文」，PR 也照這個切。

- `--title` ＝ 第一行 strip 之後；`--body` ＝ 第一行**之後**那一段，開頭空行去掉。
  那個空行是分隔符不是本文，留著的話 PR 內文從一個空行開始。
- 單行訊息沒有本文可切，`--body` 退回第一行：`--body ""` 開得出 PR，但內文整片空白，
  人在 PR 頁上看不到這一票做了什麼。
- commit 訊息不受影響：`git commit -m` 照樣收整段，標題與本文都留在 git 歷史裡。
- 第一行自己就超過 256 字：擋在 **閘開跑之前**（`子命令_收` 的第一段），訊息指名
  「標題超過 256」並把數字講出來。標題長度看一眼字串就有答案，不值得讓人先等提交閘
  本體實測 8.5 秒才被告知一個開跑前就看得出來的錯；完整測試套件約兩分鐘是驗證成本，
  不是 `收` 執行的提交閘成本，改完第一行再等一輪。
  留給 GitHub 去擋的話，那句 GraphQL 錯是在已經 commit、已經 push 之後才回的——那正
  是上面那個要人手工收拾的現場。恰好 256 字要放行，那是 GitHub 收得下的最長標題。

## 固定負控

登記在 `tests/負控/登記們/派工開分支.py`（一線一檔，不往 `登記.py` 檔尾 append）。

| 破壞什麼 | 預期 | 實際 |
|---|---|---|
| `("gh", "pr", "create", "--title", 標題, "--body", 本文)` 換回 `--title 訊息, --body 訊息` | `test_收建PR標題只取第一行.py::test_多行訊息建PR時標題是第一行本文是其餘` 要紅 | KILLED——`--title` 拿到整段三行訊息 |

這一把親手下過一次（`uv run pytest tests/負控/test_登記的變異會被殺.py` 點名這個負控
節點），跑完 `git status` 確認 `src/` 沒殘留；CI 上由 `tests.負控.執行器.執行變異` 再跑一次。

## 沒做的

不動 `gh pr create` 以外的 argv、不碰 commit 訊息怎麼組（整段照舊）、不替人截字改寫
標題——標題被動過而人不知道，比當場擋下來貴得多。
