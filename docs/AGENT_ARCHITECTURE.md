# Agent 三層架構規範:Harness / Loop / Graph

> 版本 1.2 · 2026-08-01 · 語言:繁體中文
> 用途:作為 CLAUDE.md 或系統提示詞,讓 AI(Claude / Claude Code)依此框架設計、實作與診斷 agent 系統。
> 框架來源:Bijit Ghosh〈Agent Harness Engineering vs. Loop Engineering vs. Graph Engineering〉(2026-07,X 轉載:@beamnxw)之結構化重整;整合 @vorty279〈循環工程:系統如何自我改進〉(X,2026-07-22)與行明(@Gyome1_)〈Claude Code 的完整圖工程實戰手冊〉(X,2026-07-23);並補充 LangGraph、Microsoft AutoGen、OpenAI Agents SDK 官方文件要點。

## 0. 一句話版本

| 層 | 一句話 | 回答的問題 |
|---|---|---|
| **Harness(執行載具)** | 建造模型運作於其中的環境 | 模型能看到什麼、能做什麼? |
| **Loop(迴圈)** | 設計「工作 → 回饋」的重複循環 | 什麼觸發下一次嘗試?何時停止? |
| **Graph(圖)** | 把流程的形狀變成明確的節點與轉移 | 接下來允許哪個元件執行? |

**診斷順序:環境 → 回饋 → 流程(Harness → Loop → Graph)。**

## 1. 核心原則(AI 必須遵守)

1. **Agent = 模型 + Harness。** 模型以外的一切——程式碼、設定、執行邏輯——都屬於 harness。
2. **多數「agent 失敗」不是模型失敗。** 沒有持久狀態、工具定義含糊、重試無上限、缺乏獨立驗證,都是系統層的責任。修復前先定位負責的層,不要先換模型或改提示詞。
3. **三層互不替代。** 圖畫得再漂亮,harness 掉狀態照樣失敗;harness 再完善,沒有停止規則就是燒錢;loop 再嚴謹,分支與審批埋在 ad-hoc 程式碼裡仍不可維護。
4. **由簡到繁。** 先最小 harness → 有界 loop → 需要時才引入 graph。在看過 agent 實際解一次任務之前,不畫超過必要的圖。
5. **以證據循環,不以自信循環。** 「模型說完成了」不是停止條件;「測試通過、schema 驗證、連結可解析、審核者核准」才是。

## 2. Harness Engineering(執行載具)

**回答的問題:模型能看到什麼、能做什麼?**

**定義**:模型周圍的全部機械——系統提示、工具定義、記憶、沙箱、模型路由、交接(handoff)、中介層、context 壓縮、權限、日誌、驗證介面。

**判別法**:把模型從架構圖上刪掉,還站著的全部都是 harness(工具、資料存取、狀態儲存、沙箱、中介層、評估器、重試政策、UI)。

### 2.1 六大組成

| 組成 | 內容 |
|---|---|
| Context 注入 | 指令、檢索到的事實、對話狀態、技能、任務政策 |
| 行動面(Action Surfaces) | API、瀏覽器、shell、code interpreter、資料庫、MCP 工具 |
| 持久化 | 檔案、檢查點、session、進度日誌、git 歷史、長期記憶 |
| 執行控制 | 逾時、重試、預算、模型路由、子 agent 生成、審批閘 |
| 安全與治理 | 權限、隔離、允許清單、密鑰處理、人工簽核 |
| 可觀測性 | 追蹤(trace)、工具輸入/輸出、狀態轉移、成本、延遲、評測結果 |

### 2.2 Harness 五問(最小生產檢核)

1. **Context**:注入、檢索、或刻意排除了哪些資訊?
2. **Action**:模型可呼叫哪些工具?實際允許到什麼程度?
3. **State**:進度、工件、失敗與決策存活在哪裡?
4. **Policy**:哪些動作需要確定性阻擋或人工核准?
5. **Evidence**:操作者如何檢視發生了什麼、為什麼?

### 2.3 設計規則

- Harness 必須**任務特化**:研究 agent 需要來源檢索、引用追蹤、區分證據與推論;編碼 agent 需要 repo、檔案工具、測試執行、diff 邊界;客服 agent 需要帳號權限、政策檢查、升級路徑。把大 harness 複製到不相關任務,只會增加失敗面而不增加能力。
- **不要把 harness 當雜物抽屜**:工具越多選錯越多,context 越雜越混淆,權限越寬風險越大——三者過量都放大爆炸半徑。
- **長時間、跨 session 的工作靠 harness,不靠提示詞**:初始化器、進度檔、git 歷史、增量提交的紀律,讓每個新 context window 能從上次中斷處接續。
- 工具權限即能力邊界:「只能讀一個目錄的工具」與「有網路的 shell」是不同的能力;「儲存任務狀態的記憶檔」與「context 結束即消失的對話」是不同的持久性;「人工核准掛鉤」與「請模型小心的指令」是不同的控制。這些是執行期屬性,不是提示詞美學。

### 2.4 何時處理 harness

缺能力/無法乾淨續跑/遺失狀態/擁有不該有的存取權/無法稽核/跨環境行為不一 → 修 harness。

## 3. Loop Engineering(迴圈)

**回答的問題:什麼觸發下一次嘗試?何時停止?**

**定義**:每個會用工具的 agent 都內建最小 loop——呼叫模型 → 看結果 → 跑工具 → 回饋觀察 → 重複至產出最終答案。Loop engineering 從你**刻意**在此之上加建循環開始。

### 3.1 四種 loop 形狀

| 形狀 | 機制 | 用途 |
|---|---|---|
| Agent loop | 模型選動作、收工具結果、重複至達成任務條件 | 多數短流程 |
| Verification loop | 外部評分器檢查產出、回傳可行動的回饋、有證據才重試 | 品質收斂 |
| Event loop | 排程、webhook、新文件喚醒 agent | 讓 agent 成為系統元件,而非手動呼叫的聊天 |
| Improvement loop | 檢視 trace 與失敗 → 調整指令或工具 → 重跑評測 → 有改善且無不可接受回歸才保留 | 版本迭代 |

### 3.2 Loop 契約(7 欄位,缺一不可)

| 欄位 | 定義 |
|---|---|
| Trigger | 什麼啟動這個循環?(使用者請求、排程、失敗測試、新資料、評估器回饋) |
| Goal | 哪個**可觀察的狀態**算成功?(不是「持續改善」) |
| State / Memory | 下一輪需要知道什麼,而不必重播全部歷史? |
| Action policy | agent 允許改什麼、呼叫什麼、委派什麼、花多少? |
| Evidence | 用什麼評估結果?(測試、schema 驗證、引用、diff、指標、人工審查) |
| Feedback | 證據失敗時,回饋什麼**具體、精簡**的原因? |
| Stop rule | 什麼終止循環?(成功、預算耗盡、逾時、不可恢復錯誤、人工升級) |

### 3.3 邊界控制(必備)

最大迭代次數、逾時、token 預算、無進展偵測、升級路徑。這些不是「agent 比較笨」的表徵,而是防止自主流程把不確定性轉成無限成本或副作用的控制。

### 3.4 成本原則

每個評分器、審核者、重試都是額外的模型呼叫或工具執行。**從能運作的最簡架構開始;只在「失敗的成本」高於「檢查的成本」之處,增加 loop 複雜度。**

### 3.5 提示詞 vs. Loop

提示詞決定模型在一次呼叫內做什麼;loop 決定系統在呼叫**之後**做什麼——如何讀結果、選回饋、決定是否繼續、持久化進度、何時停止。這是一次性指令與受管理流程的差別。

### 3.6 實戰:自我改進循環(self-improving loop)

> 來源:@vorty279〈循環工程:系統如何自我改進〉(X,2026-07-22)之結構化重整。

**核心主張**:完美的提示不存在;存在的是能自己找到夠好版本的循環。**你不是設計答案,而是設計找出答案的循環。** 這是 §3.1「Improvement loop」的具體實作形。

#### 四步循環(重複直到指標不再上升)

| 步驟 | 內容 | 要求 |
|---|---|---|
| ① 產生 Generate | 嘗試產生提示、程式碼、答案或策略 | 從記憶(近幾次嘗試+回饋)出發,不從零開始 |
| ② 評估 Evaluate | 結果過指標:測試、評分器、編譯器、評判器 | **自動且數值化** |
| ③ 反思 Reflect | 以文字說明失敗原因 | 不是「得分 0.4」,而是「漏掉空輸入檢查」 |
| ④ 變異 Mutate | 依反思重寫,回到 ① | 從存檔最佳結果出發 |

#### 存檔(archive)是關鍵

- 每次嘗試與其分數、回饋存入存檔;下一次變異從**目前最佳**開始。
- **沒有存檔 = 重試;有存檔 = 定向進化。** 個別嘗試分數上下波動是雜訊;「存檔最佳」線單調上升。
- 停止條件:達到目標值,或迭代/預算耗盡——**缺停止條件,循環會無限燒錢**。
- 實例:ShinkaEvolve 以存檔+智慧父代採樣,約 150 次評估達到先前需數千次的水準;GEPA 以反思失敗做提示演化,部分任務樣本效率高於 RL 數倍。

#### 思考者 · 工作者 · 驗證者(Thinker / Worker / Verifier)

單一模型卡住時把角色拆開:**思考者**拆解任務與計劃(強模型)、**工作者**執行產出、**驗證者**獨立驗收——接受或退回重做(可用便宜模型)。仍是產生→評估→反思,但驗證者是獨立 agent 而非測試;適用於「評估本身需要推理」的任務。成本約 3 倍,依 §3.4 成本原則使用。

#### 最大陷阱:Goodhart 效應

循環只會改進你所衡量的。指標不誠實 → 代理指標上升、實際品質下降。

- **鐵律:結果能「自動且誠實」驗證,循環工程才有效**——測試通過/失敗、數學有正解、SQL 有毫秒數。
- 沒有客觀評估(如「讀者喜不喜歡」)→ 循環會優化評判者而非現實:先建客觀評估器,或最後一步人工把關,或將循環錨定到規範(spec)而非單一標量指標。
- 呼應 §8 反模式二(自寫自評)與 §11(評估獨立於被優化元件)。

#### 最小循環 pseudo-code

```python
memory, best = [], {"score": -1}
for i in range(max_iters):
    attempt = generate(task, memory[-3:])          # 記憶餵回生成
    score, feedback = evaluate(attempt, tests)     # 自動、數值化、誠實
    memory.append({"attempt": attempt, "score": score, "feedback": feedback})
    if score > best["score"]:
        best = {"score": score, "attempt": attempt}  # 存檔最佳:重試 → 定向進化
    if score >= target:
        break                                        # 停止:目標 + 迭代上限
```

#### 適用場景與開源起點

程式碼修復(SICA)、提示演化(GEPA)、演算法搜尋(AlphaEvolve / OpenEvolve)、SQL 與管線優化。開源:SakanaAI/ShinkaEvolve、gepa-ai/gepa、MaximeRobeyns/self_improving_coding_agent、algorithmicsuperintelligence/openevolve、ShengranHu/ADAS、XMUDeepLIT/Awesome-Self-Evolving-Agents;基礎閱讀:Reflexion、DSPy。使用前檢查授權與最後提交日期。

## 4. Graph Engineering(圖)

**回答的問題:接下來允許哪個元件執行?**

**定義**:節點=工作步驟;邊=允許的轉移(順序、條件分支、平行 fan-out、join、循環、人工中斷);狀態在圖中流動。拓撲讓你能實際驗證你意圖中的控制流程。

**注意**:這不是知識圖譜(knowledge graph)。工作流程圖表示控制與狀態轉移,不是資料中的實體與關係——兩者解決不同問題,由不同團隊建置。

### 4.1 六項設計決策

| 決策 | 問題 |
|---|---|
| 節點邊界 | 哪些工作屬於確定性函式/LLM 呼叫/專家 agent/人工審核步驟? |
| 狀態 schema | 每個節點能讀寫什麼?平行更新如何合併? |
| 路由條件 | 什麼證據把工作送往前進、後退、側路、或升級? |
| 並行 | 什麼可平行執行?什麼必須 join?共享資源如何協調? |
| 循環與出口 | 哪裡允許重試?允許幾次?什麼讓循環安全? |
| 持久化 | 檢查點放哪裡?中斷後如何恢復執行? |

### 4.2 何時值得/不值得

- **值得**:真實分支、真實平行工作、審批閘、恢復路徑、多個專家 agent。(AutoGen 的判準:需要精確控制 agent 順序、不同結果走不同下一步、確定性分支、含真實循環的多步流程。)
- **不值得**:工作本質是「給一個 agent 三個工具讓它做完」。圖能讓除錯更容易,但也可能在你理解任務之前就凍結假設;若模型需要動態發明計畫,強行把每條路徑塞進固定圖,系統會更脆弱而非更穩。

### 4.3 實戰:圖工程與菱形模式(Claude Code)

> 來源:行明(@Gyome1_)〈Claude Code 的完整圖工程實戰手冊〉(X,2026-07-23)之結構化重整。

**核心主張**:與其寫更長的提示,不如設計資訊在系統中傳遞的路徑:**線性 → 扇出 → 簡化 → 驗證 → 綜合**。Claude Code 不必以單一 agent 逐項完成長清單:它可以產生編排程式碼、生成專門子代理、把輸出路由給不同模型,證據通過驗證後才組裝最終結果。DAG、管線、屏障、MapReduce 都是老模式——改變的是節點內部做的事。圖的第一個功能是**控制帳單**:計算發生在哪、哪個模型處理哪個決策、不確定結果如何流轉。

#### 節點三原則

1. **一個節點一個決策**:有界任務、明確輸入、明確輸出、有限決策面。搜尋+評估影響+設計修復+寫建議塞進一個節點 = 多個隱藏階段,無法除錯。
2. **邊承載結構化證據**:節點輸出 schema 化(file、lines、severity、confidence、evidence),下游可拒絕不完整結果、歸類相關檔案、轉送不確定證據;自由段落迫使每個下游重建上游語意,多階段後歧義累積改變結論。
3. **確定性工作交給程式碼**:合併、去重、排序、明確路由規則用普通程式碼——同輸入同輸出;丟給模型只增加 token 成本與證據遺失風險。**每次模型呼叫都應對應一個真正需要判斷的決策。**

#### 菱形模式(扇出 → 屏障 → 扇入)

任務大到單一 context 裝不下時的標準形狀:

- **扇出**:分支必須「共享輸入、互不依賴」才成立;拆分依據是不同來源/視角/程式碼區域/假設——把模糊任務拆成十二個近似任務,只會得到措辭略異的重複結論。
- **屏障(barrier)**:暫停下一階段直到收集足夠證據。**屏障是可靠性模型,不只是同步機制**,要回答:最少幾個成功分支?哪些分支必要?失敗節點重試,還是判定最終結果不完整?
- **先簡化,後綜合**:全部發現直接灌給頂級模型會淹沒重點。程式碼去重 → 模型分群排序;激進壓縮會抹掉驗證所需細節——**每條結論保留 sourceFindingIds 可追溯性**。

#### 可靠性模式

| 模式 | 規則 |
|---|---|
| 按風險路由 | 模型給分類,分支邏輯留在程式碼;昂貴審查只花在高嚴重度發現 |
| 對抗驗證 | 重要發現交給多位獨立審查者,任務是「推翻」不是「改進」;共識(如 ≥2 票)才通過 |
| 隔離工作區 | 並行編碼 agent 各用 git worktree;後續節點比較補丁、檢查衝突、擇一合併 |
| 收斂循環 | seen 集合對「所有出現過」的項目去重(只去重已確認項,被拒項下輪會重跑同樣工作);停止 = 連續無新發現輪數 + 預算 + 最大迭代,三者並用 |
| 模型分層 | 提取/基本分類/小範圍搜尋用快模型;架構審查/對抗驗證/最終綜合用強模型;先做 token 預算——二十次便宜呼叫可能貴過一次強呼叫 |

#### 菱形 pseudo-code

```js
const findings = await parallel(branches.map(b => () =>
  agent({ task: b.task, context: scope, schema: FINDING_SCHEMA })))
const done = findings.filter(Boolean)
if (done.length < MIN_REQUIRED) throw new Error("覆蓋率不足")        // 屏障是可靠性策略
const unique = dedupeByKey(done.flat(), f => `${f.file}:${f.line}`)  // 確定性工作 = 程式碼
const curated = await agent({ task: "分群、依衝擊排序、保留來源引用", input: unique })
const verdict = await panel(reviewers, curated)                      // 對抗驗證:推翻,不是改進
return verdict.approvals >= 2 ? synthesize(curated) : escalate()     // 共識才綜合
```

#### 何時不要畫圖

單一模型裝得下相關 context、獨立分支少、錯誤答案代價低 → 線性即可。圖的開銷:編排碼、schema、重試、日誌、中間儲存、更多需除錯的故障狀態。(與 §4.2、§8 反模式一一致。)

## 5. 巢狀結構與除錯順序

三層是巢狀關係,不是競爭關係:

```
Harness:context + tools + state + permissions + observability
  └── Graph:nodes + edges + 狀態轉移 + 恢復路徑
        └── Loop:行動 + 觀察 + 驗證 + 停止
              └── 模型呼叫與工具結果
```

Graph 跑在 harness 裡,因為它需要 harness 的狀態儲存、工具、政策與追蹤;loop 活在 graph 的節點裡,因為每個節點可能要朝局部目標迭代。

除錯順序範例:
- 模型拿不到需要的檔案 → 查 **harness**
- 有改檔,但測試沒通過就停了 → 查 **loop**
- 測試失敗後,修復節點從未執行 → 查 **graph**
- 三種情況下,先換模型都是錯誤處方。

## 6. 介面定義(pseudo-code)

```ts
// ── Harness:模型以外的一切 ──────────────────────────
interface Harness {
  context:   ContextInjector   // 指令、檢索事實、對話狀態、技能、政策
  tools:     ToolRegistry      // 窄而有文件的工具契約(API、shell、DB、MCP)
  state:     StateStore        // 檔案、檢查點、進度日誌、git、長期記憶
  control:   ExecutionControl  // 逾時、重試、預算、模型路由、子 agent、審批閘
  policy:    Governance        // 權限、隔離、允許清單、密鑰、人工簽核
  telemetry: Observability     // trace、工具 I/O、狀態轉移、成本、延遲
}

// ── Loop 契約:7 欄位缺一不可 ────────────────────────
interface LoopContract {
  trigger:      Trigger         // 使用者請求|排程|webhook|失敗測試|新資料
  goal:         ObservableState // 可觀察的成功狀態,不是「持續改善」
  memory:       StateRef        // 下一輪所需,不重播全部歷史
  actionPolicy: Permissions     // 可改、可呼叫、可委派、可花費的範圍
  evidence:     Evaluator[]     // 測試|schema|引用|diff|指標|人審
  feedback:     FeedbackFn      // 失敗時:具體、精簡的原因
  stop:         StopRule        // 成功|預算|逾時|不可恢復|升級
}

function runLoop(c: LoopContract, h: Harness) {
  let fb = null
  while (!c.stop.reached()) {
    const action  = model.decide(h.context.view(), fb)   // 模型只做決策
    const result  = h.execute(action)                    // harness 執行並記錄
    const verdict = c.evidence.evaluate(result)          // 證據,不是自信
    if (verdict.pass) return success(result)
    fb = verdict.reasons                                 // 回饋餵入下一輪
    c.stop.consume({ attempts: 1, tokens: result.usage })
  }
  return escalate(h.telemetry.trace())                   // 具名升級路徑
}

// ── Graph:接下來允許誰執行 ──────────────────────────
interface GraphSpec {
  nodes: { id, kind: "fn" | "llm" | "agent" | "human", run }[]
  edges: { from, to, when: Condition }[]  // 順序|分支|fan-out|join|循環|中斷
  state: StateSchema                      // 各節點讀寫範圍與合併策略
  checkpoints: CheckpointPolicy           // 中斷後從哪裡恢復
}
```

## 7. 按症狀診斷表

| 症狀 | 負責層 | 修復方向 |
|---|---|---|
| 無法安全取得正確的資料或工具 | Harness | 工具契約、權限、沙箱、context 注入 |
| 跨 session 忘記進度 | Harness | 持久狀態、檢查點、進度工件、壓縮策略 |
| 第一次嘗試接近但不穩定 | Loop | 外部評分器、確定性測試、回饋、有界重試 |
| 過了成功點還在做/沒證據就停 | Loop | 證據型終止狀態、預算感知停止規則 |
| 多個專家需按受控順序執行 | Graph | 明確節點、邊、路由條件、join |
| 多步驟流程中失敗難定位 | Graph + Harness | 對齊圖節點的有狀態追蹤 |
| 中斷後工作消失 | Harness + Graph | 狀態持久化與檢查點邊界 |
| 分數上升但實際品質下降 | Loop + Harness | 評估器或改進邊界過擬合 |
| 流程變動太頻繁,固定圖畫不住 | (簡化) | 簡化 harness、控制權留給模型、延後圖形化 |

## 8. 五大反模式(禁止)

1. **還不理解工作就先畫圖。** 團隊在看 agent 實際解一次任務前,就把商業流程翻成幾十個節點。應先用較簡單的 harness 收集 trace,再把證實穩定的路徑正式化。
2. **讓同一個模型自寫自評。** 自我審查與自己共享盲點。優先用確定性檢查、獨立的審核 context;高影響動作必須人工核准。
3. **用「繼續試」當整個 loop 規格。** 無界重試是成本漏洞,不是策略。每個 loop 需要可量測目標、每輪新證據、最大嘗試次數、具名升級路徑。
4. **把 harness 當雜物抽屜。** 更多工具、更多記憶不等於更好:擁擠的工具集增加選擇錯誤,吵雜的 context 增加混淆,過寬的權限增加風險。
5. **把編排失敗怪給模型。** 模型無法補償過期狀態、含糊的工具 schema、壞掉的 API、缺失的出口條件。修理真正擁有該失敗的層。

## 9. 上線前檢核清單

- **Harness**:工具窄、有文件、可觀測?狀態持久?權限最小化?操作者能暫停、檢視、續跑一次執行?
- **Loop**:什麼證據證明成功?失敗時回饋什麼?允許幾次重試?預算用完會發生什麼?
- **Graph**:哪些路徑必須確定性?哪裡可平行?共享什麼狀態?人工閘與恢復路徑在哪裡?
- **評估**:團隊能重播真實 trace、比較版本、把改善歸因到特定變更而非直覺?
- **營運**:成本、延遲、失敗率、人工介入率、任務級成功率在生產環境有實際監控?

## 10. 建置順序(rollout path)

1. 一個模型、一個窄任務、一個最小 harness。
2. 一個有界 loop,帶外部驗證訊號。
3. 加上 trace、預算、權限邊界、持久工件。
4. 隱式控制流程變得難以測試時,才引入 graph。
5. 擴大自主權之前:holdout 評測 + 人工審查。

此順序避免最常見的架構錯誤:在理解節點內該住什麼行為之前,先畫複雜的圖。圖可以讓壞的 loop 更好視覺化,但不會讓它更可靠。

## 11. 應量測指標

- 對可測試規格的成功完成率
- 驗證通過率與回歸率
- 重試次數、無進展循環、升級頻率
- 工具呼叫錯誤與權限拒絕
- 時間、token、外部服務成本
- 中斷或節點失敗後的恢復成功率
- 人工核准、駁回、覆寫次數
- 重現失敗所需的 trace 完整度

評估必須獨立於被優化的元件:若 loop 的模型能改寫自己的評分器,分數不證明工作變好;若 graph 能靜默跳過失敗節點,最終回應成功不證明每個必要檢查都跑過。

## 12. 給 AI 的執行規則

- 當使用者要求你**設計新 agent**:依 §10 順序進行;寫程式之前,先產出 harness 五問(§2.2)的答案與 loop 契約(§3.2)的 7 欄位。
- 當使用者要求你**診斷 agent**:依 §7 對照症狀,指出負責層與修復方向;引用 §5 的除錯順序(環境 → 回饋 → 流程)。
- 當使用者要求你**審查架構**:跑 §9 檢核清單並標記缺項;逐條檢查 §8 反模式。
- 當使用者要求你**建立自我改進循環**:依 §3.6——先設計誠實的自動評估器(防 Goodhart),再設計記憶回饋、存檔與停止條件。
- 當使用者要求你**把大型任務圖形化**:依 §4.3 菱形模式——扇出設計、邊 schema、屏障策略、簡化可追溯、對抗驗證、收斂停止、模型分層;先回答「這個任務真的需要圖嗎」。
- 任何時候:
  - 不得建議「換更強的模型」作為第一修復。
  - 不得以模型自述完成作為停止條件。
  - 不得在未看過實際 trace 前擴充圖。
  - 失敗紀錄必須說明:發生什麼、在哪發生、哪一層擁有修復。「agent 表現不好」不是可行動的診斷。
