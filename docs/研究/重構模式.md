核心結論：Fowler 第二版把重構目錄分成七大類；業界通常由 IDE 處理語法與引用層面的機械重構，再用測試與遷移模式控制語意及系統邊界風險。

## 1. Fowler《Refactoring》第二版的分類骨架

結論：第二版的正式重構目錄可視為七大類，範圍從局部函式整理到繼承結構調整。

以下依第二版目錄列出主要手法英文原名；完整目錄可參考[出版社的第二版 TOC](https://www.informit.com/store/refactoring-improving-the-design-of-existing-code-9780134757711)與[Fowler 官方重構型錄](https://refactoring.com/catalog/index.html)。

| 分類 | 代表手法英文原名 |
|---|---|
| 1. A First Set of Refactorings | `Extract Function`, `Inline Function`, `Extract Variable`, `Inline Variable`, `Change Function Declaration`, `Encapsulate Variable`, `Rename Variable`, `Introduce Parameter Object`, `Combine Functions into Class`, `Combine Functions into Transform`, `Split Phase` |
| 2. Encapsulation | `Encapsulate Record`, `Encapsulate Collection`, `Replace Primitive with Object`, `Replace Temp with Query`, `Extract Class`, `Inline Class`, `Hide Delegate`, `Remove Middle Man`, `Substitute Algorithm` |
| 3. Moving Features | `Move Function`, `Move Field`, `Move Statements into Function`, `Move Statements to Callers`, `Replace Inline Code with Function Call`, `Slide Statements`, `Split Loop`, `Replace Loop with Pipeline`, `Remove Dead Code` |
| 4. Organizing Data | `Split Variable`, `Rename Field`, `Replace Derived Variable with Query`, `Change Reference to Value`, `Change Value to Reference` |
| 5. Simplifying Conditional Logic | `Decompose Conditional`, `Consolidate Conditional Expression`, `Replace Nested Conditional with Guard Clauses`, `Replace Conditional with Polymorphism`, `Introduce Special Case`, `Introduce Assertion` |
| 6. Refactoring APIs | `Separate Query from Modifier`, `Parameterize Function`, `Remove Flag Argument`, `Preserve Whole Object`, `Replace Parameter with Query`, `Replace Query with Parameter`, `Remove Setting Method`, `Replace Constructor with Factory Function`, `Replace Function with Command`, `Replace Command with Function` |
| 7. Dealing with Inheritance | `Pull Up Method`, `Pull Up Field`, `Pull Up Constructor Body`, `Push Down Method`, `Push Down Field`, `Replace Type Code with Subclasses`, `Remove Subclass`, `Extract Superclass`, `Collapse Hierarchy`, `Replace Subclass with Delegate`, `Replace Superclass with Delegate` |

要注意第二版的命名變化：

- 第一版的 `Extract Method` 在第二版通常改稱 `Extract Function`。
- `Move Method` 改稱 `Move Function`。
- `Rename Method`、`Add Parameter`、`Remove Parameter` 等被整合到 `Change Function Declaration`。
- 第二版刪除了第一版型錄中的幾個大型重構，改把重點放在可逐步執行的小型重構。

這些差異見[Fowler 對第二版變更的說明](https://martinfowler.com/articles/refactoring-2nd-changes.html)。

## 2. 哪些已自動化，哪些仍需手動

結論：只要變更可以由 AST、型別資訊與引用圖推導，IDE 通常能自動完成；涉及設計意圖、外部契約或跨系統語意時，仍必須人工決策。

### 已高度自動化的類型

| 手法 | IDE 通常能做什麼 |
|---|---|
| `Rename Variable`、`Rename Field`、`Rename Function` | 更新同一專案內的引用、import、override，並提供 preview |
| `Extract Function`／`Extract Method` | 將選取程式碼抽成函式，推導參數與回傳值 |
| `Inline Function`、`Inline Variable` | 將函式或變數的使用處展開 |
| `Move Function`、`Move Field`、移動 class/package | 更新引用、import、namespace 與部分可推導的存取修飾詞 |
| `Change Function Declaration` | 重新命名、增加或移除參數，並遷移可找到的呼叫端 |

例如，IntelliJ IDEA 的文件明確支援[Rename](https://www.jetbrains.com/help/idea/rename-refactorings.html)、[Extract Method](https://www.jetbrains.com/help/idea/extract-method.html)與[Move refactorings](https://www.jetbrains.com/help/idea/move-refactorings.html)；Visual Studio 也支援[Extract Method 與 Inline Method](https://learn.microsoft.com/en-us/visualstudio/ide/reference/refactoring-extract-inline?view=visualstudio)。

這些操作仍不是「完全不用看」：

- IDE 通常會先分析衝突並提供 preview。
- `Extract Method` 若有多個輸出值、複雜泛型、例外或副作用，可能只能半自動完成；JetBrains 文件也列出多輸出與型別推導限制。
- Rename 對 reflection、字串形式的 method name、動態載入程式碼或外部 consumer 不一定找得到。

### 半自動化的類型

以下手法通常有 wizard 或部分支援，但設計決策仍由人做：

- `Extract Class`
- `Extract Interface`
- `Extract Superclass`
- `Pull Up Method`
- `Push Down Method`
- `Change Function Declaration`
- API 相容層、adapter、deprecated wrapper 的建立
- 大型資料結構或模組移動

工具可以搬程式碼，卻很難判斷：

- 新類別的責任邊界應該在哪裡。
- 函式應該移到哪個 module 或 aggregate。
- 公開 API 是否需要保留相容層。
- 新抽象是否真的降低耦合，而不是增加一層轉接。

### 通常仍以手動為主的類型

這些手法的關鍵不是語法，而是語意與設計：

- `Replace Conditional with Polymorphism`
- `Introduce Special Case`
- `Replace Type Code with Subclasses`
- `Substitute Algorithm`
- `Split Phase`
- 複雜的 `Extract Class`
- 資料庫 schema、事件格式、訊息契約與分散式交易的改造
- 需要同時改變 API consumer、部署設定或外部服務的重構

原因是 IDE 無法可靠推導「正確的新設計」。此外，公開介面、reflection、動態語言、字串呼叫與外部使用者都會使引用分析不完整。Fowler 也指出，若介面只是專案內部使用，全部 caller 一起修改可算重構；若是已發布的 public interface，就需要版本相容與遷移策略，詳見[Fowler 對介面變更的討論](https://martinfowler.com/bliki/IsChangingInterfacesRefactoring.html)。

## 3. 「重構不准改行為」如何機械化驗證

結論：characterization、approval、golden master 負責建立或比較行為基準，mutation testing 則檢查測試本身是否有能力抓到錯誤；它們不能互相取代。

建議流程是：

1. 先捕捉舊系統目前的可觀察行為。
2. 執行重構。
3. 以同一批輸入重跑並比較輸出。
4. 再用 mutation testing 檢查測試是否真的有效。

| 方法 | 機械上驗證什麼 | 適用時機 | 主要盲點 |
|---|---|---|---|
| Mutation testing | 對程式植入小錯誤，確認測試能否使它失敗；結果分為 `killed`、`survived` | 已有測試後，檢查關鍵模組或變更範圍的測試品質 | 不比較新舊版本；成本高；等價突變可能無法被測試殺死 |
| Characterization test | 記錄「系統現在實際怎麼做」，將觀察到的輸出變成測試預期 | 遺留系統沒有規格或測試，準備開始改造前 | 可能把既有 bug 也固定下來；只涵蓋測試到的輸入 |
| Approval test | 將實際輸出存成 artifact，由人檢查後批准，之後自動 diff | 輸出很大或結構複雜，例如 JSON、XML、HTML、報表 | 人可能無意義地全數 approve；時間、UUID、排序等非確定性會造成雜訊 |
| Golden master | 用舊系統或參考實作對一批輸入產生基準，讓新實作逐筆比較 | 替換大型元件、服務或整個子系統 | 舊系統不是必然正確；輸入樣本不足時，不能宣稱等價 |

### Mutation testing

Mutation testing 是「測試測試」：工具修改 production code，例如把 `>` 改成 `>=`、刪掉條件或改變回傳值，再執行測試。測試失敗代表 mutant 被 `killed`；測試仍通過代表 `survived`。

[PIT 官方文件](https://pitest.org/)特別指出，line coverage 只能表示程式被執行過，不代表測試能偵測錯誤，因此 mutation score 比單純 coverage 更接近測試有效性。由於成本高，通常只對 changed code 或高風險模組執行。[Stryker](https://stryker-mutator.io/docs/)也採用相同概念。

它不是「新舊版本等價性測試」：

- 它測的是測試 oracle 是否敏感。
- `survived` 不一定代表測試錯，也可能是 equivalent mutant。
- 100% mutation score 也不等於證明所有行為都保留。

### Characterization test、Approval test、Golden master

三者在業界有重疊，差別主要在焦點：

- `Characterization test` 強調「描述既有系統的實際行為」。
- `Approval test` 強調「輸出先產生，再由人審核批准」。
- `Golden master` 強調「以舊系統輸出作為新系統的參考基準」。

Michael Feathers 對 characterization test 的經典做法是：先建立 harness，執行舊系統，觀察輸出，寫出預期值，再重複這個過程擴大覆蓋範圍，詳見[Feathers 的說明](https://www.artima.com/weblogs/viewpost.jsp?thread=198296)。

ApprovalTests 的典型流程是產生 `.received` 檔，再由人檢查後改名或確認為 `.approved`；可參考[ApprovalTests Java 文件](https://github.com/approvals/ApprovalTests.Java)與[Approval Testing 概念說明](https://approvaltestscpp.readthedocs.io/en/latest/generated_docs/ApprovalTestingConcept.html)。

實務上應先正規化非穩定資料：

- 移除 timestamp、UUID、random value。
- 固定集合排序。
- 遮罩機密資料。
- 將外部服務改成 deterministic fixture。
- 對浮點數與非同步結果定義容許誤差。

若行為刻意要改變，不能直接更新 golden master 或 approval artifact；應先由產品、領域專家或 API 擁有者明確批准差異，再新增描述新行為的測試。

## 4. 大型重構的安全網

結論：Strangler Fig 負責逐步切流量，Branch by Abstraction 負責逐步替換內部供應者，Parallel Run／Dual Run 負責讓新舊實作在相同輸入下互相比對。

嚴格說，`Strangler Fig` 與 `Branch by Abstraction` 是 Fowler 明確命名的模式；`Parallel Run` 在 Fowler／Thoughtworks 的遺留系統脈絡常稱 `Incremental Dual Run`，而業界也常引用 Sam Newman 的 `Parallel Run` 命名。以下將它們視為同一組大型替換策略，但不把三者誤稱為同一篇 Fowler 文章中的固定分類。

| 模式 | 什麼時候用 | 典型做法 | 代價 |
|---|---|---|---|
| `Strangler Fig` | 可以在入口、路由或 facade 截取流量，並能按功能逐步移植 | 在舊系統外圍建立新服務；先把新功能或一小段 route 導向新系統，再逐步擴大，最後移除舊系統 | 新舊系統並存；proxy/router 可能成為瓶頸或單點；要處理資料同步、跨系統交易、監控與回退 |
| `Branch by Abstraction` | 需要替換內部 library、module、framework、database adapter 或 service provider | 先建立穩定 abstraction；讓舊實作掛在後面；逐步遷移 caller；建立新實作；用設定或 feature flag 切換；最後刪除舊實作與臨時 abstraction | 需要維護兩套 implementation、adapter、flag 與抽象層；短期增加間接性與測試矩陣 |
| `Parallel Run`／`Dual Run` | 新舊結果風險高、規格不完整，且可以對同一輸入執行兩套系統 | 舊系統繼續提供正式結果；新系統以 shadow 或非同步方式執行；比較兩者輸出與狀態；確認後逐步切換 | 計算量與基礎設施成本可能近乎加倍；副作用必須可隔離或具 idempotency；需要輸出正規化、PII 管理與差異分析 |

### Strangler Fig

Fowler 的[新版 Strangler Fig 說明](https://martinfowler.com/bliki/StranglerFigApplication.html)強調，遺留系統現代化不應假設「重寫出完全相同的新系統」很容易，因為舊系統中往往存在大量未文件化行為；較安全的方式是建立 transitional architecture，逐步替換並持續交付價值。

AWS 的[Strangler Fig 指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-decomposing-monoliths/strangler-fig.html)也列出限制：若系統無法被攔截或路由，或規模太小而不值得引入 proxy，這個模式未必適合。

### Branch by Abstraction

[Branch by Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html)的重點是：所有中間狀態都能 build、test、deploy，舊實作與新實作可在一段時間內共存。

它特別適合：

- 替換 ORM、logging framework、message broker client。
- 將單體中的一個 module 拆出。
- 替換付款、搜尋、定價等內部 provider。
- 多個團隊需要持續交付，不能長期停在 migration branch。

不要把它與 Fowler 的 `Parallel Change` 混淆：[`Parallel Change`](https://martinfowler.com/bliki/ParallelChange.html)主要是介面或 schema 的 `expand → migrate → contract`；`Parallel Run` 則是實際讓新舊系統收到相同輸入並比較執行結果。

### Parallel Run／Dual Run

Fowler 在[主機系統替換文章](https://martinfowler.com/articles/uncovering-mainframe-seams.html)中稱這種做法為 `Incremental Dual Run`：同一輸入送入舊、新系統，再比較輸出，必要時允許容許誤差。Zalando 的[實際 Parallel Run 經驗](https://engineering.zalando.com/posts/2021/11/parallel-run.html)也指出，舊系統通常先保留為 source of truth，直到新系統在真實流量與資料下證明可靠。

它不適合直接拿來處理不可重複的副作用，例如：

- 重複扣款。
- 重複寄信。
- 產生不可逆的外部交易。
- 會改變共享資料的非 idempotent command。

常見做法是 shadow traffic、只執行 read path、複製資料到隔離環境，或將 side effect 改成可去重事件。AWS 的[平行請求重播架構](https://docs.aws.amazon.com/reference-architecture-diagrams/latest/replaying-parallel-requests/replaying-parallel-requests.html)就是以錄製舊系統 request/response，再重播到新系統並比較結果。

## 5. 反模式：何時「重構」其實是重寫

結論：是否為 rewrite 不看改了多少行，而看是否有意重新實作系統、改變可觀察契約，及能否透過小步驟、測試與回退逐步交付。

Fowler 對 refactoring 的核心定義是：在不改變可觀察行為的前提下，改善程式內部結構，使未來更容易理解與修改，見[Definition of Refactoring](https://martinfowler.com/bliki/DefinitionOfRefactoring.html)。

### 流程上的辨識表

| 檢查點 | 真正的 refactoring | 偽裝成 refactoring 的 rewrite |
|---|---|---|
| 目的 | 明確聲稱外部行為不變 | 同時加入新需求、修 bug、換架構或換平台 |
| 基準 | 有 characterization、contract、integration 或 approval tests | 沒有基準，只說「新版本應該差不多」 |
| 交付方式 | 小步驟、持續 build/test、可獨立部署 | 長期獨立開發，最後一次 big-bang cutover |
| 新舊關係 | 舊實作可留在 abstraction、router 或 feature flag 後面 | 舊系統長期不動，直到最後整個替換 |
| 回退能力 | 每一階段可 revert、切回舊實作或停止路由 | 上線後只能整批回滾或資料難以還原 |
| 差異處理 | 每個輸出、API、資料與事件差異都有明確理由 | 發現差異後以「新系統比較合理」帶過 |
| 收尾 | 有 owner 和期限移除 flag、adapter、proxy、舊程式 | 臨時層永久留下，形成新的架構債 |

實務上可採用以下規則：

- 把 `refactor`、`feature`、`bugfix`、`migration` 分成不同 ticket 或 commit。
- 在開始前寫出可觀察契約：API response、錯誤、資料庫狀態、事件、排序、效能要求是否都算行為。
- 對未知的遺留行為先建立 characterization 或 golden master。
- 每個中間版本都必須能編譯、通過測試並部署。
- 大型變更保留舊實作，使用 abstraction、router、feature flag 或 dual run。
- 對預期差異建立明確批准紀錄，不要直接「更新全部 snapshot」。
- 為 transitional architecture 建立拆除任務與期限。

若出現以下情況，應在文件與管理上稱為「重寫／替換／現代化」，而不是純重構：

- 整個 module 或服務被新團隊獨立重建。
- 新舊系統直到最後才整批切換。
- 沒有既有行為基準，也沒有可重播輸入。
- 同時變更資料模型、API、使用者流程與商業規則。
- 以「功能 parity」取代具體的可觀察契約。
- 沒有逐步發布與回退路徑。
