# 1. 業界 Agentic / 分散式系統的 ID 體系比較

### 【一句話結論】
**系統分幾種 ID，取決於它有幾個不同生命週期的「邊界」；把「業務實體」、「執行調度」、「狀態快照」與「因果追蹤」混用同一個 ID，是系統難以重試、無法分叉（Branching）與回溯（Time-travel）的根源。**

---

### 五大真實系統 ID 體系對照

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 業務生命週期 (Business Boundary)      : WorkflowId / ThreadId / SessionId     │
│   └── 單次執行調度 (Execution Boundary) : RunId / ExecutionId                 │
│         └── 不可變狀態快照 (Snapshot)    : CheckpointId / StateVersion        │
│               └── 因果追蹤 (Causality)  : TraceId / SpanId / StepId          │
│                     └── 外部協定 (I/O)  : ToolCallId / TaskToken             │
└─────────────────────────────────────────────────────────────────────────────┘
```

| 系統 | 定義的 ID 類型 | 產生源與格式 | 為什麼要分開？（核心解決的具體問題） |
|---|---|---|---|
| **Temporal**<br>*(分散式調度基準)* | 1. `WorkflowId`<br>2. `RunId`<br>3. `ActivityId`<br>4. `TaskToken` | • `WorkflowId`: 業務自訂（如 `user-123-sync`）<br>• `RunId`: 系統 UUIDv4<br>• `ActivityId`: 節點唯一字串<br>• `TaskToken`: 包含前三者的 base64 payload | • **保證唯一性與重試分歧**：`WorkflowId` 保證同一個業務實體同一時間只有一個在跑；當重試或重跑時，`WorkflowId` 不變但發行新的 `RunId`，**避免重試把歷史帳本覆寫**。<br>• `TaskToken` 讓非同步工人完成後回傳，調度器能瞬間解構出上下文。 |
| **LangGraph**<br>*(狀態圖架構)* | 1. `thread_id`<br>2. `checkpoint_id`<br>3. `checkpoint_ns`<br>4. `run_id` | • `thread_id`: 外部調用者指定<br>• `checkpoint_id`: 時間單調遞增字串 / UUIDv7<br>• `checkpoint_ns`: 子圖命名空間字串<br>• `run_id`: 單次調用 UUID | • **支援 Time-Travel 與 Fork**：`thread_id` 是整條對話，每一次節點狀態變更都會產生不可變的 `checkpoint_id`。如果人要介入修改歷史（Human-in-the-loop），只需指定舊的 `checkpoint_id` 分叉出去，不影響原線。<br>• `checkpoint_ns` 解決 **子圖（Subgraph）內部節點名稱與父圖衝突** 的問題。 |
| **W3C TraceContext**<br>**& OpenTelemetry** | 1. `trace_id` (16B)<br>2. `span_id` (8B)<br>3. `parent_span_id`<br>4. `tracestate` | • 隨機 16/8 bytes 16進位<br>• 透過 HTTP Header / context 傳遞 | • **跨程序因果樹（Causal Graph）**：`trace_id` 貫穿整條鏈，`span_id` 代表單一工作單元。**只要有 parent_span_id，隨意以非同步、異步、亂序方式寫入日誌，事後都能 100% 重建 DAG 執行樹**。 |
| **OpenAI Agents / Assistants** | 1. `thread_id`<br>2. `run_id`<br>3. `run_step_id`<br>4. `message_id`<br>5. `tool_call_id` | • 官方前綴字串：`thread_xxx`, `run_xxx`, `step_xxx`, `call_xxx` | • **解耦「對話內容」與「推理狀態機」**：`message_id` 是用戶看的；`run_id` 是背景 LLM poll 狀態；`run_step_id` 紀錄「這一步是呼叫工具還是生成文字」；`tool_call_id` 供模型精確將工具 output 與 input 進行 pair 配對。 |
| **LangSmith / MLflow Trace** | 1. `trace_id` (Root Run)<br>2. `run_id` (Child Run)<br>3. `session_id` / `project_id` | • UUIDv4 / UUIDv7 | • **計費與評估聚合**：`session_id` 聚合同一用戶成本；`root_run` 聚合單次調用延遲；`child_run` 監控單一 prompt token 消耗。 |

*依據與出處：[Temporal Architecture Guide](https://docs.temporal.io/workflows#workflow-execution)、[LangGraph Persistence & Time Travel Docs](https://langchain-ai.github.io/langgraph/concepts/persistence/)、[W3C Trace Context RFC](https://www.w3.org/TR/trace-context/)*

# 2. ID 產生方式深度評選與 nova 現況診斷

### 【一句話結論】
**狀態與執行請全數採用 `UUIDv7`（兼具毫秒時序、SQLite B-tree 零裂頁、與極低碰撞率）；不可變資產（Prompt、Artifact、Chunk）全數採用 `Content-Addressed (BLAKE3/SHA-256)`；nova 現有的「時戳＋6位十六進位」在同秒並行時只要數百次就會發生碰撞，且破壞時序單調性。**

---

### ID 方案橫向評測

| 方案 | 可排序性 | 時鐘依賴程度 | 碰撞機率（數學實際數字） | SQLite 主鍵寫入行為 (B-tree) | 跨程序/無中心協調 | 適用場景 |
|---|---|---|---|---|---|---|
| **UUIDv4** | ❌ 完全無序 | 零依賴（純隨機） | $2^{122}$ 空間。產生 $2.71 \times 10^{18}$ 個才有 50% 碰撞率。 | 🔴 **極差**：隨機寫入引發頻繁 Page Split，緩存命中率低，磁碟寫入放大 2~3 倍。 | ✅ 完美 | 僅用於不需要排序的臨時 Token |
| **UUIDv7**<br>*(RFC 9562, 2024 正式標準)* | ✅ **毫秒字典序單調** | 依賴毫秒時鐘（有防回撥機制） | 48-bit 時戳 + 12-bit 序列 + 62-bit 隨機。同毫秒產生 4096 個仍保證嚴格遞增且無碰撞。 | 🟢 **最優**：全順序追加（Append-only），B-tree 填充率 > 90%，零頁分裂。 | ✅ 完美（原生支援分散式） | **執行、狀態、Event、Checkpoint 首選** |
| **ULID** | ✅ 毫秒可排 (Base32) | 依賴毫秒時鐘 | 48-bit 時戳 + 80-bit 隨機。同毫秒 80-bit 隨機。 | 🟢 **優**：表現同 UUIDv7，但 26 字元 Base32 比 UUID 字串短。 | ⚠️ 跨程序同毫秒無法共享 entropy 遞增 | 需短網址/人類可讀性高的場合 |
| **KSUID** | ⚠️ 秒級可排 (Base62) | 依賴秒級時鐘 | 32-bit 秒時戳 + 128-bit 隨機（長度 27 字元）。 | 🟡 **中**：秒內無序，同一秒內的插入依然會造成局部的 B-tree 抖動。 | ✅ 良好 | 日誌系統（Payload 偏大：20 bytes） |
| **Snowflake**<br>*(Twitter/Sony)* | ✅ 嚴格單調遞增 | 🔴 **高度依賴**（時鐘回撥會拋錯或停機） | 41-bit 時戳 + 10-bit Worker ID + 12-bit 序號（64-bit int）。 | 🟢 **最優**（整數比字串更省空間與索引）。 | 🔴 **極差**：跨程序必須有 Worker ID 協調器（ZooKeeper/Redis）。 | 大型分散式高並發集中叢集 |
| **Content Hash**<br>*(SHA-256 / BLAKE3)* | ❌ 無時序 | 零依賴 | $2^{256}$ 空間，密碼學抗碰撞。 | 🔴 隨機，但做 Key-Value 查詢極快。 | ✅ 完美 | **Artifact、Chunk、Snapshot 去重** |

---

### nova 現狀診斷：`20260830T012847Z-38fb89`

nova 目前的設計為：**秒級 ISO8601 時戳 ＋ 6 碼十六進位（24 bits 隨機）**。

#### 1. 什麼規模與情境下會出事？（碰撞數學）
* 24-bit 的隨機空間總量為 $N = 16^6 = 16,777,216$。
* 根據生日悖論近似公式 $P \approx 1 - e^{-\frac{k^2}{2N}}$：
  * **當同一秒內有 180 個並行任務**：碰撞機率達到 **$0.1\%$**（千分之一）。
  * **當同一秒內有 580 個並行任務**：碰撞機率達到 **$1.0\%$**。
  * **當同一秒內有 4,800 個並行任務**：碰撞機率達到 **$50\%$**。
* **致命情境（不需要等到 580 個並行）**：
  1. **Fan-out 併發**：當 Graph 引擎進行 Fan-out，在 10 毫秒內同時啟動 20 個 Subagent，這 20 個 agent 共享同一個秒級時戳。此時只要隨機數生成器的種子（seed）受到 Python `fork` 或事件迴圈複用影響，碰撞率會劇烈飆升。
  2. **檔案覆寫事故**：nova 將其作為「帳本檔名」，一旦碰撞，`open(..., 'w')` 或 append 就會將兩個完全不同的 Agent 執行記錄寫入同一個檔案，造成**執行狀態相互污染、帳本直接損毀**。

#### 2. 時序破壞問題
* 在同 1 秒內產生的多個執行：
  * 檔案 A: `20260830T012847Z-ff0012`
  * 檔案 B: `20260830T012847Z-00a123`
  * `ls` 或字串排序時，後生的 B 會排在先生的 A 前面。**它失去了「秒內單調性」**。

# 3. 圖（Graph）引入後的 ID 體系與 Fan-out/Join 證據鏈

### 【一句話結論】
**圖的靜態拓撲用語意字串，動態實例用複合鍵，不可變快照用 UUIDv7；Fan-out / Join 的證據追溯必須採用 Content-Addressed DAG，將「結論」與「引用的原始 Finding ID 陣列」以因果邊（Lineage Edge）綁定。**

---

### 圖執行所需的 ID 矩陣

```
[Graph Definition (Static)]
  └── node_id: "extractor", "synthesizer"
  └── edge_id: "extractor->synthesizer"

[Graph Execution (Dynamic)]
  └── execution_id (UUIDv7)
        └── branch_id (fork-index / hash): 隔離並行狀態
              └── step_id / attempt_id: (複合鍵: execution_id:branch:node:attempt)
                    └── checkpoint_id (UUIDv7): 不可變狀態快照
```

| ID 種類 | 形狀建議 | 缺它的後果（具體壞事） | 能否用複合鍵取代？ |
|---|---|---|---|
| `node_id` | 靜態字串（如 `fetch_doc`） | 無法定義圖拓撲，代碼無法指定執行邏輯。 | 否（靜態拓撲基礎） |
| `branch_id`<br>*(或 checkpoint_ns)* | 字串/雜湊（如 `branch-0`, `sub-analyzer-a`） | **Fan-out 時狀態覆蓋**：兩個並行節點同時寫入 state 的同一個 key，後完成的把先完成的洗掉（Race Condition）。 | 可以：由 `fanout_idx` 或 `parent_step_id` 派生。 |
| `attempt_id` | 整數 `1, 2, 3...` | **Self-Correction 混淆**：節點 Reflection 重試時，第 1 次失敗的 log 與第 2 次成功的 log 混在同一帳本，無法計算單次重試成本。 | **可以**：使用複合鍵 `(run_id, node_id, attempt)`。 |
| `checkpoint_id` | `UUIDv7` | **無法 Time-Travel 與中斷重啟**：當節點 5 當機，系統不知道節點 4 的確切 State 記憶體鏡像為何，只能從頭重跑。 | 否（狀態快照必須全局不可變唯一）。 |
| `artifact_id` | `Content-Hash` (BLAKE3) | **重複儲存與資產漂移**：Subagent 重複生成相同檔案時浪費空間，或檔案內容變了但引用者不知道。 | 否（必須用內容定址保證不可變性）。 |

### 3b. Fan-out / Join 證據追溯數據模型 (`sourceFindingIds`)

當 10 個 Worker 並行分析並各自產出 findings，最後由一個 Join 節點 Synthesize 出結論時，資料模型必須是 **以 Finding 為節點的 DAG（有向無脊圖）**。

#### 資料模型架構（以 SQLite / JSON 結構表達）

```sql
-- 1. 證據實體表（不可變）
CREATE TABLE findings (
    finding_id TEXT PRIMARY KEY,        -- 建議: "fnd_" || substr(sha256(canonical_json(content)), 1, 16)
    execution_id TEXT NOT NULL,         -- 所屬執行 (UUIDv7)
    branch_id TEXT NOT NULL,            -- 產出分支 (Fan-out 識別)
    node_id TEXT NOT NULL,              -- 產出節點
    content TEXT NOT NULL,              -- 事實描述 / 結構化 JSON
    raw_evidence_quote TEXT,           -- 原始文件摘錄
    confidence REAL,                    -- 信心度 (0.0 ~ 1.0)
    created_at TEXT NOT NULL
);

-- 2. 證據因果追溯表 (Lineage / Provenance Edges)
CREATE TABLE finding_lineage (
    derived_finding_id TEXT NOT NULL,   -- Join 節點產出的結論 ID
    source_finding_id TEXT NOT NULL,    -- 被引用的原始 Finding ID
    contribution_weight REAL,           -- 貢獻權重 (可選)
    PRIMARY KEY (derived_finding_id, source_finding_id),
    FOREIGN KEY (derived_finding_id) REFERENCES findings(finding_id),
    FOREIGN KEY (source_finding_id) REFERENCES findings(finding_id)
);
```

#### JSON Payload 呈現範例
```json
{
  "finding_id": "fnd_7a8b9c1d2e3f4a5b",
  "node_id": "synthesizer_join",
  "statement": "系統在週六凌晨 02:00 遭遇記憶體洩漏並觸發 OOM。",
  "sourceFindingIds": [
    "fnd_1111aaaa2222bbbb", // 來自 worker-1: 日誌發現 OOMKilled
    "fnd_3333cccc4444dddd"  // 來自 worker-2: 監控指標顯示 01:55 記憶體攀升
  ],
  "lineage_depth": 2
}
```
**優勢**：若審計時懷疑結論，可沿著 `finding_lineage` 遞迴查詢（CTE Recursive Query），一直回溯到最底層的 Raw Log 檔名與行號。

# 4. RAG 的 ID 階層與「引用過期（Stale Chunk）」解法

### 【一句話結論】
**RAG 的核心原則是「檢索與生成永遠綁定不可變版本（Commit Hash / Content Hash）」；解決引用過期絕對不能靠原地更新（In-place Overwrite），而是採用 Git 式的 Immutable Snapshot 或 Bi-temporal（雙時態）標記。**

---

### RAG ID 階層設計

```
Document (邏輯實體) : doc_id = "wiki/architecture.md"
  └── Doc Version (不可變快照) : doc_version_id = git_hash 或 sha256(content)
        └── Chunk (文字片段) : chunk_id = sha256(doc_version_id + chunk_index + chunk_text)
              └── Embedding (向量) : vector_id = sha256(chunk_id + model_name + embedding_params)
```

---

### 避免「答案引用被改掉的 Chunk」：三種業界作法與代價

| 機制 | 運作原理 | 優點 | 代價與缺點 | 適用規模 |
|---|---|---|---|---|
| **1. 內容定址快照**<br>*(Git-like Content Addressed)* | `chunk_id` 由內容 Hash 決定。文件修改後產生全新 `chunk_id`，舊 chunk 不刪除（留在向量庫）。Agent 生成時附帶引用的 `chunk_id`。 | **絕對一致性**：無論文件怎麼改，歷史 Agent 回答中的引用鏈永遠能 100% 重現當時看到的原文。 | **儲存膨脹**：向量庫空間持續增長，需定期執行垃圾回收（GC，刪除無任何 Run 引用的孤兒 chunk）。 | **極高可靠性要求**<br>（法規、審計、科研） |
| **2. 軟刪除 ＋ 讀取校驗**<br>*(Tombstone & Read Validation)* | 更新文件時，舊 chunk 被標記 `deleted_at = timestamp`。Agent 檢索只撈 `deleted_at IS NULL`。若 Agent 在生成瞬間發現 chunk 被標記刪除，阻斷回答並重新檢索。 | 儲存可控，容易做即時過濾（Metadata filter: `active: true`）。 | 若更新頻繁，長任務 Agent 可能在 Join/Synthesize 階段發生 **一致性中斷（Consistency Breach）**，迫使整個流程 Retry。 | **中小型業務系統** |
| **3. 原地刪除覆寫**<br>*(Hard Overwrite / Upsert)* | 依賴 `doc_id + chunk_index` 做主鍵，直接 `UPSERT` 覆蓋舊向量。 | 最省空間，實作最簡單。 | 🔴 **致命災難**：Agent 檢索時拿到版本 A，生成到一半文件被覆寫成版本 B，最後產出的答案包含「版本 A 的推論」但「引用的 URL/內容卻是版本 B」，產生無法排查的幻覺。 | **玩具原型專案** |

**給 nova 的建議**：採用 **方案 1（Content Hash）＋ 弱引用 GC**。
向量 metadata 寫入：`{ "doc_id": "auth.md", "doc_version": "a3f89e", "chunk_hash": "c78b..." }`。回答永遠引用具體的 `chunk_hash`。

# 5. 何時從 Append-only JSONL 遷移至 SQLite？

### 【一句話結論】
**當「單次排程需跨多個執行做狀態比對」、「目錄檔案數突破 3,000」或「出現多程序並行寫入狀態」的瞬間，就是必須切換到 SQLite 的鐵律門檻；在 WAL 模式與 `busy_timeout` 設定下，SQLite 能完美承載每 15 分鐘排程與人工並發寫入，徹底解決 JSONL 跨檔案無事務（Transaction）的隱患。**

---

### 具體遷移觸發條件（Trigger Thresholds）

| 維度 | JSONL 極限值（該搬家的臨界點） | 抵達極限時發生的具體症狀 |
|---|---|---|
| **執行次數 / 檔數** | **> 3,000 個檔案** | 在 macOS / Linux 上，`ls` 或目錄掃描的 inode lookup 延遲從 5ms 暴增至 **200ms~500ms**，CLI 啟動感知明顯卡頓。 |
| **查詢形態** | **點查（Point Lookup）與分頁（Pagination）** | 想要看「最近 20 筆失敗的執行」，JSONL 必須 `stat` 全部 3,000 個檔案並逐一打開讀取尾行，磁碟 I/O 飆高；SQLite 帶索引查詢只需 **0.2ms**。 |
| **關聯查詢** | **跨執行狀態檢索** | 例如：「找出所有包含 `fnd_xxx` 的歷史執行」——JSONL 需執行全文 `grep`，耗時數秒並吃滿 CPU。 |
| **並行寫入** | **> 1 個 Process 同時運行** | 當每 15 分鐘的 CronJob 正在跑，工程師手動觸發一次 CLI，兩者若需寫入全域狀態（如專案索引、收件箱消耗），JSONL 無法提供跨檔案的原子性（ACID），**必然發生重複收件（Double Processing）**。 |
