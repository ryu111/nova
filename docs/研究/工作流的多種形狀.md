### 1. 業界 Agent 工作流框架如何表達「一種工作流」（資料結構與型別系統）

* **結論一句話**：現代框架對工作流的表達光譜，從「靜態 DAG 與確定性 Saga（Airflow/Prefect/Temporal）」走向「帶有 Reducer 狀態通道的有向循環圖（LangGraph）」與「事件驅動的多角色拓撲（AutoGen/CrewAI）」，核心分歧在於**狀態不可變性 vs. 動態累加性**以及**控制流是否允許非確定性循環**。
* **各家型別系統與資料結構**：
  * **LangGraph**：`StateGraph[StateT]` ➔ 編譯為 `CompiledGraph`。狀態 Schema 採用 `TypedDict` 或 `pydantic.BaseModel`，搭配通道 Reducer（如 `Annotated[list, operator.add]`）；節點為 Callable `(state, config) -> dict`，邊為靜態邊 (`add_edge`) 或條件邊 (`add_conditional_edges`) 支援循環。
  * **CrewAI**：`Crew` 類別封裝 `agents: List[Agent]`、`tasks: List[Task]`、`process: Process`（`sequential` 或 `hierarchical`）。Task 透過 `context: List[Task]` 與 `output_pydantic: Optional[Type[BaseModel]]` 定義資料依賴。
  * **AutoGen (v0.2 / v0.4)**：v0.2 核心為 `GroupChat`（共享 `messages: List[Dict]`）+ `GroupChatManager`；v0.4 轉為事件驅動 Actor 模型（`AgentRuntime`、`TopicId`、`MessageContext`、`RoutedAgent`，支援 `RoundRobinGroupChat`、`SelectorGroupChat`、`Swarm`）。
  * **Temporal**：`@workflow.defn` 配合 `@activity.defn`，狀態依賴確定性事件溯源歷史（Event History），透過 Replay 保證一致性，**嚴禁非確定性隨機與無約束循環**。
  * **Prefect**：`@flow` 與 `@task` 動態構建 Task Graph，型別系統依賴 `PrefectFuture[T]` 與運行時狀態枚舉（`Pending`, `Running`, `Completed`, `Failed`）。
  * **Airflow**：靜態 `DAG` 物件包含 `BaseOperator` 節點，透過 `>>` 連接，資料透過 `XCom` 序列化傳遞，**嚴禁圖內循環（Cycle-free）**。
  * **Anthropic 6 Patterns**（*Prompt Chaining*, *Routing*, *Parallelization*, *Orchestrator-Workers*, *Evaluator-Optimizer*, *Autonomous Agent*）：以原生 Python 控制流（`while`, `for`, `if-else`）、函數簽章與 Pydantic Schema 表達，不依賴厚重框架。

### 2. 「角色（Agent Role）」的工廠化設計與代價

* **結論一句話**：角色工廠設計應採用「**Protocol 規範行為契約 + Pydantic Schema 定義能力宣告 + Builder/Registry 實現運行時裝配**」，避免單純依賴 Decorator 或無型別檢查的 YAML 設定檔。
* **常見做法與代價分析**：
  1. **設定檔驅動（YAML / JSON）**（如 CrewAI `agents.yaml`）：
     * *做法*：Prompt、角色目標、工具名寫在 YAML，工廠動態載入。
     * *代價*：無編譯期靜態檢查，工具依賴若名稱拼錯只能在運行時報錯，Schema 升級維護成本高。
  2. **裝飾器模式（Decorator）**（如 `@agent`, `@task`）：
     * *做法*：在類別方法上加上裝飾器由框架元編程自動註冊。
     * *代價*：隱藏依賴注入（DI）邏輯，難以在運行時動態生成同一角色的多個變體。
  3. **Protocol / 抽象基類（ABC）**（如 `typing.Protocol` / LangChain `Runnable`）：
     * *做法*：定義 `async def step(self, ctx: Context) -> StepResult` 行為介面。
     * *代價*：需撰寫較多 boilerplate 代碼，但具備**靜態型別安全與最佳可測試性**。
  4. **Fluent Builder 模式**（如 `AgentBuilder().with_role(...).build()`）：
     * *做法*：鏈式 API 注入 LLM、Tools、Budget 與 Hook。
     * *代價*：需維護較多 Builder 方法，但防呆與可觀測性最強。

### 3. 無機械判準工作流的終止機制與具體數字

* **結論一句話**：無測試可綠的研究型工作流，終止機制必須由「**硬性防護底線（步數 / Token 預算）**」與「**語義收斂判準（Evaluator Rubric 評分 + 邊際效益遞減）**」構成多層防禦，絕對不可單純依賴 LLM 自行決定退出。
* **主流框架停止機制與官方預設值**：
  * **LangGraph**：`recursion_limit`（單次圖執行的 superstep 節點上限），官方預設值為 **`25`**；超出時拋出 `GraphRecursionError`。
  * **CrewAI**：`Agent.max_iter` 官方預設值為 **`25`**（舊版為 20）；`max_retry_limit` 預設為 **`2`**；`max_execution_time` 預設為 **`None`**。
  * **AutoGen (v0.2 / v0.4)**：v0.2 的 `max_consecutive_auto_reply` 預設為 `None`（委派類別常數，實務常設 10~30）；v0.4 透過複合條件 `MaxMessageTermination(max_messages=25) | TextMentionTermination("TERMINATE") | TimeoutTermination(300)`。
* **研究型工作流的實務終止策略**：
  1. **硬性底線**：步數上限 `max_steps = 25`、Token 上限 `100k`、逾時 `300s`。
  2. **Evaluator 評分門檻**：獨立 Evaluator Agent 針對準則（完整性、可靠性、矛盾消除）評分 $\ge 4.0 / 5.0$ 即退出。
  3. **邊際效益遞減（Delta Convergence）**：連續 2 輪搜尋筆記資訊增量低於閾值即判定飽和退出。
  4. **Human-in-the-Loop (HITL) 中斷**：超過 15 步未收斂時主動拋出確認中斷點。

### 4. 判準指令執行失敗 vs 測試紅（Infra vs. Test Failure）

* **結論一句話**：把「指令跑不起來（退出碼 127/126/3/4）」當成「測試紅（退出碼 1）」是 Agent 系統最嚴重的經典反模式，會導致 LLM 誤以為業務邏輯錯誤而胡亂修改代碼引發連鎖崩潰；工業界標準解法是**狀態三元化（PASS / FAIL / ERROR）**並**強制解析結構化測試報告（如 JUnit XML）**而非單看 `$? != 0`。
* **退出碼語義標準**：
  * **Pytest 退出碼**：
    * `0` (`ExitCode.OK`)：測試全過（Green）。
    * `1` (`ExitCode.TESTS_FAILED`)：測試有斷言失敗（標準 Red，可交由 Agent 修復代碼）。
    * `2` (`ExitCode.INTERRUPTED`)：執行被中斷（SIGINT）。
    * `3` (`ExitCode.INTERNAL_ERROR`)：pytest 本身或 plugin 崩潰（環境錯誤）。
    * `4` (`ExitCode.USAGE_ERROR`)：命令列參數或配置檔錯誤（配置錯誤）。
    * `5` (`ExitCode.NO_TESTS_COLLECTED`)：找不到任何測試（路徑或模式比對錯誤）。
  * **POSIX Shell 退出碼**：
    * `126`：Command invoked cannot execute（無執行權限）。
    * `127`：Command not found（二進位檔缺失、PATH 錯誤、虛擬環境未啟用）。
    * `128 + N`：被 Signal 殺死（如 `137` 為 OOM killer SIGKILL，`143` 為 SIGTERM）。
* **業界防禦做法**：
  * **三元狀態判定**：`PASS`（綠燈）/ `FAIL`（業務紅燈，反饋給 Coding Agent）/ `INFRA_ERROR`（環境紅燈，由環境修復模組接管或阻斷，嚴禁餵給業務 Prompt）。
  * **解析 JUnit XML**：檢查 `<testsuite tests="N" failures="F" errors="E">`，確認 `tests > 0` 且 `failures > 0` 才視為 Red。
* **出處連結**：

  * [GNU Bash Exit Status](https://www.gnu.org/software/bash/manual/html_node/Exit-Status.html)

### 5. Graph Engineering 的現代定義與 Workflow Orchestration 差異

* **結論一句話**：Workflow Orchestration 處理的是「**確定性、無循環、以資料管道與交易補償為核心的線性排程（Static DAG）**」；而 Graph Engineering 處理的是「**非確定性、高度循環、以狀態通道 Reducer 與語義分流為核心的自適應狀態機（Cyclic State Graph）**」。
* **核心差異對比**：
  * **拓撲形狀**：Orchestration 依賴 DAG（禁止圖內 Cycle，如 Airflow 會拋出 `AirflowDagCycleException`）；Graph Engineering 本質即為 Cyclic Graph（生成-反思-修正循環）。
  * **控制流機制**：Orchestration 由確定性代碼（`if-else`、Cron、資料事件）驅動；Graph Engineering 由 **LLM 語義決策與 Tool Calling** 驅動。
  * **狀態流轉**：Orchestration 是節點間 I/O 參數傳遞與 XCom 序列化；Graph Engineering 是 **State Channels**（支援自定義 Reducer 與黑板模式）。
  * **人機協同**：Orchestration 為靜態審批閘道；Graph Engineering 具備 **時光旅行（Time-Travel）**、狀態編輯重播（State Forking）。
