# 官方套件的角色與工作流參數

## 一、角色的參數集（34 份 agent 定義統計）

| 欄位 | 出現次數 | 意思 | nova 有嗎 |
|---|---|---|---|
| `name` | 31 | 識別碼，別的 agent 靠它呼叫 | ✗ 角色沒有名字，只有 Python 變數名 |
| `description` | 31 | **什麼時候該派它、誰派它** | ✗ |
| `model` | 23 | 哪顆模型 | ✓ 派工表的 `模型` |
| `tools` | 22 | 能用什麼工具，**含能呼叫哪些子 agent** | 部分：`權限` 只有唯讀／可編輯／全開三級 |
| `color` | 19 | 顯示用 | ✗（也不需要） |
| `effort` | 7 | **思考深度** | ✗ **在派工表外面**——這正是 fable 被我打成 `max` 的那個坑 |
| `initialPrompt` | 1 | 起手指令 | ✓ 角色提示 |

`name` 與 `description` 是唯二每份都有的。**`description` 是給派工者讀的，不是給角色自己讀的**
——它回答「什麼時候輪到你」，而不是「你要做什麼」。nova 的角色現在沒有這一格，
所以「哪個角色該上場」只能寫死在階段表裡。

### `model: inherit` 是最常見的取值（11 次，多於 sonnet 的 8 次）

繼承呼叫者的模型。nova 沒有這個概念——派工表要嘛指名要嘛用該家預設。
「跟派我的人用同一顆」在扇出時是有意義的預設：主辦者升級模型，
底下的節點跟著升，不必逐格改表。

### `effort` 只出現 7 次，但取值幾乎都是 `xhigh`（6 次）、一次 `medium`

那唯一的 `medium` 是 `scan-inventory`——**普查用的便宜節點**。
也就是說深度不是全域旋鈕，是**每個角色自己的**：
掃目錄結構用 medium，找漏洞用 xhigh。

## 二、組裝的機制：`tools` 裡可以放 `Agent(...)`

```
claude-security（主辦，opus / xhigh）
  tools: … Workflow(claude-security:scan)
         Agent(scan-inventory, scan-researcher, scan-verifier,
               patch-generator, patch-verifier, explore)

scan-researcher   tools: … Agent(claude-security:explore)
scan-verifier     tools: … Agent(claude-security:explore)
patch-generator   tools: … Agent(claude-security:explore)
patch-verifier    tools: … Agent(claude-security:explore)
```

**`explore` 被四個不同的節點共用。** 它是唯讀探索器（sonnet／xhigh，
只有 Read／Glob／Grep／Bash），誰都能叫。這就是使用者說的
「每一個節點都應該可以單拆出來使用，而且都能隨時組裝」的現成範例：

- **能力邊界寫在 `tools` 上**，不是寫在提示裡——呼叫者拿不到沒被列出的東西
- **組裝是資料不是程式碼**：一行 `Agent(a, b, c)` 就是這個節點能組裝誰
- **有些節點刻意不給單獨叫**：`description` 明寫 `not for direct invocation`、
  `dispatched by the fix job` —— 可組裝不等於每個都該當入口

## 三、工作流的形狀：`claude-security:scan` 的六階段

```
Inventory     把 repo 切成 component；每個頂層目錄要嘛掃要嘛明講跳過
Threat model  一個 component 一個建模者                      ← 扇出（資料決定 N）
Research      component × category 的每一格一個研究者          ← 扇出（矩陣相乘）
Sweep         補矩陣沒覆蓋到的                                ← completeness critic
Panel         三個視角各一票的對抗驗證                         ← 對抗（視角相異，不是三個一樣的）
Adversarial   只有 max 才跑：邊緣案例重審、對每個倖存者紅隊     ← 深度改變圖的形狀
```

跟使用者的 `研究型 worker(搜尋:[]llm, 對抗:[]llm, 整合:[]llm)` 是同一個形狀，
但有三件事更精細：

1. **扇出的 N 是資料決定的**，不是寫死的數字。維度可以相乘（component × category）
2. **對抗是「多視角」不是「多份一樣的」**。三個 voter 各拿一個 lens，
   redundancy 抓不到的失敗模式靠 diversity 抓
3. **`effort` 是工作流的參數，而且會改變圖**：`max` 才啟用第六階段。
   深度不只是「想多深」，它決定**要不要多跑一輪**

### 單獨叫的失敗模式，它處理了

沒給 args 就被叫起來時，它不亂猜，回一個明確的結構：

```
{ started: false, reason: "no-args",
  next: "……告訴使用者去跑 /claude-security 開選單，
         不要重新叫這個工作流，也不要自己手工做一次" }
```

**「不要重跑」寫在回傳值裡**，跟 nova 的退出碼 3（結果未知，腳本不准重跑）
是同一個設計——但它多給了一句「該做什麼」，而 nova 現在只給碼。

## 四、nova 缺的四格（照這份對照出來的）

| 缺什麼 | 現況 | 代價 |
|---|---|---|
| 角色的 `name` 與 `description` | 角色是三個字串常數 | 「哪個角色該上場」只能寫死在階段表 |
| 每個角色自己的 `思考深度` | 深度是 CLI 旗標，派工表管不到 | 我手打 `max` 派 fable，使用者說 high 就夠 |
| `model: inherit` | 要嘛指名要嘛用該家預設 | 升級主辦者的模型，底下不會跟著升 |
| 能力邊界比 `權限` 更細 | 唯讀／可編輯／全開三級 | 給不了「只能 Read/Glob/Grep」這種節點 |

**第二格最急**，因為它已經花掉錢了。
