# 一、七個錯各自的治本

## 判準與合併原則

本答案只把「包住執行者、違反時會失敗」的程式碼當成治本；文件或 skill 裡的提醒不算。文件若宣稱會自動擋下，把關器本身還必須有測試背書；用規避換來的綠仍是假綠。（`CLAUDE.md:81-94`）

現行硬規則要求新增保證時做一次固定負控並登記到 `docs/負控紀錄.md`，但又明定那些負控「不必重跑」；因此登記完成後，沒有持續執行的保證。（`CLAUDE.md:120-122`）

七錯不會拆成七套互不相干的修補，應分成四個共用治本：A／B 是同一個 CLI 入口的兩種語意洩漏；C／D／E 是同一個「負控只被宣稱、沒有執行」的病；F 是該負控執行器必須一併驗證的「測試是否真的走過破壞點」；G 則需要執行者外層的退出狀態閘，不能靠 shell 使用提醒。（A／B 同檔、C／D／E 的事實鏈見 `今晚的錯誤清單.md:5-67`；F／G 見 `今晚的錯誤清單.md:69-80`。）

### 已查實：A 與 B 雖同檔，根因不同

**A 的根因是「專案鍵被重算」，不是 `--工作目錄` 沒有生效。** 剖析器把 `--工作目錄` 定義成「在哪裡工作」，真正執行也確實用 `在哪跑(參數.工作目錄)`；但取題與手動入列用 `在哪跑(None)`，預設事件帳本也用 `在哪跑(None)`，成果帳本再獨立用一次 `在哪跑(None)`。鎖又是從那個錯的成果目錄推出來。因此同一輪同時存在「工作專案」與「行程 cwd 專案」兩個答案。（`src/nova/載體/剖析器.py:210-227`；`src/nova/載體/命令列.py:505-513,810-827,839-865,897,910-912,946-958,1104-1108`）

現有 CLI 驗收測試把啟動 cwd 與 `--工作目錄` 都設成同一個 `專案`，所以不可能看見 A；收件驗收、成果帳驗收與鎖驗收都是這個佈景。（`tests/驗收/test_收件檔就是派工.py:21-29,41-63`；`tests/驗收/test_成果帳本.py:24-32,48-65`；`tests/驗收/test_排程不會疊在一起.py:26-34,49-67`）

**B 的根因是把兩個正交概念塞進同一個布林值。** `從收件匣` 原本只描述題目來源；`nova 跑` 先落檔後把它設為 `True`。撞鎖分支卻拿同一值推論「這是排程」，因此手動 `nova 跑` 被當成排程回 0。（`src/nova/載體/命令列.py:810-827,839-886`）

而且 B 不是單純少一支測試：既有 `test_撞到鎖時題目要留在佇列上` 明確斷言手動 `nova 跑` 撞鎖應回 0；另一檔只測「沒有 `--從收件匣` 的手動工作流回 2」，完全沒覆蓋 `nova 跑` 這個組合。（`tests/驗收/test_你敲就是一次事件.py:108-128`；`tests/驗收/test_排程不會疊在一起.py:70-102`）路線圖本身反而明寫「排程回 0、人手動下的回 2」，所以目前是文件宣稱與執行中的測試互相矛盾。（`docs/路線圖.html:269-285`）

**A 的治本應是一個不可變的「專案執行脈絡」型別，加一支故意讓 cwd 與目標不同的驗收測試。** `主程式` 只准從 `參數.工作目錄` 解一次 `根`；型別內一次導出收件匣、事件帳、成果帳、鎖與狀態路徑，工作流後段只收這個脈絡，不再各自拿 `argparse.Namespace` 呼叫 `在哪跑(None)`。這不是抽象潔癖：目前 `在哪跑(None)` 的明定語意就是 cwd，而專案識別又由絕對路徑雜湊，所以每重算一次就可能換專案鍵。（`src/nova/載體/判準.py:88-90`；`src/nova/載體/帳本.py:133-160`）驗收要從「控制 worktree」啟動，明給另一個 `--工作目錄 目標worktree`，並同時斷言題目只在目標匣、鎖只擋目標、兩本帳與狀態都只落目標鍵；少任一格就讓測試紅。這一支覆蓋的正是現在散落的錯誤重算點。（`src/nova/載體/命令列.py:505-513,810-827,839-865,891-912,946-1008,1026-1045,1104-1108`）

**B 的治本是把「題目來源」與「誰喚醒這輪」拆成兩個型別。** 收件檔已經有 `typed/file/schedule/mcp`，而註解明定那是「誰造了檔」，不是「誰撿起它」；因此不能再拿 `從收件匣` 推導喚醒者。（`src/nova/載體/收件.py:43-46,72-90`）新增 `喚醒來源.人手／排程`（或等價 enum），由排程 plist 明傳 `排程`，`nova 跑` 明傳 `人手`；撞鎖只看這個 enum。排程現在只傳 `工作流 --從收件匣`，沒有任何正交的喚醒來源可辨。（`src/nova/載體/排程.py:198-212`）驗收矩陣至少要釘三格：排程＋收件匣撞鎖回 0、手動 `工作流 --從收件匣` 回 2、手動 `跑` 回 2 且票仍在。這會推翻目前那支錯誤地期待 0 的測試，而不是新增一支互相矛盾的測試。（既有錯誤期望：`tests/驗收/test_你敲就是一次事件.py:108-128`；目前只釘住前兩種舊組合：`tests/驗收/test_排程不會疊在一起.py:70-102`。）

### G：nova 沒算錯退出碼；錯的是 pipeline 的執行者與觀測邊界

`主程式` 會回 handler 的整數，`python -m nova` 也確實 `sys.exit(主程式())`；console script 則直接指到 `主程式`，由產生的 launcher 處理回傳值。（`src/nova/載體/命令列.py:1500-1507`；`src/nova/__main__.py:11-16`；`pyproject.toml:9-12`）但 Bash 沒開 `pipefail` 時，pipeline status 定義就是最後一個 command 的 status，所以 `nova … | tail -40` 的 0 是 tail 的 0；子程序 nova 無權改父 shell 對整條 pipeline 的判決。[GNU Bash pipeline 官方定義](https://www.gnu.org/software/bash/manual/html_node/Pipelines)

今晚那條 pipeline 只在當時對話／記憶，repo 裡的 production caller **查不到**；能引用的證據只有錯誤清單。（`今晚的錯誤清單.md:77-80`）因此 **G 的完整治本不在 nova 內，而在擁有 shell 的 command executor**：它必須一律用 `set -o pipefail` 執行 pipeline，或用該 shell 的 per-command status 取 nova 那一段，再以它作自己的狀態。這個外層 wrapper 才是「包住執行者」的閘；驗收要真的跑「左段回 4、`tail` 回 0」並要求 wrapper 回 4，拿掉 `pipefail` 時該測試必紅。

repo 現有 hook 已用 `|| exit 2` 包住 nova，沒有經過會吞碼的 pipeline，是正確形狀；負控紀錄也證明拿掉它會 fail-open。（`.claude/settings.json:5-11`；`docs/負控紀錄.md:225-226`）但今晚 ad-hoc command executor 的外層檔案查不到，故修改檔與確切成本都**查不到**；不能假裝改 `src/nova/` 就治好了 repo 外的 shell。nova 額外在 stderr 印 `NOVA_EXIT=<n>` 可以改善可觀測性，但它既不會讓 pipeline 失敗，也包不住誤判者，依本題判準只是補償訊號，**不算治本**。（兩個現行入口都只回／傳遞狀態：`src/nova/__main__.py:11-16`；`src/nova/載體/命令列.py:1500-1507`。）

# 二、C／D／E：把「宣稱的負控」變成會執行的閘

## 現況不是「閘還不夠強」，而是負控根本不在執行圖上

`docs/負控紀錄.md` 自己把現制稱為「手工版的 mutation testing」，並明寫 `cosmic-ray`／`mutmut` 尚未導入；它的操作契約仍是人手改壞、親眼看紅、再改回來。（`docs/負控紀錄.md:1-12`）現有機械檢查只用正規式抽出文件裡的 `test_*` 名字，再確認 repo 中存在同名函式；它沒有改 production code，也沒有執行被點名的測試。（`tests/驗收/test_文件即事實.py:23-31,34-45,88-96`）CI 規則表也只有 pytest／ruff／mypy 等規則，沒有負控 runner。（`src/nova/載體/規則表.py:152-259`）因此 E 的直接根因已查實：**紀錄可被檢查「寫得像真的」，不可被檢查「真的殺得掉變異」。**

檔案現況也和題目中的「九節」不同：目前有一張從第 16 行開始的大表，另有 18 張表，表頭落在第 457、486、519、573、594、617、650、669、709、736、776、811、826、848、874、903、938、963 行；機械計數共 325 個資料列。這表示「一次把舊散文全轉完」本身已是遷移專案，不能藏在導工具的工時裡。（`docs/負控紀錄.md:16-260,457-963`；325 是逐行排除表頭與 `|---|` 後的本研究計數。）

## C 與 D 是同一種測試品質洞，但不是同一個測試案例

C 的兩條接線本來都會落回恰好相同的供應商預設：例行在派工表是 `high`、推理是 `max`，而角色工廠少傳一格時，下游仍會用預設，故 argv 比對是假綠。（`src/nova/載體/派工表.py:27-30`；`src/nova/迴圈/角色工廠.py:35-46`；成因與後來補的非預設 sentinel 見 `tests/單元/test_角色工廠.py:145-173`。）直接守下一個接縫的測試其實早已存在，但它只守 `固定提示角色 → 呼叫選項`，守不到新插入的 `角色藍圖 → 固定提示角色` 接縫；這也解釋了 F 為何點到它才是對路。（`src/nova/載體/角色.py:43-53`；`tests/單元/test_角色.py:81-84`）

C 的兩個症狀要用同一原則、各守自己的 seam：角色工廠已有 `xhigh`／不存在型號的 sentinel；`nova 問` 那一半則應讓測試注入一筆同樣非預設的 `派法`，再斷言第 413 行收到那個值。這不必、也不應為測試去改 production 派工策略；可注入的是第 490 行查表的回傳值，真正要守的是第 413 行的轉遞。（`src/nova/載體/命令列.py:477-495,409-418`；策略不可為測試改值的既有裁定：`docs/負控紀錄.md:917-929`。）把第 413 行改成 `None` 後這支 sentinel 必紅，才把第一次的 survived mutant 轉成可登記的負控。

D 的初版則是「有限代數型契約只驗一個成功例」。今晚紀錄指出 production 188 行、測試 42 行且只驗成功；現在的 production 仍是 188 行，但測試已長成 263 行，四種結果各有測試、六種護欄原因被整表比對、十種資料類別參數化驗不可變，也驗結構型節點與上下文明傳。（初版事實：`今晚的錯誤清單.md:55-59`；契約四終局：`src/nova/契約/節點.py:18-24,89-144`；現有補強：`tests/單元/test_節點契約.py:31-60,110-142,145-182,185-263`。）所以共同治本是同一個「可執行負控閘」；但 D 還要把**契約有限集合本身列成資料驅動的窮舉測試**。若只靠通用 mutator 隨機改語法，不能保證四終局／六原因每一格都被要求過。

## 業界名詞與可用工具

這件事就叫 **mutation testing（變異測試，也叫 mutation analysis）**；故意改壞的版本叫 mutant，測試抓到叫 killed，沒抓到叫 survived，根本沒走到叫 no coverage。這三種不能混成一個「沒紅」；PIT 的官方基本概念還另分 timeout、non-viable 與 run error，正好對應這份負控紀錄反覆踩過的「測試沒抓到／破壞沒套用／runner 壞掉」三種不同病。[PIT 官方名詞與狀態](https://pitest.org/quickstart/basic_concepts/)；repo 的同類真實紀錄見 `docs/負控紀錄.md:275-285,307-334,407-430`。

成熟工具分兩層看：

- Python 直接可用的是 **mutmut** 與 **Cosmic Ray**。mutmut 會記住已做結果、找相關測試並平行執行；Cosmic Ray 支援每個 worker 一份隔離副本的分散式跑法。[mutmut 官方文件](https://mutmut.readthedocs.io/en/latest/)；[Cosmic Ray 官方文件](https://cosmic-ray.readthedocs.io/en/latest/index.html)與[分散執行說明](https://cosmic-ray.readthedocs.io/en/latest/tutorials/distributed/)。repo 自己也已把這兩個名字寫成尚未導入的候選。（`docs/負控紀錄.md:7-12`）
- 其他生態的成熟參照是 Java 的 **PIT** 與 JavaScript／.NET 的 **Stryker**。重要的不是跨語言硬搬工具，而是它們已驗證的做法：先收 per-test coverage，只跑覆蓋該 mutant 的測試；Stryker 還支援 incremental 與精確到檔案行範圍的 targeted mutation。[Stryker per-test coverage](https://stryker-mutator.io/docs/stryker-js/configuration/)；[Stryker incremental／指定行](https://stryker-mutator.io/docs/stryker-js/incremental/)；PIT 也用 coverage 與測試時間選相關測試。[PIT 官方說明](https://pitest.org/quickstart/basic_concepts/)

因此這個 repo 應採兩層：**mutmut 當 nightly 的廣泛探索器；repo-owned 的 selective／targeted mutation gate 執行已登記的精確負控。** 前者會找沒想到的洞，後者才把「文件宣稱的這一刀」變成每次都能重演的合約。只開 mutmut 的檔案／函式 filter 仍不足以取代後者：紀錄裡有刪測試檔、改設定檔、改 mtime、故意掛住與跨 OS 的操作，不全是 production 函式裡的通用 AST operator。（例子：`docs/負控紀錄.md:31-33,197-216,519-540,730-764`）

## 中間路線可行；登記應在 Python，不在 YAML

建議新增 `tests/負控/登記.py`（資料）與 `tests/負控/test_登記的變異會被殺.py`（runner 自測及參數化執行），再由 `src/nova/載體/規則表.py` 登記一條 CI 規則。規則集中地本來就明定在 `規則表.py`，而 `CLAUDE.md` 明禁把邏輯塞進 YAML／JSON。（`CLAUDE.md:39-43`；現行唯一規則表：`src/nova/載體/規則表.py:152-259`）

一筆登記應是 frozen dataclass，而不是可自由寫散文的 dict；概念形狀如下（**示意，不是已存在的程式碼**）：

```python
變異(
    識別="role-depth-to-call-options",
    目標=Path("src/nova/載體/角色.py"),
    操作=替換一次(
        原文="思考深度=self.思考深度,",
        變成="思考深度=None,",
    ),
    必須覆蓋=frozenset({49}),
    該紅=("tests/單元/test_角色.py::Test固定提示角色::test_思考深度會傳進呼叫選項",),
    最多秒=2.0,
    平台=任何平台,
)
```

`替換一次`、刪檔、設 mtime、預期 timeout 等操作是 Python 函式／Protocol，邏輯留在 Python；登記只組合 typed operation 與 typed expectation。每個 operation 都必須斷言錨點恰好出現一次，並比對變異前後 SHA；現在的散文只有自然語言「拿掉／改回」，runner 無法判定改了零次或兩次，而 repo 已實際踩過 `str.replace` 沒命中卻報紅的假負控。（`docs/負控紀錄.md:323-334,455-477`）

`docs/負控紀錄.md` 不該被 runner 反向解析成程式。它應改成兩區：

1. **自動負控表是由 Python registry 產生的唯讀 view**，欄位只放 `id／目標:行／操作摘要／該紅 nodeid／平台／CI tier`；gate 在記憶體重生一次並與 committed Markdown 逐字比，漂移就紅。執行真相只住 Python，文件不藏邏輯。
2. **外部／人工證據表** 明列 `manual-canary`、不能 blocking 的原因、最後驗證環境／日期、到期日；過期顯示紅色 `STALE`，但不能冒稱測試通過。現有 325 列在完成遷移前一律標 `legacy-unverified`，不能因為散文寫了「紅 ✓」就算 CI 保證。

這樣保留這份檔案原本「紀錄，不是規範」的定位，同時消除現行「測試名存在就當文件可信」的錯誤代理指標。（文件自述：`docs/負控紀錄.md:1-9`；現行代理檢查：`tests/驗收/test_文件即事實.py:88-96`）**所以答案不是 YAML，也不是把 Markdown 表格寫得更規整；是 Python typed registry 作 authority，Markdown 只當生成報表。**

runner 必須 fail-closed 地走完以下狀態機；少任何一步，E 只是換格式沒有治本：

1. 在未變異副本跑被點名測試，必須先是 0；本來就紅的測試不能「殺」任何 mutant。
2. 每個 mutant 用自己的 `/tmp` 副本／worktree；確認目標基線雜湊、錨點唯一、變異後雜湊不同。docs 現行 D runner 已經手工做 SHA 與還原檢查，可直接把那個經驗收進通用 runner。（`docs/負控紀錄.md:931-947`）
3. 在原始碼上先做 F 的 per-test coverage preflight；指名測試沒走到 `必須覆蓋` 的 executable line，結果是 `WRONG_TEST`，當場讓閘紅，不准等 mutation 後再把「沒紅」含糊報成 survived。
4. 清 `src/`、`tests/` 的 `__pycache__` 後才跑 mutated copy；`PYTHONDONTWRITEBYTECODE` 不能代替清除，現有 gate 已把這個動作包住 pytest。（`src/nova/載體/規則表.py:87-108,131-147`）
5. 每支 `該紅` 分開跑；只有正常收集到該 nodeid 後的 pytest exit 1 算 killed。exit 2／3／4／5、找不到 nodeid、runner exception、一般 timeout 都是 gate error；只有登記成「預期掛住」的 mutant 才把受控 timeout 算 killed。repo 已有「拿掉停止規則就掛住」與「跑不起來不等於紅」兩個反例。（`docs/負控紀錄.md:33,542-583`）
6. runner 自己也要有會 fail 的測試：至少覆蓋 survived、錯 test、錨點零次／兩次、baseline 原本紅、pytest 跑不起來、預期與非預期 timeout、以及清 pycache 呼叫被拿掉。否則新 runner 又只是另一個被宣稱的把關器。（判準：`CLAUDE.md:87-91`；現有「只測清除函式、沒測閘有叫」的前車之鑑：`tests/整合/test_閘不准吃快取.py:251-269`。）

## 哪些不能放進同一個 blocking gate

題目舉的「同一秒改兩次、長度剛好一樣」**可以機械化，而且已經機械化**：測試用兩段等長 bytes，明設回同一個 mtime，先證明快取確實假綠，再證明閘帶 `--no-incremental`；完全不靠真的剛好同一秒。（`tests/整合/test_閘不准吃快取.py:128-192`）Python `.pyc` 那一族也用同法，清 cache 後斷言跑到新內容。（`tests/整合/test_閘不准吃快取.py:195-269`）掛住也不是不可機械化：子程序設 deadline，逾時後收割，結果分類成預期 timeout 即可。（既有掛住負控：`docs/負控紀錄.md:33,197`）

不能誠實當「每個 PR 都會自動擋」的是環境沒有可決定 oracle 的項目：

- GitHub ruleset 的「真的 push main 被遠端擋」、真 LLM CLI 的認證／額度／網路、以及會花真 token 的行為，依賴 repo 外會變的狀態；預設 pytest 本來就排除 `真cli`／`真端點`。（例子：`docs/負控紀錄.md:20,27-29,144-146`；排除設定：`pyproject.toml:32-44`）處理方式是有隔離帳號／sandbox repo 的 scheduled canary，輸出 commit、環境與時間戳證據；沒有該環境就標 `NOT_RUN` 並讓「自動保證」報表紅或降級成明寫 manual，不能把 skip 算 pass。
- OS 差異需要 matrix，不是本機一次。repo 已有 macOS 負控沒紅、Linux CI 才紅的實例，後來把 mutation 改成兩邊都能斷言的 symlink 行為。（`docs/負控紀錄.md:514-540`）有 macOS＋Linux runner 就機械跑；缺一邊就只能宣稱已覆蓋的那一邊。
- 純人眼語意（例如「活動監視器看起來像誰」）先降成可觀測的 kernel name／inode／argv 再測；降不成的部分只能留人工驗收，記最後驗證時間與到期日，不准寫「會自動擋」。這個 repo 已把活動監視器敘述降成 hardlink、inode 與整條命令測試，正是可採的轉法。（`docs/負控紀錄.md:514-524`；入口為何用具名直譯器：`src/nova/__main__.py:3-8`）

# 三、F：負控點名錯測試，怎麼機械抓

**可以，而且應該在真正套 mutation 之前就抓。** 工具是 coverage.py 的 **measurement context／per-test coverage**：每個測試的執行行號分開記，再用 `CoverageData.contexts_by_lineno()` 反查「這一行有哪些 test context 跑過」。coverage.py 官方把 dynamic context 的主要問題直接描述成「what test ran this line?」，pytest-cov 的 `--cov-context=test` 會替每支測試切 context；API 則直接回 `line -> contexts`。[coverage.py contexts](https://coverage.readthedocs.io/en/7.14.3/contexts.html)；[CoverageData API](https://coverage.readthedocs.io/en/7.13.5/api_coveragedata.html)

F 的路徑錯位可以精確重現：被破壞的 `固定提示角色` 接線在 `src/nova/載體/角色.py:43-53`，思考深度那格是第 49 行；被錯點名的兩支 `test_派工接線` 走的是 `_子命令_問` 自己直接建立 `呼叫選項` 的另一條路，第 413 行也剛好有一格 `思考深度`。（`tests/整合/test_派工接線.py:39-58`；`src/nova/載體/命令列.py:394-421`）所以它們能證明 `nova 問 → 呼叫選項`，完全不能證明 `固定提示角色 → 呼叫選項`。真正直打該接縫的是 `test_思考深度會傳進呼叫選項`。（`tests/單元/test_角色.py:81-84`）

本研究在隔離副本把錯的兩支與對的一支同批用 `pytest-cov --cov-context=test` 跑過，查 API 的結果是：

| production line | per-test context 結果 | 判決 |
|---|---|---|
| `src/nova/載體/角色.py:49` | 只有 `tests/單元/test_角色.py::Test固定提示角色::test_思考深度會傳進呼叫選項` | 對的負控 test |
| `src/nova/載體/命令列.py:413` | 只有 `test_例行工作會帶上深度high`、`test_推理工作會帶上深度max` | 兩支不是沒跑，是跑在另一條同名接線 |

這三支正常跑實測 wall 0.18 秒；加 per-test coverage 是 0.34 秒，**F 這一筆的 coverage preflight 增量 0.16 秒**。整個 `tests/單元` 670 支在同一隔離副本加 per-test coverage 是 2.13 秒；本研究同環境未加 coverage 約 1.52 秒，增量約 0.61 秒。這些是 2026-08-30 實測，不是 source 宣稱；測試數與被查 production 行則分別見 `tests/單元/test_角色.py:81-84`、`src/nova/載體/角色.py:43-53`。

機械判決要分兩關，不能用 coverage 取代 mutation：

| coverage preflight | mutated test | 真正含義 |
|---|---|---|
| 沒覆蓋 mutation footprint | 不必跑 | `WRONG_TEST`：F，點名錯路 |
| 有覆蓋 | 綠 | `SURVIVED`：走到了，但 assertion 沒鑑別力；C 的預設值假綠屬這類 |
| 有覆蓋 | 紅 | `KILLED`：這筆登記成立 |
| coverage／pytest 跑不起來 | — | `RUN_ERROR`：閘自己壞了，fail closed |

footprint 應登記「必須覆蓋的 executable lines」，不是天真要求文字 diff 每一行都有 hit；多行 literal、decorator 與 import-time code 未必各自是可執行事件。對 module import 時就執行的 static mutant，context 可能是空字串，coverage.py 也明寫 test context 建立前的程式落在 empty context；這類要每支 test 隔離啟動，或誠實標 `STATIC` 後跑完整相關 test set，不能硬配給某一支。[coverage.py 的 empty context 說明](https://coverage.readthedocs.io/en/7.14.3/contexts.html)；同一限制在 Stryker 也會讓 static mutants 改跑全測試。[Stryker 官方設定](https://stryker-mutator.io/docs/stryker-js/configuration/)

子程序是本 repo 的重要 caveat。舊測速文件已明寫 coverage／testmon 預設看不到 child process，所以光在父 pytest 開 coverage 會漏掉驗收測試中另起的 `python -m nova`。（`docs/設計/05-測試怎麼跑最快.md:222-241`）coverage.py 7.10 之後可在設定中開 `[run] patch = subprocess`，它會自動讓 Python child 啟動 coverage、強制 parallel data，結束後必須 `coverage combine`；若 `exec*e/spawn*e` 自訂環境還要傳 `COVERAGE_PROCESS_START`。[coverage.py subprocess 官方設定](https://coverage.readthedocs.io/en/latest/config.html)；[process 指南](https://coverage.readthedocs.io/en/7.14.1/subprocess.html) 非 Python 的 `ruff`／真 LLM CLI 當然沒有 Python line coverage，這種 mutation footprint 必須落在 nova 父／子 Python，或另用工具自己的 trace。

**F 的增量實作成本（推測）是 70–120 行、每個小批次約 +0.2–0.7 秒。** 約 35–55 行做 coverage 執行／combine／API 查詢，35–65 行測 `WRONG_TEST`、static、subprocess 與 run error；依賴在 `pyproject.toml` 加 coverage／pytest-cov，runner 落在前述 `tests/負控/`。今晚這三支的實測是 +0.16 秒；含子程序的列因要啟動與 combine，推測每批再多 0.3–1.0 秒，查不到 repo 實測，必須在 runner 完成後量。這一成本已包含在第二題 C–F 的共用 370–550 行中，不重複計價。（現行 dev dependencies 沒有 coverage：`pyproject.toml:20-30`；現行測試層級實測基準：`docs/設計/05-測試怎麼跑最快.md:103-142`。）
