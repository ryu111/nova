### 1. 測試層級的隔離手法 (Test-Level Isolation)

> **結論**：消除資源競爭最徹底的手法是「完全消除共享狀態」，利用執行序／進程唯一的 Worker ID 動態派生獨立的 DB Schema、臨時目錄與隨機動態埠號（Port 0），使每個平行 Worker 享有完全自包含的沙盒環境。

#### 具體做法與機制：
1. **每個 Worker 一份 DB / Schema / tmpdir**：
   * **DB / Schema 隔離**：在 PostgreSQL 中使用 Schema 隔離（連線時 `SET search_path TO worker_{worker_id}, public;`），避免為每個 worker 重建完整 Database（耗時數秒），測試前置時間（Fixture Setup Latency）可從**數秒降至 50~100ms**。在 Django 中使用 `python manage.py test --parallel` 會自動以 `test_dbname_1`、`test_dbname_2` 模式複製獨立資料庫。
   * **檔案 tmpdir 隔離**：使用 pytest 的 `tmp_path` 或 `tmp_path_factory.mktemp(f"worker_{worker_id}")`，底層自動隔離在 `/tmp/pytest-of-user/pytest-N/worker_gw0/` 目錄，杜絕共用固定檔案路徑時的 I/O 覆蓋。
2. **Testcontainers 與 Port 動態配置**：
   * **動態隨機 Port (Port 0)**：徹底禁止固定埠（如 5432、8080），Testcontainers 會將容器埠對應至 Host 端的隨機未佔用埠（Ephemeral Port / `getMappedPort()`），徹底解決 `EADDRINUSE` 錯誤。
   * **Ryuk 自動垃圾回收**：伴隨啟動的 `moby-ryuk` 守護容器會在測試 Process 異常崩潰（Crash / SIGKILL）時自動清除殘留容器，防止記憶體與 Port 洩漏。
3. **pytest-xdist `--dist loadgroup` 與 `loadscope` 的差別**：
   * `--dist loadscope`（粗粒度自動）：按代碼結構（Module 或 Class）分發，同一測試檔案內的所有測試必在同一 Worker 執行，適用於共享 Class Fixture 的情境。
   * `--dist loadgroup`（細粒度手動）：透過裝飾器 `@pytest.mark.xdist_group(name="group_name")` 分組，**跨多個檔案但操作同一個外部排它資源**（如同一測試帳號、同張單一鎖表）的測試會強制派給同一 Worker 序列執行，其餘無相依測試仍可自由平行化。
4. **pytest 的 `filelock` / `flock` 跨進程序列化**：
   * 在 Session-scoped fixture 中使用 `filelock.FileLock`（底層封裝 `fcntl.flock` 或 Windows `LockFileEx`）。多個 Worker 同時啟動時，僅有首個搶到鎖的 Worker 會執行重型初始化（如全域 Migration 或下載模型），其餘 Worker 等待鎖釋放後直接讀取快取產物。

### 2. 排程層級 (Scheduling & Resource Throttling)

> **結論**：在多 Job／多 Runner 併發時，測試隔離必須向上延伸至 CI 調度器；透過限制平行作業數、語意化資源鎖與排它標記（Exclusive），從排程端阻止多個 Job 壓垮共享依賴或實體硬體。

#### 具體做法與機制：
1. **GitHub Actions Concurrency**：
   * **取消舊 Commit 爭搶**：`concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }`，在開發者頻繁 Push 時自動中斷舊 Commit 的 CI，避免多個 PR 的相同分支同時對測試環境產生資源轟炸。
   * **排隊互斥鎖**：對共享 Staging 或實體硬體的 E2E Job，使用固定 group 名稱並設 `cancel-in-progress: false`，GitHub 會自動進行 Job 佇列排隊（Queueing）。
2. **Bazel 資源調度與排它標記**：
   * **併發控制**：`bazel test //... --local_test_jobs=4` 或 `HOST_CPUS*0.5`，將測試併發與編譯併發分開，防止測試佔滿 CPU/RAM 造成 Context Switch 延遲與 Timeout 假紅。
   * **排它標記**：`tags = ["exclusive"]` 告知 Bazel 執行該測試 Target 時，本地主機不得有任何其他 Action 同時運行。
   * **自定義資源標記**：支援 `tags = ["resources:gpu:1"]` 搭配 `--local_resources=gpu=2`，確保調度器同一台機器最多只同時排程 2 個 GPU 測試。
3. **Jenkins Throttle 與資源鎖**：
   * **Throttle Concurrent Builds Plugin**：自訂 Category（如 `Selenium-Tests`），限制全叢集或單一 Node 同時運行的 Job 上限，避免 Selenium Grid Session 耗盡。
   * **Lockable Resources Plugin**：在 Pipeline 中使用 `lock(resource: 'shared-device', inversePrecedence: true) { ... }` 實施語意化鎖。

### 3. 判別法：分辨「真的壞了」與「搶資源」及業界 Flaky 分類

> **結論**：判別資源爭搶假紅的關鍵是「隔離單跑驗證（Isolation Re-run）」與「系統負載關聯分析」；業界研究指出大規模 CI 系統中高達 **84%** 的 Pass-to-Fail 轉換實為 Flaky，且超過 **60%** 的根本原因集中於非同步超時（Async Wait）與並發競爭（Concurrency）。

#### 具體做法、數據與分類模型：
1. **Google 規模化研究（John Micco, 2016 / Memon et al., ICSE 2017）**：
   * **16% 的測試用例**具有不同程度的 Flakiness。
   * 在所有從 Pass 變成 Fail 的狀態轉換中，**高達 84% 實際上是 Flaky 假紅**，僅 16% 是代碼變更引入的真實缺陷。
2. **Luo et al. (ACM FSE 2014) Flaky 根因分佈**：
   * **Async Wait (45%)**：非同步操作未完成即 Assert，平行高負載時 CPU 延遲導致 Timeout。
   * **Concurrency (20%)**：共享記憶體 Data Race、Deadlock、原子性破壞。
   * **Test Order Dependency (12%)**：前面的測試修改全域狀態/DB，污染後續測試。
   * **Resource Leak (8%)**：連線池耗盡、FD 洩漏、Port 未釋放。
   * **Network / Time (10%)**：外部依賴與時區隨機數。
3. **Microsoft 實務與 FlakeFlagger (Alshammari et al., ICSE 2021 / Lam et al., ISSTA 2019)**：
   * **FlakeFlagger**：針對重跑 10,000 次成本過高的問題，透過提取靜態與動態特徵（代碼覆蓋率方差、執行時間波動、無序集合迭代等），以 **0.85+ 的 Precision/Recall** 不經重跑直接預測潛在 Flaky 測試。
4. **四步診斷矩陣（真壞 vs 搶資源）**：
   * **單獨隔離跑 10 次**：真壞必 100% 失敗；搶資源在單跑時 100% 通過。
   * **錯誤類型**：真壞多為業務邏輯 `AssertionError`；搶資源多為 `TimeoutException`、`ConnectionReset`、`EADDRINUSE`、`DeadlockDetected`。
   * **系統遙測關聯**：失敗時間點與 Host CPU Spike (>95%)、Disk I/O 飽和、DB 連線池耗盡高度重疊。
   * **群聚效應**：大量互無相依的測試在同一秒內集體發生 Timeout。

### 4. 標記法：將測試標為 Serial 的通用做法與其代價

> **結論**：將無法隔離的測試標記為 Serial 是快速止血的必要手段，但會受到「阿姆達爾定律（Amdahl's Law）」的嚴苛制約，極少量的 Serial 測試便會形成 CI 執行時間的長尾瓶頸（Straggler）並大幅推升 CI 算力閒置成本。

#### 具體標記做法：
* **Python (pytest)**：
  * `@pytest.mark.xdist_group(name="serial_group")`：所有 serial 測試固定分發給同一個 worker。
  * `@pytest.mark.serial`：搭配 CI 拆分執行（先跑 `pytest -m "not serial" -n auto`，再跑 `pytest -m "serial" -n 1`）。
* **Java (JUnit 5)**：
  * `@Execution(ExecutionMode.SAME_THREAD)`：強制該測試類別在同一個執行緒運行。
  * `@ResourceLock(value = "SYSTEM_PROPERTIES", mode = ResourceAccessMode.READ_WRITE)`：細粒度聲明讀寫排它鎖。
* **Go**：
  * Go 原生預設**全為 Serial 執行**，只有顯式宣告 `t.Parallel()` 的測試才會並發；不加 `t.Parallel()` 即為 Serial。

#### 標記的代價與量化模型：
1. **阿姆達爾定律（Amdahl's Law）的理論天花板**：
   $$\text{Speedup} = \frac{1}{(1-p) + \frac{p}{N}}$$
   * 假設測試集總耗時 100 分鐘，若有 **10%（10 分鐘）** 被標記為 Serial（$1-p = 0.10$）。
   * **即便投入 $N = 64$ 或 $\infty$ 個 CPU 核心，測試總執行時間永遠無法低於 10 分鐘，最大加速比被鎖定在 10 倍以內**。
2. **長尾效應與 CI 算力浪費（Straggler & Idle Cost）**：
   * 當其他 Worker 跑完平行測試後，只剩 1 個 Worker 在跑 Serial 佇列，其餘已配置的 CI VM / 容器核心將處於 **100% 閒置計費狀態**。
3. **架構負債增長**：
   * 標記 `@serial` 常被當作逃避重構共享狀態的捷徑。若無 CI 標記比例監控與門禁，Serial 測試數量平均每季度會自然增長 **15%~25%**，最終抵消平行化帶來的效益。
