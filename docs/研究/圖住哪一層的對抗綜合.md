  A3 才不自相矛盾（見 A4）。
- **C4**：SQLite 現在不用。但依據換成 opus 的：1.7 ms 量的是 glob 不是工作，
  真指標是 `nova 帳本` 全掃的 53 ms；規模驅動是總位元組不是檔數（線性外插
  3,000 檔約 340 ms）；原門檻的理由（inode lookup 暴增）在 APFS 上不成立——

- **D2**：「不必由不同團隊建置、不必存在於不同系統」推不翻。opus 補一條界線收下：

  在人的尺度吃 53 ms，現在分開（記憶體 tuple vs jsonl）是對的，別合成一張表。
- **C5 的反駁**：`收件.py:249` 的 `rename(2)` 對同一 pathname 原子且可序列化，

### C1

## 已推翻的（附推翻它的具體反例）

### A4「hook 絕不是圖；只有 Workflow 工具是純圖」
兩個獨立失敗模式，都留：
- **前提錯**（sol）：Claude Code 的 Workflow 是可含 loop、branch、`pipeline()`、
  `parallel()` 的 JS orchestration script，不是純圖。且 Stop hook 回 `block` 時
  執行會**繼續**、理由成為下一條指令——tracer 若把 final response 當終點，
  繼續的那段成本與 checkpoint 全漏記。
- **定性錯**（opus）：`Stop`／`SubagentStop` 決定的正是「終止 vs 回頭邊」，
  那是整張圖最重要的拓撲決策（要不要收工）；而且它是掛在終止邊上執行任意碼的
  predicate——正是 A3 禁止的東西。這個張力的正解：Stop-hook 類的 continuation
  判斷要像 nova 的 `卡住了` 一樣住在圖外的 stop rule 裡，不准用「hook 絕不是圖」
  把它藏掉。

### B2「圖是次要根因：分類錯誤，有路由節點就不會走進去」
兩個獨立失敗模式，都留：
- （opus）nova **沒有「選圖」這個動作可以錯**：全庫只有一張 `TDD階段表`，
  `跑工作流` 拿到 `階段表` 參數第一件事是 `del`（`工作流.py:73`）。沒有選擇點
  就沒有分類錯誤，只有「預設值不適用於這個輸入」——那是入口的型別問題。

## 兩家對撞的三處

### 一、C2：sol 限縮 vs opus 推翻
衝突在**評估層不同**，不是事實矛盾。sol 評「UUIDv7 作為格式」：可當 run ID，
但「可排序＋唯一」說太滿（RFC 9562 同毫秒單調性是可選實作、唯一性仍是機率、
仍需排他建檔；內容雜湊當知識資產 ID 會合併不同 provenance 的同 bytes）。
opus 評「換 UUIDv7 這個動作」在現碼上的後果：預算鎖 fail-open＋三處耦合
（`_窗口內的執行`、`收件._檔名時戳`、`_像識別碼`）＋修不掉繼承路徑。
**裁決**：以清單原句「改用 UUIDv7」論，推翻。sol 的格式層評估保留為將來條件：
真要換，必須同步改那三處，且換完撞號依然靜默——所以兩家共同的處方是
O_EXCL 先行（下一步 3）。

### 二、A1：sol 站得住 vs opus 需要限縮
衝突在「內圈」的定義域：sol 只數 nova 自己的圖遍歷（單游標、無 ready-set／join
——這半對）；opus 把節點內容物算進去。源碼裁決給 opus：`接力.py:101-110` 的
failover 迴圈實在，997,031 token 在單節點內部燒掉、外圈毫無可見性是今晚實測。
限縮版 A1 收 opus 的公式，保留 sol 的外圈檢驗。

### 三、Q1：sol 說 A4 錯得最貴 vs opus 說 A2
**裁 A2。** A4 已被兩家當場擊殺——死掉的主張沒有「被照著做一年」的機會；
會活一年的是以限縮形式存活的半錯主張，A2 正是：隱藏邊集中在中止／護欄路徑、
每張新表把「拓撲是純資料」的信念再複製一次、sequencing rule 被讀成 permanent
prohibition。sol 憂慮的實質（continuation 與成本不進 trace、事後因果不可重建）
在 nova 語境裡就是 A1 已驗證的「節點內不可見」——併進 A1 限縮版保留，不因裁決而丟。

## 未決的（附分勝負的實驗）

### 未決一：`卡住了` 對「真紅迴圈」是全滅還是機率性失效
opus 說 pytest 尾巴的 `in 0.12s` 每次不同，精確相等幾乎不可能成立；但快速套件的
耗時四捨五入後可能重複，「幾乎不可能」沒被量過。結構我已驗證：證據＝
`(stdout+stderr)[-4000:]`（`判準.py:48`）；逾時證據是常數字串（`判準.py:39`），
所以**逾時迴圈它仍會 fire**——「死碼」至少要限縮成「對真紅迴圈疑似失效」。

實驗（可直接跑）：

```bash
cd /Users/sbu/nova
printf 'def test_必紅():\n    assert False\n' > /tmp/test_必紅.py
for i in 1 2 3; do uv run pytest -q /tmp/test_必紅.py tests 2>&1 | tail -c 4000 > /tmp/卡$i; done
cmp -s /tmp/卡1 /tmp/卡2 && cmp -s /tmp/卡2 /tmp/卡3 && echo 三次全等 || echo 有不等
```

- 「三次全等」（含 `in 0.xxs`）→ opus 被推翻：`卡住了` 對真紅迴圈仍會 fire
  （但機率性，仍該正規化）。
- 「有不等」→ opus 對：修法是比對前剝掉計時與暫存路徑
  （`in \d+\.\d+s`、`pytest-of-*/pytest-\d+`）。
- 加跑一個用 `tmp_path` 的紅測試變體：預期必不等；若也全等則 opus 全錯。

### 未決二：自動意圖路由器要不要做
sol：分類器會誤判、明確旗標就夠。opus：前門路由該提前到第一或第二。

實驗：取歷史收件原文（`$XDG_STATE_HOME/nova/專案/nova-*/已處理/*.收件`，n≥30），
人工標 `tdd|research` 當基準，用最便宜的一顆腦逐張分類對照。
錯分 ≤1/30 → 路由器可接進 `_工作流開跑前` 當**預設值**（票面欄位可覆寫）；
錯分 ≥2/30 → sol 對：只做明確選擇，分類器最多做「明顯錯配時警告」。
實驗出結果前，下一步 5 只做明確選擇，不做自動分類。
