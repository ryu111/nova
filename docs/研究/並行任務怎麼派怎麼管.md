# 十幾條任務並行時，怎麼派、怎麼管、完成時怎麼排順序

---

## 摘要與核心主張

在單一主機上同時啟動 16 個 Git worktree 平行執行 `nova 跑`（TDD 七階工作流）時，真正的瓶頸**不是 LLM API 的呼叫頻寬，而是「落地串行化（Landing / Rebase Serialization）」與「認知/監管頻寬」**。

今晚實測燃燒 2,000～4,300 萬 token、合併 6 個 PR（#129～#134）的真實數據揭示了五個直接痛點：
1. **追蹤靠人手拼裝導致漏單（問題 A）**：在上下文切換中遺失了撞護欄（退出碼 4）的子程序；
2. **熱點檔案多線並改導致 rebase 衝突與錯解（問題 B）**：`工作流.py`、`tests/負控/登記.py`、`docs/負控紀錄.md` 衝突頻繁，手動解衝突產生語意毀損；
3. **憑感覺排序導致落地破壞（問題 C）**：#133 搶先合併導致 #132 行號漂移破壞；
4. **四種退出碼（0/1/3/4）處置混淆（問題 D）**：護欄停工（4）與未知狀態（3）不可一概視為失敗重試；
5. **前置依賴缺乏喚醒機制（問題 E）**：依賴未解的任務沉睡在 scratchpad 中無人知曉。

根據 **利特爾法則（Little's Law）** 與 **限制理論（Theory of Constraints / Drum-Buffer-Rope）**，並行管理的核心在於：**以落地的吞吐量作為節奏鼓（Drum），以檔案讀寫集合交集（Bernstein's Conditions）作為派工邊界，以不可變狀態掃描器作為零遺漏保證（Rope），以最小爆炸半徑與拓撲序作為確定性落地隊列。**
