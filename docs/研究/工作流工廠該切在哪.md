## 1. 五份資料其實在談三種不同的「圖」

**結論：其中四份在談工作流拓撲，arXiv 那份談的是企業狀態／事件的 Context Graph；真正的新東西不是圖論，而是把原本散落在程式與 prompt 裡的控制流、權限與證據升成可版本化契約。**

| 資料 | 實際主題 | 獨特貢獻 | 與其他資料的關係 |
|---|---|---|---|
| [AlphaLab：Graph Engineering](https://www.alphalab.site/graph-engineering) | 工作流圖：Node＋Edge＋Anchor | 用「真實相依」「fan-out/fan-in」「外部可重現證據」給出最清楚的操作性定義，也明列小任務、無平行寬度時不要畫圖 | Anthropic 模式的圖形化、實務版 |
| [arXiv 2607.07721](https://arxiv.org/html/2607.07721v1) | Context Graph：企業實體、關係、時間與 delta event | 有向、帶屬性、時間戳記的 multigraph；用規則偵測狀態變化，再按 urgency/relevance/persona/confidence 決定是否通知 | **不是工作流圖**。對 nova 最多是未來 Trigger／Context substrate，不是 orchestration |
| [CSDN：Agent 從循環走向組織](https://blog.csdn.net/m0_59164520/article/details/163142831) | 把 agent 系統視為組織 | 區分穩定的 Org Graph 與每次執行的 Work Graph；邊還承載資料、控制、權限、證據、失敗傳播 | 與 AlphaLab 同核心，但更偏治理與組織設計 |
| [Towards AI：Graph Engineering](https://pub.towardsai.net/graph-engineering-9986f8d5bdbd) | 顯式、可版本化的 topology＋typed state | 最具體談 reducer、checkpoint、interrupt、fan-out cap、partial failure；也坦白這是 LangGraph、DAG、actor、contract-net 等舊模式的「命名事件」，不是發明 | 與 CSDN 同核心，偏 runtime／distributed systems |
| [Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) | 六種常見 workflow/agent 形狀 | 區分 predefined workflow 與模型動態控制的 agent；主張從最簡單形狀開始，只有量測證明值得才增加複雜度 | 沒使用 Graph Engineering 這個總稱，但列出的模式全部都是小型 graph motif |

arXiv 那份的評估也是三個合成企業情境、每個 200 個模擬 delta event；平均 Precision@5 0.83，但作者自己列出 graph completeness、人工規則覆蓋、alert fatigue、隱私等限制。因此它不能用來支持「工作流 graph 比 linear workflow 好」，只能支持「企業狀態可以用圖承載」。

同一件事換名字的對照如下：

| Anthropic 名稱 | 圖／傳統控制流名稱 |
|---|---|
| Prompt chaining | 線性 pipeline；退化的 DAG |
| Routing | switch／conditional edge |
| Parallelization—sectioning | 靜態 fan-out＋barrier＋fan-in |
| Parallelization—voting | 固定 N 次並行評估＋quorum/reducer |
| Orchestrator-workers | 動態 fan-out＋fan-in；執行時產生 Work Graph |
| Evaluator-optimizer | 帶 inferential gate 的回頭邊 |
| Agent | 模型選擇下一條邊的動態 loop／policy |
| Anchor | 外部不可由優化者任意改寫的參照 |
| Verifier/evaluator | 讀取證據、做判定的 sensor |
| Gate | 根據判定允許或拒絕轉移的 enforcement point |

Anchor、verifier、gate 彼此相關但不是同義詞：測試輸出是 anchor，測試執行器是 verifier，只有綠才往下走是 gate。

## 2. Anthropic 六種模式靠什麼停

**結論：前四種主要靠「有限拓撲走完」而停，不代表品質已通過；真正容易無界的是 evaluator–optimizer 與 agent，而 Anthropic 的概念文章和 cookbook 都沒有提供可直接照抄的完整 production stop contract。**

應把三種概念分開：

1. **拓撲終止**：沒有下一個節點了。
2. **品質接受**：有足夠證據認為結果合格。
3. **安全護欄**：即使還沒合格，也因預算、時間或無進展而停。

| 模式 | 正常怎麼停 | 是否證明品質 | Production 必須補什麼 |
|---|---|---|---|
| Prompt chaining | 固定步驟列表跑完；中間 gate 可提早拒絕 | 否。只是最後一段產生完成 | gate 失敗語意、schema failure、timeout |
| Routing | 分類一次，選中的分支跑完 | 否。分類與分支結果都可能錯 | `unknown` 分支、低信心升級、不得默認任一分支 |
| Parallelization | 固定分支到達 barrier，aggregator 完成；voting 通常固定 N 票 | 只有另訂 quorum／證據規則才有 | fan-out cap、timeout、必要分支、最低成功數、partial failure |
| Orchestrator-workers | orchestrator 產生有限 worker 清單，每個跑一次，再合成 | 否。worker 數量與完整性通常是模型判斷 | worker 數硬上限、遞迴 spawn 禁令、barrier/quorum、合成後驗證 |
| Evaluator-optimizer | evaluator 回 `PASS` | 是 inferential acceptance，不是機械真值 | 最大輪數/token/time、無進展、外部證據或人工升級 |
| Agent | 模型判定完成／不再叫工具；遇 blocker 問人；或撞最大迭代 | 模型的「完成」本身不證明任何事 | observable end state、human checkpoint、max iteration、at-most-once、未知結果處理 |

Anthropic 的[官方 cookbook 索引](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/README.md)把前三種實作成有限的 `for`／固定輸入列表；orchestrator-workers 範例也是一次分解、跑完有限 worker 清單就返回。最值得警戒的是[官方 evaluator-optimizer notebook](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/evaluator_optimizer.ipynb)：核心是 `while True`，只有 evaluator 回 `PASS` 才跳出，沒有最大迭代、token 或無進展條件。

所以「沒有機械判準時靠什麼停」的誠實答案是：

- chaining／routing／parallel／orchestrator-workers：靠程式拓撲耗盡。
- evaluator-optimizer：靠另一個模型的判定。
- agent：靠模型自報完成、環境觀測、人工決定或硬上限。

對 nova 而言，模型的 `PASS`／`DONE` 最多只能形成「完成候選」；真正終點應是：

```text
領域證據達標
或 人工明確接受
或 護欄生效

不得只有「模型說完成」
```

## 3. Graph Engineering 比一條線多了什麼

**結論：只有當「單一 program counter」不足以描述執行時，才值得付 graph runtime 的代價；有第二種工作流、甚至有條件回頭邊，都還不必然需要圖層。**

數學上，nova 的 TDD 狀態機已有 cycle，當然是一張有向圖；工程上 Graph layer 多的是這些一級能力：

- 同時有多個 runnable node，而不是永遠只有一個「目前階段」。
- fan-out、barrier、quorum、join 與 partial failure。
- typed shared state，以及平行寫入時的 reducer／ownership。
- node-boundary checkpoint、interrupt、跨程序 resume、idempotency。
- node／edge 級權限、證據、成本與 trace。
- 執行時動態新增或裁掉分支。

成本不只是多幾個類別，而是必須回答：某一分支逾時是否擋住全部、哪些 worker 必須成功、兩個更新如何合併、重啟會不會重做副作用、checkpoint 與外部世界是否一致。Towards AI 將其概括成 distributed-systems 問題；Anthropic 的研究系統也顯示多 agent 約使用一般聊天 **15 倍 token**，適合有價值且真正可平行的廣度型問題，不適合高度共享 context 或依賴密集的工作。[Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)

給 nova 的明確「還不用圖」判準是：

```text
max_ready_nodes == 1
而且 next = f(current_node, current_exit)
而且沒有 join／quorum／state reducer
而且不需要在節點邊界持久暫停後跨程序恢復
而且 transition table 與單一路徑 trace 仍容易閱讀、窮舉、測試
```

只要全部成立，就用單游標 state machine。真正的升級訊號，是 `目前: 節點代碼` 必須變成 `就緒: frozenset[節點代碼]`，並開始需要 join 與 reducer。

因此今晚的 trace：

- 足以證明 nova 需要「多種 workflow spec＋安全選擇」。
- 足以證明結果語意不能只有綠／紅。
- **尚未證明需要 `src/nova/圖/`、graph scheduler 或 DSL。**

這與 AlphaLab「沒有工作寬度就別畫圖」、CSDN「拓撲必須承載真實約束」、Anthropic「先用最簡單方案」是一致的。

## 4. 研究型工作流如何收斂

**結論：研究沒有 open-world 的「全對測試」，業界實際收斂的是「在固定範圍、證據標準與預算內達到覆蓋＋來源支持＋搜尋飽和」，不是證明世界上再也沒有遺漏。**

[Anthropic 的 agent eval 指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)對研究型輸出建議組合三種 grader：groundedness、coverage、source quality；LLM critic 可以找未支持主張與覆蓋缺口，但必須以專家判斷校準。

| 做法 | 運作方式 | 成本 | 主要失效模式 |
|---|---|---|---|
| Loop-until-dry | 每輪搜尋後確定性去重；連續 K 輪沒有「新的實質主張」才進下一階 | 重複 full sweep，邊際收益快速下降 | 同一搜尋角度形成局部 fixed point；工具壞掉也看似 dry；同義改寫破壞 dedupe；一輪 dry 是隨機漏看 |
| Completeness critic | 獨立 context 讀問題、覆蓋表、claim ledger、草稿，輸出具體缺口 | 一次 critic 加缺口定向搜尋，通常低於全員重跑 | 與作者共享盲點、虛構缺口、無限提高標準、不能證明不存在未知資訊 |
| 多視角交叉驗證 | 不同 worker 分別查不同來源類型、反例、術語、時間範圍，再保留 provenance 合成 | 約 N 倍搜尋＋協調與合成；Anthropic 實例約 15× token | 錯誤高度相關、正確少數被投票消掉、重複查同一路徑、合成時丟引用與異議 |

[Iterative Audit Convergence 個案](https://www.mdpi.com/2674-113X/5/2/26)在九輪發現數為 `15, 8, 12, 2, 8, 1, 4, 1, 0`，顯示收斂不是單調的；而且 audit protocol 本身也在成熟，所以零發現不是數學 fixed point。該研究實際以一次 clean pass 停止，但建議後續複驗採兩次連續 clean pass；作者同時承認這只是單一系統個案。

多 agent 也不是天然的 completeness 機器。[MAST 研究](https://arxiv.org/html/2503.13657)分析 1,600 多條 trace、整理 14 種失效模式，其中包括不知道何時停、重複步驟、過早終止、不完整或錯誤驗證；明確 verifier 有幫助，但 verifier 只做表面檢查仍會放過真正錯誤，簡單 majority voting／cross-verification 的效果也不一致。

我建議 nova 的研究型完成契約是：

```text
完成候選 =
    所有使用者要求的覆蓋格都有內容
    AND 所有重要事實主張都有可讀來源支持
    AND 來源品質義務已滿足
    AND 連續 2 輪沒有新實質主張

完成 =
    完成候選
    AND 獨立 completeness critic 沒指出具體、實質缺口
    AND 引用驗證通過

護欄 =
    最大輪數／token／時間／工具呼叫／fan-out 任一到頂

中止 =
    必要工具、憑證或環境根本無法執行
```

兩輪 dry 是可配置保守值，不是真理。撞護欄時應交付「部分研究＋已知缺口」，標成護欄收場；不能把「不完整」轉成紅，再送回模型無限補。

建議形狀：

```text
界定問題 → 搜尋一輪 → 去重／更新覆蓋
                         ├─ 有缺口或尚未連乾兩輪 → 搜尋一輪
                         └─ 候選完整 → completeness critic
                                          ├─ 有具體缺口 → 定向搜尋，dry 歸零
                                          └─ 無缺口 → 引用驗證 → 綜合 → 完成
```

第一版甚至可以把多角度搜尋封裝在一個有硬 fan-out cap 的節點裡；等真的需要 barrier、partial result、獨立恢復，再升 graph。

## 5. nova 應該把抽象切在哪

**結論：應抽出「單游標工作流核心＝節點執行終局＋具名出口＋轉移表＋型別化工作狀態＋停止政策」，不要抽象成通用 `跑判準()->bool`，也不要現在就做完整 Graph layer。**

### 今晚事故的真正歸屬

| 層次 | 問題 | 修正 |
|---|---|---|
| Harness | launchd 找不到 `uv`，卻被解讀成測試紅 | `跑不起來` 與 `紅` 分開；而且應在第一個 LLM 呼叫前 preflight |
| Workflow selection | 研究任務進了 TDD | 第一版要求明確選 `tdd`／`research`；未選或不確定時 fail-closed，不能默認 TDD |
| Loop | 卡住偵測只懂重複的 pytest 紅，而且要先夾數次昂貴實作才看得見 | stagnation detector 必須由工作流提供：TDD 看相同 gate receipt，研究看 coverage/claim novelty |
| Graph | 沒有發生「正確節點因拓撲而沒被排程」 | 不是這次根因 |

目前工作樹已做了重要 containment：

- [`跑工作流`](/Users/sbu/nova/src/nova/迴圈/工作流.py:50)雖收 `階段表`，第 73 行立刻 `del 階段表`，後面仍查全域 TDD 表。

這正好指出切點：**執行能不能成功**與**成功執行後得到哪個領域出口**必須分開。

- 找不到 `uv`：`執行終局=確定失敗，出口=None`
- pytest 跑完且紅：`執行終局=成功，出口=紅`
- 研究搜尋跑完但無新發現：`執行終局=成功，出口=乾`
- critic 跑完指出缺口：`執行終局=成功，出口=有缺口`

### 建議的核心簽章

```python
from __future__ import annotations

from collections.abc import Callable
from dataclasses import dataclass
from enum import StrEnum
from typing import NewType

from nova.契約.工作流 import 任務, 停止條件, 結束, 預設停止
from nova.契約.模型回應 import 用量, 終局


節點代碼 = NewType("節點代碼", str)
出口代碼 = NewType("出口代碼", str)


class 節點種類(StrEnum):
    模型 = "llm"
    函式 = "fn"
    判準 = "gate"
    審查 = "review"
    人工 = "human"


@dataclass(frozen=True, slots=True)
class 節點定義:
    代碼: 節點代碼
    名稱: str
    種類: 節點種類
    允許出口: frozenset[出口代碼]


@dataclass(frozen=True, slots=True)
class 轉移:
    從: 節點代碼
    出口: 出口代碼
    到: 節點代碼 | 結束


@dataclass(frozen=True, slots=True)
class 工作流規格:
    代碼: str
    起點: 節點代碼
    節點表: tuple[節點定義, ...]
    轉移表: tuple[轉移, ...]


@dataclass(frozen=True, slots=True)
class 節點紀錄:
    節點: 節點代碼
    執行終局: 終局
    出口: 出口代碼 | None
    證據: str
    花費: 用量 | None = None


@dataclass(frozen=True, slots=True)
class 執行快照[S]:
    任務: 任務
    目前: 節點代碼
    狀態: S
    軌跡: tuple[節點紀錄, ...]
    已花token: int


@dataclass(frozen=True, slots=True)
class 節點輸出[S]:
    執行終局: 終局
    出口: 出口代碼 | None
    新狀態: S
    證據: str
    花費: 用量 | None = None


type 節點執行器[S] = Callable[
    [節點定義, 執行快照[S]],
    節點輸出[S],
]
type 前置檢查 = Callable[[任務], 結束 | None]
type 卡住判定[S] = Callable[[執行快照[S]], 結束 | None]


@dataclass(frozen=True, slots=True)
class 已組裝工作流[S]:
    規格: 工作流規格
    初始狀態: Callable[[任務], S]
    執行節點: 節點執行器[S]
    前置檢查: tuple[前置檢查, ...]
    卡住判定: 卡住判定[S]


@dataclass(frozen=True, slots=True)
class 工作流結果[S]:
    結束: 結束
    狀態: S
    軌跡: tuple[節點紀錄, ...]


def 跑工作流[S](
    任務: 任務,
    *,
    工作流: 已組裝工作流[S],
    停止: 停止條件 = 預設停止,
) -> 工作流結果[S]:
    ...
```

`工作流規格`仍是可印進 journal、可窮舉測試的資料；任意多個具名出口取代現在的綠／紅二分。Runner 只負責：

- 先跑全部 preflight。
- 維持一個目前節點。
- 執行節點。
- `結果未知`／確定失敗的共通安全語意。
- 依 `(節點, 出口)` 查轉移。
- token／步數／時間護欄、記帳與 trace。
- 呼叫該工作流自己的卡住判定。

### TDD 與研究只是兩個 adapter

```python
def 建TDD執行器(
    *,
    角色表: Mapping[節點代碼, 角色],
    跑判準: 判準,
```

### 切錯的代價

| 錯誤切法 | 代價 |
|---|---|
| 抽象成 `跑判準()->bool` | 再次把環境失敗、未知、領域不合格壓成 False，重演今晚事故 |
| 讓 Research 繼承 `BaseTDDWorkflow` | 被迫捏造「綠／紅」，completion critic 變成假測試 |
| 每種工作流複製一份 runner | token、未知結果、journal、護欄修復會分叉漂移 |
| 以 `dict[str, Any]`／自由文字做通用結果 | 每個下游重新解析模型文字，停止規則不可窮舉測試 |
| 現在直接做完整 Graph DSL | 尚未用到就先背負 scheduler、join、reducer、checkpoint、partial failure 的全部故障面 |
| 自動 router 低信心仍挑一個 workflow | 研究再次靜默落入 TDD；錯誤發生在最昂貴呼叫之前卻沒被擋住 |

最合適的演進順序是：

1. 把目前 TDD 行為以 characterization tests 釘住。
2. 抽出上述單游標核心，TDD 只換表示法、不改行為。
3. 增加「第一個 LLM 前」的判準可執行性 preflight。
4. 增加明確的 `tdd|research` 選擇與研究 workflow。
5. 研究的平行搜尋先封裝在一個有硬上限的節點內。
6. 等 trace 真的要求多個 active cursor、join、reducer 或跨程序 resume，再開 Graph layer。
