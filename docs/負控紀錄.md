# 固定負控紀錄

**這是紀錄，不是規範。** 規則本身住 CLAUDE.md 與 `docs/決策/`；
這份檔只回答一個問題：**這條防護，有沒有人親眼看過它紅？**

每一列都是做過一次的實驗：故意把實作弄壞，確認指名的那支測試真的會失敗，再改回來。
所以**下次有人懷疑同一條防護時不必重推**——照著「破壞什麼」那一欄做一次就好。

新增保證時做一次負控，寫進 commit 訊息，然後在這裡補一列。**不要往 CLAUDE.md 加列**
（理由見 [`docs/決策/0001-規則要住哪一層.md`](決策/0001-規則要住哪一層.md)）。

> 這其實是**手工版的 mutation testing**：改一個字元、看測試會不會抓到。
> 業界的機械版是 `cosmic-ray` 或 `mutmut`，會直接算出 mutation score。
> 目前沒導入，理由與前置問題寫在那份決策紀錄的「之後可能怎麼走」。

| `排程預算.旗標()` 回空的（預算進不了 `ProgramArguments`） | 排程單元三支＋`test_帶了預算旗標之後那行指令還是跑得起來` 紅。寫死的話，人在終端機打的每一次都擋得住，時鐘自己跑的那幾百次一次都擋不住 |
| 旗標跟數字塞成同一格 `"--預算token 500000"` | `test_每一格都是獨立的字串` 紅。`ProgramArguments` **不經過 shell** |
| `_子命令_排程` 自己算一次 `f"com.nova.{專案.name.lower()}"` | `test_印出來的檔名跟plist裡的Label是同一個` 紅。**兩份對照表就是這條 bug 的形狀**——專案名有空格或大寫時，印出來的安裝指令會給一個 `launchctl load` 不動的檔名，而那行字自己說「檔名要跟 Label 一致」 |
| `_問的前置` 不再叫 `_秘密先交出去` | `test_載進去的祕密會被用到` 等三支紅——憑證根本沒交到子程序手上 |
| 祕密載進 `dict(os.environ)` 而不是 `os.environ` | `test_祕密一個字都不准進帳本` 紅。**祕密會被用、但不會被遮**——遮罩讀的是 `os.environ`，這是一個沒有任何症狀的洩漏 |
| `遮罩` 不看 `NOVA_LOADED_SECRETS` 名單 | `test_名單上的鍵不管叫什麼都要遮`＋`test_祕密一個字都不准進帳本` 紅。`MY_THING` 撞不上「鍵名看起來是祕密」那條規則，只能靠名單 |
| `載入到` 不把鍵名記進名單 | 同上三支紅 |
| 權限太鬆只警告不擋 | `test_太鬆的時候載入要炸不是靜默跳過`＋`test_權限太鬆時整個不出生` 紅 |
| 錯誤訊息改成 `f"...{行}"`（把整行印出來） | `test_錯誤訊息不准把值印出來` 三個參數化案例紅。**祕密要放在出錯的那一行上**——第一版放在別行，那條路根本走不到，負控完全沒紅 |
| `nova 跑` 不落收件檔、直接把字串塞進工作流 | `test_敲的那句話會先變成一個收件檔`＋`test_撞到鎖時題目要留在佇列上` 紅。**那就是第二條執行路徑**——佇列上看不到、`ls` 查不到、撞到鎖就整個掉了 |
| `nova 跑` 先跑再落檔 | 上面兩支＋`test_敲一句話就會被做掉` 紅。撞到鎖時題目掉了，而使用者以為他派出去了 |
| 成果不記來源（`來源=""`） | `test_成果上看得出是誰觸發的`＋`test_手丟的檔案來源是檔案不是你敲` 紅。四個事件源收斂到同一個入口之後就分不出是誰敲的了 |
| `誰造的` 永遠回 `你敲` | `test_手丟的檔案來源是檔案不是你敲` 紅。**這條防的是全部標成你敲**——來源是「誰造了這個收件檔」，不是「誰醒來把它撈起來」 |
| `丟一件` 的檔名不帶時戳 | `test_開頭是讀得回來的時戳`＋`test_來源讀得回來` 紅。`待處理` 照檔名排序，時戳掉了「先進先出」就靜默壞掉，而佇列看起來完全正常 |
| 醒來完全不記（回到今天的狀態） | `test_需要你的事都在這.py` 六支紅。排程醒來的絕大多數在兩本帳上一筆都不留 |
| 空收件匣那條不填結果（從退出碼反推） | `test_收件匣是空的也要留痕跡` 紅。**反推不出來**：`0` 同時是「做完了」「收件匣空的」「撞到鎖讓開」 |
| 預算鎖擋下時不填結果 | `test_被預算鎖擋下要留痕跡` 紅。護欄生效不是壞了，**但它要看得見** |
| 跑完之後不用工作流自己的 `結束代碼` | `test_做完一件之後看得到`＋`test_人看得懂的那份也要印出來` 紅。兩套詞彙會讓人不知道哪個是真的 |
| 佇列深度改讀狀態檔裡的快照 | `test_佇列上還有幾件看得到` 紅。快照會過期——丟五個檔進去還說 0 |
| `讀現況` 不吃 `OSError` | `test_第一次跑的人不會看到錯誤` 紅。「還沒有狀態」是第一次跑的人的正常狀態，炸掉的話狀態列會一直閃紅 |
| 把「遮罩還不存在」那句舊註放回路線圖 | `test_不准說一個已經有的模組不存在` 紅。**第一版是綠的**——正規式 `([\u4e00-\u9fff]{2,6})(?:還)?不存在` 貪婪匹配抓到的是「而遮罩」，永遠不等於模組名。改成直接拿模組名拼字串比 |
| 成果帳的 `任務` 不過遮罩 | `test_使用者自己打進去的祕密也不准進成果帳` 紅 |
| 歸檔的 `.收件` 不過遮罩 | 同上一支紅。「原文」的意思是「當初丟進來的是什麼」，不是「連憑證一起留一份」 |
| 把 serial 佔比門檻改成 0.1% | `test_預設門檻為百分之八` 與 `test_佔比低於門檻放行` 紅 |
| 拿掉判準對 pytest 4／5 的映射（退回全當紅） | `test_沒收集到任何測試是跑不起來`、`test_用法錯誤是跑不起來`、`test_真pytest在沒有測試的目錄回跑不起來`、`test_真pytest旗標打錯回跑不起來` 紅。**exit 5「沒收集到任何測試」正是「研究題誤進 TDD 工作流」的形狀**——當紅回報就會一路回去「再實作一次」 |
| 讓 `_像pytest` 無條件回 `True` | `test_不是pytest的指令退出碼5仍是紅` 紅。退出碼語意是各程式自己的知識（nova 自己的 4 是「護欄生效」），無條件翻譯等於把別人的回饋偽裝成環境問題 |

## 跑負控之後一定要清 `__pycache__`

2026-08-29 被咬兩次：程式碼還原了、直接求值也對，**但測試持續紅在同一行**。
原因是 `__pycache__` 還是被破壞過的那份。

```bash
find src tests -name __pycache__ -type d -exec rm -rf {} +
```

**「還原後還是紅」有兩種成因**：真的沒還原、或是快取。兩者長得一模一樣，
而後者會讓人去追一個不存在的 bug。清掉再驗，兩秒的事。

## 一次「負控沒紅」的紀錄（2026-08-29）

「門面改成不給目錄也開帳本」這條**第一次跑的時候沒有紅**——當時的斷言看的是
`tmp_path`，而帳本其實寫到了 `~/.local/state/nova/帳本/`（73 個檔案）。
**測試看錯地方，所以它守不住任何東西。**

修法有兩層：斷言改看 `預設帳本目錄()`，並加一支 autouse 的
`帳本不准寫到家目錄` fixture 把預設目錄整個導進暫存區。沒有那支 fixture，
這條保證在測試裡根本驗不了——真的寫了也不在測試看得到的地方。

教訓：**負控沒紅不代表防護沒問題，也可能是測試沒對準。**
兩者長得一模一樣，只有真的去看檔案才分得出來。

### 第二次（2026-08-29，生圖）

「生圖的提示不叫它搬進工作目錄」這條也沒紅。原因同一類：斷言掃的是**整串 argv**，
而 `--add-dir` 本來就會把工作目錄放進去——**把提示裡那句話整個拿掉，測試照樣綠**。

修法：只看提示那一個參數（用 `generate_image` 這個關鍵字認出它），不看整串。

兩次都是同一個形狀：**斷言的範圍比要守的東西大**。範圍一大，
別的東西就會替它成立，於是防護拆掉了測試也不知道。

### 第三次（2026-08-29，逾時截斷）

`test_太長要截斷` 餵 10 萬字進去，但用的假解析器**會回一段短文字**，
而實作是 `半成品.文字 or 部分標準輸出`——短文字是真值，那 10 萬字根本沒走到截斷那一行。
把截斷整個拿掉，測試照樣綠。

三次都是同一句話的不同寫法：**測試沒有真的碰到它要守的那段程式碼。**
第一次是斷言看錯目錄，第二次是斷言掃的範圍太大，第三次是輸入根本到不了那條分支。

所以負控要看的不只是「有沒有紅」，還有**紅的是不是那一支**。

### 第四次（2026-08-30，程序收割的管線那一支）

`test_孫程序抓著管線不准讓收屍卡住` 的 docstring 原本寫「守的是收割後多一句
`communicate()`」。單獨把那句加回去——**綠的，1.09 秒**。
因為收割已經先把孫殺了，第二次讀立刻拿到 EOF。

要連 `start_new_session=True` 一起拿掉才紅（4.4 秒）。所以那支測試真正守的是
**「不准有活著的後代抓著管線」**，不是「不准再 communicate 一次」。
docstring 照這個結論改掉了。

這次和前三次不一樣：**測試有碰到它要守的程式碼，是我對它守什麼描述錯了。**
一支只在兩項同時壞掉才會紅的測試不是沒有價值，但**它的 docstring 必須講明這件事**
——否則下一個人會以為單改一項有防護。

### 第五次（2026-08-30，破壞根本沒套用）

跑「`列出成果` 拿掉 `reverse=True`」時看到綠的，一度以為 `test_最近的排前面`
守不住東西。實際上是**破壞本身沒生效**：改寫腳本用
`python3 -c "...s.replace(...)..."`，殼把引號吃掉之後比對字串對不上，
而 **`str.replace` 找不到就靜默回原字串**。檔案根本沒變，跑的還是好的那份。

改成引號 heredoc（`python3 - <<'PY'`）並加一行
`assert 新 != s, "替換沒生效"` 之後，同一條負控當場紅。

前四次是「測試沒碰到要守的程式碼」，這次是**破壞沒碰到程式碼**——
方向相反，但症狀一模一樣：綠的。所以負控腳本一律要斷言「我真的改到了」，
不要只看測試結果。同一類的還有查 ruff 快取假綠那次：用「改內容再跑一次」去驗，
mtime 會跟著變，坑就不成立了——**測法把要測的東西填掉了**。

### 第六次（2026-08-30，負控驗的是跑完就丟的臨時斷言）

派 nova 做成本落盤那輪，`負控紀錄` 一次進了七列，其中**六列寫著
「固定 smoke assertion」**——意思是負控是對著一段臨時寫、驗完就刪的斷言做的。

那不是負控。**負控要證明的是「repo 裡的某支測試會紅」**；斷言不留下來的話，
被證明的那個保證在下一次改動時沒有任何東西守著。而且它比沒做更糟：
紀錄上看起來有七道防線，實際只有一道。**在「防止假安全感」的文件裡製造假安全感。**

實際的洞：那一輪只留下一支真測試，而且它只斷言「混著有跟沒有的時候是 `None`」。
把實作改成 `總成本美金 = None`（永遠不讀成本）——**全綠**。
補上 `test_全部都有成本時總成本是加總` 之後，同一個破壞當場紅。

所以往後：**負控那一列裡的測試名，必須是 repo 裡搜得到的名字。**
搜不到就代表那一列在說謊。

### 第七次（2026-08-30，負控沒紅但實作是對的）

預算鎖那輪的第三條負控——拿掉 `_窗口內的執行` 的檔名時戳過濾——**綠的**。

原因不是實作錯了：時間過濾本來就由 `花了多少` 做，檔名過濾是**純效能最佳化**
（別把三個月前的幾千個帳本檔全開起來讀）。所以「窗口外的不算」那支測試
拿掉最佳化照樣綠。

但這一格仍然是假保證：**那段程式碼沒有任何測試守著，下一個人會很合理地把它刪掉**，
然後每次呼叫前都把整個專案的帳本讀完——一個沒有人會發現的成本漏洞。

修法不是刪掉那段程式碼，也不是接受負控是綠的，而是**把它的真行為釘住**：
它改變的是「開幾個檔」，就寫一支數開檔數的測試（`test_三個月前的帳本不會被開起來`，
monkeypatch `nova.載體.命令列.讀一次執行` 計次）。補上之後同一個破壞當場紅，40 vs 1。

前六次都是「負控該紅卻綠」＝實作有洞。**這次是「負控該紅卻綠」＝測試有洞**——
症狀一樣，位置相反。所以負控綠掉的時候要先問完兩題再動手：
**是實作沒做到，還是這條保證根本沒人守？**

順帶一個 monkeypatch 的坑：`from x import y` 之後，呼叫端查的是**自己模組裡**的
那個名字。打在來源模組 `nova.載體.帳本讀取.讀一次執行` 上不會有任何效果——
改了、測試綠、其實沒接上，就是「用規避換來的假綠」。要打在
`nova.載體.命令列.讀一次執行`。

**同一次的兩個補課。** 上面那兩列第一次做的時候都是綠的，原因各不相同：

- `_檔名時戳` 那條：我挑的破壞（`%Y-%m-%d…`）剛好落在**另一支**測試的守備範圍
  （它讓過濾不再排除任何東西，是效能退化不是算錯），而我只跑了一支。
  **負控綠掉先問「是保證沒人守，還是我挑的破壞打歪了」**——跑整個檔案就看得出來。
- 收件匣那條：斷言寫成 `"一件.md" in stdout`，而 `nova 收件` **連 `處理中/` 也印**
  （印成「⚠ 沒收尾」），所以搬走了照樣綠。**斷言要分得出好狀態與壞狀態**，
  「名字還印得出來」不是「它還在等」。改成 `"等著  一件.md" in` 加上
  `"沒收尾" not in` 之後當場紅。

### 第八次（2026-08-30，祕密放在不會出錯的那一行）

「錯誤訊息不准把值印出來」第一版寫成：

```python
讀祕密("A=1\nB C\nGOOD_KEY=超級機密的值\n")   # 壞的是第 2 行
assert "超級機密的值" not in str(錯)
```

第 2 行 `B C` 一報錯就停了，第 3 行根本沒被讀到。**那個祕密不在任何一條
可能被印出來的路徑上**，所以把訊息改成 `f"...{行}"` 也不會紅。

同一類的還有第七次那個「我挑的破壞打歪了」。合起來是一條：
**負控要打在被測的那一格上，測試資料也要放在被測的那一格上。**
祕密要放在出錯的那一行；改壞的要是那支測試真正守著的那段。

改法：`parametrize` 三種壞行，每一種的祕密都在出錯的那一行上
（整行看不懂、鍵名不合法、鍵裡有空白），兩個方向的破壞都當場紅。

### 第九次（2026-08-30，負控腳本自己跑到系統 Python）

`nova 跑` 那五條負控第一次全部「紅 ✓」——**而且全是假的**。訊息是：

```
/Library/Developer/CommandLineTools/usr/bin/python3: No module named pytest
```

腳本用 `python3 - <<'PY'` 起（前一輪 hook 擋掉 `uv run` 之後順手換的），
於是 `sys.executable` 是系統的 3.9，pytest 根本沒裝。**五次「紅」的理由
都不是那條保證失效，是測試套件根本沒跑起來。**

CLAUDE.md 早就寫著「一律走 `uv run`，忘了會靜默跑到系統 Python 3.9」——
這次是它在**驗證腳本**上發作。驗證腳本比被驗的程式碼更容易漏掉這條，
因為它「只是個腳本」。

所以負控腳本從此要斷言兩件事，跟「我真的改到了嗎」並列：

```python
assert "/.venv/" in sys.executable, f"跑到系統 python 了：{sys.executable}"
assert "No module named pytest" not in 尾, "又跑到系統 python 了"
```

前八次問的是「這個紅是真的嗎」。這次要多問一句：**這個紅是因為我要測的那件事嗎？**

### 第十次（2026-08-30，量法只掃了一半，剩下那一半就是洩漏的地方）

`test_祕密一個字都不准進帳本` 的量法第一版寫成「掃 `帳本/` 與 `已處理/`」，
理由是要避開祕密檔自己（它就住在同一個專案目錄底下）。那支測試一直是綠的。

結案盤點時真的跑一次、然後 `grep` 整個狀態目錄，才發現**祕密躺在
`已處理/*.json` 的 `task` 欄位裡**——模型講的那句話被遮了，
使用者自己打進去的那句話沒有。

為什麼那支測試沒抓到：它讓假模型**複述祕密**，所以驗的是「模型的回應有沒有被遮」。
題目那一半從來沒有真的檢查過——兩本帳合起來掃，其中一本的漏洞會被另一本的
綠掩蓋掉。改成分開量（`_只有事件帳本` 與 `_成果帳裡的全部字`）之後，
新測試當場紅。

原本的理由「任務已經在 `ps` 的 args 上，記它沒有多開一條路」在兩個方向上站不住：
`ps` 的 args 是程序活著的那幾秒，`已處理/` 是躺在磁碟上直到有人刪掉；
而**收件匣那條路根本不經過 `ps`**——題目來自一個檔案。

教訓跟第七、九次同一族，但這次在**量法**上：
**一個把兩個對象合起來算的斷言，只證明了「至少有一個是乾淨的」。**

### 第十一次（2026-08-30，接續：三條都紅，但偵測腳本的比對字串打錯）

新增「撞到上限自動接續」時做的三條固定負控：

| 破壞什麼 | 該紅的測試 |
|---|---|
| `_也許接著排` 的判準 `碼 != 護欄碼` 放寬成 `碼 == 放行`（非 0 就接續） | `test_結果未知不准排回去` |
| `收件.最多輪次` 從 3 改成 999 | `test_輪次用完就停下來等你` |
| `接著排` 裡的 `遮罩(前情).文字` 改回 `前情` | `test_祕密一個字都不進接續票` |

三條都紅。**但第一次跑的時候第三條被報成「沒紅」**——腳本用
`該紅的 in 尾` 判斷是不是紅在該紅的地方，而我在腳本裡把那個測試名
多打了一個「准」字。pytest 的輸出裡當然找不到，於是一條真的紅被記成假綠。
（那個打錯的名字這裡不照抄，`test_文件提到的測試都真的存在` 會把
文件裡出現的每一個測試名都當成宣稱去查——它抓到過這一條。）

教訓跟第七到第十次同一族，但位置又換了一層：
**這次錯的不是測試、不是破壞、不是量法，是「判斷紅得對不對」的那個字串。**
負控腳本裡每一個用來比對的名字，都要先對著來源檔斷言它存在：

```python
assert 該紅的 in pathlib.Path(測試檔).read_text(encoding="utf-8"), "測試名打錯"
```

第一條負控是這一批裡最要緊的那條。它守的是使用者親自畫的那條線——
**「撞到上限的自動接著做，被殺掉的等我看」**。退出碼 3 的意思是
「不知道工作做了沒」，自動重排會把可能已經做過的事再做一次；
判準寫成「非 0 就接續」的話兩支測試裡只有一支會紅，而那一支正是這條。

### 第十二次（2026-08-30，預設走 nova 的 hook：五條）

`nova 檢查編輯` 掛在 agent 的 `Edit`／`Write` 上，沒說出理由就擋下編輯。

| 破壞什麼 | 該紅的測試 |
|---|---|
| `_子命令_檢查編輯` 不印那段 JSON（殼變裝飾） | `test_改repo裡的檔案要先說理由` |
| `說得出理由了嗎` 反過來（有記號才擋） | `test_繞過之後同一個session就不擋了` |
| `記下繞過` 收下空理由 | `test_理由是空的不算說過` |
| `在管轄範圍嗎` 連點開頭的地盤也管 | `test_點開頭與暫存工作區的地盤不管` |
| 擋下來時退出碼改回非零（fail-closed 化） | `test_真的擋下來的時候也是零` |

五條都紅。

**最後一條是這一批的核心。** 這一支跟 `檢查指令` 的方向**刻意相反**：

| | `檢查指令`（禁令） | `檢查編輯`（預設走 nova） |
|---|---|---|
| 守什麼 | 不可逆的動作 | 一個**預設值** |
| 讀不懂輸入 | fail-closed | **fail-open** |
| 怎麼擋 | 退出碼 2 | **印 JSON**，退出碼永遠 0 |

理由是這一支掛在 `Edit`／`Write` 上，而**修 nova 的唯一辦法就是編輯 nova 的檔案**。
用退出碼擋的話，`uv run` 自己失敗（venv 沒建好、import 錯）跟「故意擋下」
在退出碼上分不開，於是 nova 一壞就再也修不回來。2026-08-30 這件事真的
發生過兩次——那次掛在 `Bash` 上，還能用 Edit 逃出來；掛在 Edit 上沒有逃生口。

**已知不管的：走 `Bash` 寫檔（`sed`、heredoc、`cat >`）繞得過去。**
不去補：判斷一條 shell 指令有沒有在寫檔是判不準的，而 `禁令.py` 的立場同樣適用
——這裡的對象不是對手，是**會手滑的執行者**。文件不准宣稱有把關器而沒有，
所以這條限制寫在這裡也寫在模組 docstring 裡。

### 第十三次（2026-08-30，活動監視器上的名字：四條，其中一條揭出多餘的程式碼）

`nova 排程` 的 `ProgramArguments[0]` 從 console script 換成硬連結出來的
專用直譯器 `.venv/bin/nova-inbox`，這樣活動監視器才看得出是誰。

| 破壞什麼 | 該紅的測試 | 結果 |
|---|---|---|
| 第一格改回 console script | `test_啟動器自己的kernel名字是nova開頭` | 紅 ✓ |
| `確保啟動器在` 改成建符號連結 | `test_跟著符號連結走到真的那份` | 紅 ✓ |
| 已經在就不對 inode | `test_直譯器換掉之後啟動器要跟著換` | 紅 ✓ |
| 拿掉 `-m nova` | `test_那行指令整條真的跑得起來` | 紅 ✓ |

**第二條第一次跑的時候沒紅，而我對它的判讀是錯的。** 原本的破壞方式是把
`真身 = 直譯器.resolve()` 改成 `真身 = 直譯器`，預期「不跟符號連結走」會出事。
在我這台 macOS 上它沒出事，於是我當成「那行本來就不做事」，把 `resolve()` 刪了。

**CI（Linux）當場紅。** 硬連結會不會跟著符號連結走**兩個平台不一樣**：
macOS 會，Linux 不會。那行不是多餘的，是**在我跑負控的那個平台上剛好看不出來**。

所以真正的教訓是：**固定負控只在一個作業系統上跑。** 一條保證在 macOS 上
「破壞了也沒事」，可能只代表 macOS 幫你兜住了。這一族的問法要多一句——
「我真的改到了嗎 → 我的紅是因為要測的那件事嗎 → **我只在一個平台上問過嗎**」。

修法不是把 `resolve()` 加回去就算了，而是**不要依賴那個平台差異**：
自己 `resolve()`，兩個平台的行為就一樣了。破壞方式也換成
「改建符號連結」（`hardlink_to` → `symlink_to`），那是這支測試真正守著的東西
（`assert not 落點.is_symlink()`），在哪個平台都紅。

### 第十四次（2026-08-30，判準「跑不起來」被當成「紅」，燒掉 172 萬 token）

**這一次的成因是先發生了損失才被發現的**，不是先寫測試。真實 trace：

```
排程在 launchd 底下跑。launchd 不跑登入 shell，PATH 是
/usr/bin:/bin:/usr/sbin:/sbin——而 uv 住在 ~/.local/bin
      ↓
判準 `uv run pytest -q` → FileNotFoundError
      ↓
當時的實作：`return False, f"判準指令跑不起來：{錯}"`  ← 被當成「紅」
      ↓
狀態機看到判準紅 → 走紅邊 → 回去「再實作一次」（叫模型，最貴的一步）
      ↓
再驗一次 → 還是跑不起來 → 再實作 → ...
      ↓
第 3 次才被卡住偵測器停下。單次 997,031 token，三次醒來共 1,720,140
```

而 `狀態機.下一步` 裡還有一條特例讓它更糟：

```python
if 結果.終局 is 終局.確定失敗:
    if 定義.種類 is 種類.判準:
        return 定義.紅        # ← 判準壞掉也走紅邊
```

**兩層都把「環境壞了」翻譯成「測試沒過」。** nova 自己的診斷順序寫著
**環境 → 回饋 → 流程**：綠與紅是回饋，跑不起來是環境。壓進同一個 `bool`
就是把環境問題偽裝成回饋，而**環境問題重跑一百次還是同一個環境**。

| 破壞什麼 | 該紅的測試 |
|---|---|
| 把「判準確定失敗走紅邊」的特例加回 `狀態機.下一步` | `test_跑不起來不准走紅邊` |
| `建判準` 的 `OSError` 改回 `判準終局.紅` | `test_指令不存在是跑不起來` |
| plist 的 `EnvironmentVariables` 拿掉 `PATH` | `test_排程的環境跑得起預設判準` |

三條都紅。

**逾時刻意留在「紅」**：它分不出是環境壞了還是測試真的卡住，fail-closed
當紅是既有的決定，卡住偵測器會在第 3 次擋下來。這條寫成
`test_逾時還是當紅`，是**刻意不修**的宣告，不是漏掉。

教訓：**「假的安全感比沒有規範更糟」在這裡的形狀是「判準看起來在守著，
其實它連跑都沒跑」。** 而讓它變貴的不是那個錯，是**把它翻譯成一個可以重試的
錯**——可重試的錯每重試一次就叫一次模型。

### 第十五次（2026-08-30，研究存檔的抬頭：四條）

`docs/研究/` 的 README 寫著「每份開頭要寫誰產的、什麼時候、用什麼題目問的」。
**只寫在 README 裡的規矩等於不存在**——下一份研究存進來的人不會讀它。

| 破壞什麼 | 該紅的測試 |
|---|---|
| 拿掉「產出者：」那行 | `test_寫得出誰產的` |
| 拿掉日期 | `test_寫得出什麼時候` |
| 拿掉「問法：」 | `test_寫得出當初問了什麼` |
| 拿掉「不是 nova 的設計決定」那句 | `test_講明是外部資料不是我們的決定` |

四條都紅。

**這一批的順序是反的**（先寫好抬頭、再補測試），所以負控不是「補做」而是
**唯一的證明**。先有實作再寫的測試，不做負控就完全不知道它在測什麼——
它可能只是在覆述已經成立的事實。

另外多加了一支 `test_研究目錄有東西`：`parametrize` 吃空清單時
**一支都不跑，而零支測試也是綠的**。那是這種寫法特有的假綠。

### 第十六次（2026-08-30，背景派工看得見：五條，其中一條又是路徑裡的測試名）

`nohup uv run nova 問 … &` 派出去的研究**使用者的介面上什麼都看不到**。
第一版的修法是「以後改用 harness 的背景任務功能」——那是懇求，而且更糟：
那個功能是 Claude Code 的，換一個 harness 就整個消失。
改成 `nova 問 --背景` ＋ `nova 狀態` 列出「有發出去、還沒寫下結果」的執行。

| 破壞什麼 | 該紅的測試 |
|---|---|
| 背景不印識別碼 | `test_印得出識別碼與輸出檔` |
| `--背景` 改成前景跑 | `test_背景跑起來就立刻回` |
| 背景與帳本各編一個號碼 | `test_印出來的識別碼就是帳本上那個` |
| `nova 狀態` 不列還在跑的 | `test_有開始沒結束的會被列出來` |

四條都紅——**但前兩條第一次跑的時候都沒紅**：

1. `test_印得出識別碼與輸出檔` 斷言 `"識別碼" in stdout`，而 `tmp_path`
   的路徑裡有**測試自己的名字**，那三個字本來就在 stdout 上。
   **這是今晚第三次同一種假綠**（前兩次是 `"前情"` 與 `"還在跑"`）。
   改成**驗值不驗標籤**：把識別碼取出來對正規式，並確認輸出檔真的存在、
   檔名就是識別碼。
2. `test_背景跑起來就立刻回` 用「花了幾秒」當判準，而假 CLI 快到前景跑
   也在一秒內結束。改成**「模型的答案不在父程序的 stdout 上」**——
   那才是「丟出去了」的證據。

第五條（`NOVA_RUN_ID` 不驗格式就照收）**目前沒有測試守著**，誠實記在這裡：
亂設一個殘留的環境變數會讓所有執行共用同一個檔名，靜默把帳蓋掉。

### 第十七次（2026-08-30，思考深度：統一介面上的旋鈕，三家各自實作）

`max` 是**思考深度**，`gpt-5.6-luna` 才是型號。查下去發現三家都有這個旋鈕，
只是機制完全不同，而 nova 原本**把 codex 的深度寫死成 `max`**：

codex    -c model_reasoning_effort="<level>"    原本寫死 max
agy      包在型號後綴 gemini-3.7-flash-high      只有 low, medium, high

| 破壞什麼 | 該紅的測試 |

| agy 給不到的深度自動降級成 high | `test_agy沒有那幾階就當場炸` |

使用者會以為叫到了最深——帳照付、深度沒開、沒有任何訊息。**
那是「假的安全感」在這個旋鈕上的形狀。

三條都紅。

### 第十九次（2026-08-30，長提示不准走 argv：把一個記憶變成殼）

2026-08-30 派三份研究，提示直接寫在雙引號字串裡：

| | 發生什麼 |
|---|---|
| 有 `agent(prompt, opts)` 這種括號 | zsh **當場 parse error**，exit 1 |
| 有 `` `docs/設計/` `` 這種反引號 | **靜默汙染**——那五段被替換成空字串 |
| 剛好沒有 | 正常 |

**最貴的是中間那個**：沒有報錯、程序正常啟動、燒完整的 token，
然後交出一份對著殘缺題目寫的答案。當場失敗的那個反而便宜。

我的第一個修法是寫進記憶——使用者當場指出「不然就都只是記憶」。

**偵測不可能**：反引號被吃掉之後那段字完全消失，nova 收到的是一份
看起來正常的短提示，它無從分辨「本來就沒有那段」跟「那段被吃掉了」。
所以只能**改通道**：`--提示檔` 與 stdin 都不經過 shell 解析，
argv 是唯一會被展開的那條——長提示一律禁走 argv。

| 破壞什麼 | 該紅的測試 |
|---|---|
| 換行不擋 | `test_含換行就擋` |
| 訊息不給替代方案 | `test_兩條安全的路都要講` |
| `--提示檔` 被忽略（又回去讀 argv） | `test_提示檔多行多長都可以` |
| `跑` 不接同一份規則 | `test_跑也擋得住多行` |

四條都紅。

**型別也在替我們記事情**：`讀提示(*, argv片段, 提示檔)` 兩個關鍵字**都是必填**
（`提示檔` 可以是 `None`，但要傳）。給預設值的話，忘了接 `--提示檔` 的
子命令會安靜地只剩下危險的那條路——而那正是這個模組要防的事。
少傳一個在 mypy 就紅，不必靠人記得。

**規則不精確是刻意的**：`"$(cat 檔)"` 其實安全，卻也被擋。nova 站在邊界上
分不出安全的組法與危險的組法，而被擋下來的用法有一個嚴格更好的替代。

順帶修掉一個測試設計問題：那六支紅的測試第一次跑了 **224 秒**，
因為守衛還不存在，`--用 codex` 一路走到真的模型。改成一律帶假 CLI
——**測試在防護退化時的行為也是行為**。

## 2026-08-30：遮罩型別化（決策 0002 的第一個實例）

四個落盤點各自記得呼叫 `遮罩()`，2026-08-30 發現**四個裡漏了一個**（PR #95）。
修法是把「必須記得的事」變成「不得不傳的型別」：落盤點收 `已遮罩文字`，
餵裸 `str` 在 mypy 就紅。

| 破壞什麼 | 該紅的測試 |
|---|---|
| `成果.任務` 改回裸 `str` | `test_型別真的擋得住沒遮過的字[成果.任務]` |
| `帳本.事件.文字` 改回裸 `str` | `test_型別真的擋得住沒遮過的字[帳本.事件.文字]` |
| `_接續票內容` 的 `前情` 改回裸 `str` | `test_型別真的擋得住沒遮過的字[收件._接續票內容 的前情]` |
| `_寫下遮過的` 的 `文字` 改回裸 `str` | `test_型別真的擋得住沒遮過的字[收件._寫下遮過的 的文字]` |
| 歸檔繞過落盤入口自己 `write_text` | `test_收件的落盤只准走遮過的那個入口` |
| 在 `遮罩.py` 以外的檔案硬轉 `已遮罩文字(…)` | `test_不准在遮罩以外的地方硬轉` |
| `已經遮過了` 的 `因為` 給預設值 | `test_因為是必填的關鍵字` |
| 拿掉空理由的檢查 | `test_空理由不算理由`（3 支） |
| 閘的 mypy 拿掉 `--no-incremental` | `test_閘的mypy規則不會被假快取騙過去` |

九條都紅，而且**每條只紅指名的那一支**。

### 第一次跑的時候九條全部顯示「沒紅」——兩個獨立的原因

**① 比對器寫錯（我的問題）**：pytest 只把 parametrize id escape 成 `\uXXXX`，
測試函式名不會。我把兩者都 escape，期望字串永遠對不上。

**② mypy 的快取給了假結果（真缺陷）**：③ 與 ④ 兩條負控紅的都是③那一格。
成因是 **mypy 的快取鍵是路徑＋大小＋`int(mtime)`**，只在 mtime 對不上時
才去比內容雜湊——而那兩次破壞（`已遮罩文字` → `str`，各差 2 個字元）
讓檔案長度**完全相同**（6685 bytes），又落在同一秒。

這比 ruff 那條更容易踩：**連保留 mtime 的動作都不需要，同一秒內改兩次就中**。
人手改檔碰不到，腳本或 agent 連續改檔一定碰得到。
所以閘的 mypy 也帶 `--no-incremental`（146 個檔 0.07 → 1.09 秒），
測試裡自己跑的那個 mypy 也帶。由 `tests/整合/test_閘不准吃快取.py` 背書
（重現一支、閘一支，跟 ruff 同構）。

**教訓**：負控沒紅時先問「我的量法會不會就是成因」——這次兩個原因都在量法那邊，
而其中一個是真的缺陷。

## 2026-08-30：撞號不准靜默（三個落盤點）

執行識別碼撞號時三處都不出聲：帳本 `"a"` 交錯合併、`已處理/` `write_text`
靜默覆寫、背景輸出 `"w"` 靜默截斷。而且撞號**不是只有機率問題**——
`NOVA_RUN_ID` 只驗格式不驗歸屬，背景派工又會把它交給子程序，
一個殘留的值就是必然撞號。

| 破壞什麼 | 該紅的測試 |
|---|---|
| `開帳本` 的 `"x"` 改回 `"a"` | `test_同一個識別碼開第二次要當場炸`、`test_撞號的退出碼是確定失敗` |
| `歸檔` 的 `open("x")` 改回 `write_text` | `test_同號歸檔第二次要當場炸`、`test_第一份成果不准被蓋掉` |
| 背景輸出的 `"x"` 改回 `"w"` | `test_同號的背景輸出檔不准被截斷` |

三條都紅，而且**每條只紅指名的那幾支**。
**退出碼釘在 1（確定失敗）**：開檔當下還沒叫過模型、沒有副作用，重跑安全；
3 的語意是「不知道做了沒、不准重跑」剛好相反，4 是工作流停止規則專用。

### 第一次跑的時候三條都「多紅了別支」——`__pycache__` 給了假結果

**這是今晚第三個「快取鍵不含內容」的坑**（前兩個是 ruff 與 mypy），而且最嚴重：
它讓**跑的不是你剛寫回去的那份程式碼**。

Python 判斷 `.pyc` 新不新鮮，看的是它記在檔頭的
**source 的 `size` ＋ 整數秒 `mtime`**，不含內容。而這次的破壞是
`open("x")` → `open("a")`——**一個字元換一個字元，size 完全不變**；
還原又落在同一秒，於是：

```
pyc 記的 source mtime=1788060537 size=9484
py  實際的      mtime=1788060537 size=9484   → 判定新鮮，用舊的
```

症狀最難認的地方：`inspect.getsource()` 讀的是 `.py`，**印出來是新的**；
執行的是 `.pyc`，**跑起來是舊的**。所以「程式碼明明改了、行為就是不變」，
而且怎麼看原始碼都看不出問題。追了大約 15 分鐘。

`PYTHONDONTWRITEBYTECODE=1` **只擋寫、不擋讀**，舊的 pyc 照樣會被撿起來用。
唯一可靠的是**把 `__pycache__` 刪掉**。負控腳本現在每一輪都先清一次。

實測代價：`pytest tests/單元` 有 pyc 0.86 秒、冷編 1.02 秒（差 0.16 秒）。
所以閘的 pytest 規則跑之前一律清掉 `src/` 與 `tests/` 的 `__pycache__`。

| 破壞什麼 | 該紅的測試 |
|---|---|
| 閘的 pytest 不再清 `__pycache__` | `test_pytest的閘跑之前會把pycache清掉` |

**這條的第一版是假綠。** 測試原本直接呼叫 `_丟掉pycache(專案根目錄)`
再斷言目錄空了——負控當場證明：把閘裡那一行呼叫刪掉，它照樣過。
測到的是**函式本身**，不是**它被接上去了沒**。改成走 `建規則表` 真的跑一次
閘的 pytest 規則之後才紅得起來。

**教訓（第二次寫下同一句）**：負控沒紅、或紅到別支時，
先問「我的量法會不會就是成因」。今晚三次負控異常，三次都在量法那邊，
其中兩次是真的缺陷（mypy 快取、Python pyc）。

## 把轉移表變誠實那一輪（出口窮舉 ＋ `階段表` 參數）

| 破壞什麼 | 結果 |
|---|---|
| 從 `TDD階段表` 某一列拿掉一種出口（`結果未知`） | **匯入 `狀態機.py` 當場 `ValueError: test 的出口沒窮舉：缺 ['unknown']`**，8 個測試模組 collection error。機制本身由 `test_少宣告一種出口就建不出階段定義` 背書 |
| `跑工作流` 的索引改建自全域 `TDD階段表`（等於又忽略參數） | `test_傳進去的表真的會被走` 等 3 支紅（就是 `Test階段表真的是傳進來那一張` 那一整組，其餘 567 支全綠） |
| 把「寫一支會紅的測試」的 `結果未知` 從護欄接成中止 | `test_結果未知在每個階段都是護欄`、`test_結果未知是護欄不是壞掉`、`test_任何階段結果未知都要停`、`test_結果未知當場停` 共 4 支紅 |

**第一條的紅不是「一支測試紅」，是整個模組匯不進來。** 那正是這條保證要的形狀
（「建表當下就炸」），但它會**淹掉別的紅**——所以指名的執法點是那支自己組一個
缺格 `階段定義` 的測試，它不必把正典的表弄壞就證得出訊息說得出少了哪一格。

## 2026-08-30：`nova 重構`——第一個能單獨叫的節點

使用者的話：「worker 內的每一個節點都應該也是可以單拆出來使用……而且也都能隨時組裝。」

在它存在之前，要重構只有兩條路：跑整條 TDD 七階段（貴、慢、表達不了
「只整理這個模組」），或者自己動手。**第二條便宜一個數量級**，
所以護欄擋不擋得住不重要——沒有人會走那條貴的。給路跟補洞是同一件事的兩半。

護欄的判準是**跑之前拍一張快照、跑之後再拍一張**，不是「模型說它沒改」。
重構員的提示第一條就寫著「不准改任何測試檔」，但那是懇求：模型可以忽略，
而且忽略了沒有人會發現——測試被改掉之後跑起來還是綠的。

| 破壞什麼 | 該紅的測試 |
|---|---|
| 護欄只比內容（不看新增與刪除） | `test_刪掉一支測試是最嚴重的那種`、`test_新增測試也算動到` |
| 護欄不濾非測試路徑（改實作也算違規） | `test_改實作不算動到測試` |
| 子命令跑完不比對快照 | `test_動到測試檔就回護欄`、`test_護欄要說得出動到哪一個檔` |
| 重構不帶角色提示（變成裸的 `nova 問`） | `test_重構要把重構員的規矩交出去` |

四條都紅，而且每條只紅指名的那幾支。

**兩層都要有，缺一不可**：只有護欄的話模型每次都會踩（事後攔截，token 已經花了）；
只有提示的話它踩了沒人知道。前者是實線的包圍環，後者是事前告知。

**刪除為什麼要單獨列**：它在「逐檔比對內容」裡長得像什麼都沒發生——
那個鍵直接消失了。少了這一條，重構員把礙事的測試刪掉就過關。

## 2026-08-30：Bash 護欄改看行為（**第一件真的用 nova 做完的實作**）

hook 有兩條 PreToolUse：`Edit|Write|NotebookEdit` 走 `nova 檢查編輯`（會擋、
要求走 nova 或記繞過理由），`Bash` 走 `nova 檢查指令`（只擋三條禁令，
完全不看寫了什麼檔）。於是 `python3 - <<'PY' … write_text(…) PY` 一路綠燈，
而用 Edit 改同一個檔會被擋——**護欄的判準是工具名，不是行為**。

這一輪是**交給 `nova 跑` 做的**：測試員寫了 214 行 15 支測試（275,600 token，
撞護欄停在實作前）；`--起點 impl` 接著跑第二輪 5 階、674,254 token，
實作、驗證綠、重構都做完，48 支測試綠、九條閘全綠。

| 破壞什麼 | 該紅的測試 |
|---|---|
| `檢查指令` 不看寫檔（回到只擋三條禁令） | `test_寫入管轄檔案要被擋下並提示繞過或走nova`、`test_沒說理由就照擋` |
| 判準放寬回「任何相對路徑」 | `test_重導到不像路徑的東西要放行` |
| 繞過對 Bash 無效（拿掉出路） | `test_說得出理由就放行` |
| 訊息又填回佔位符 | `test_擋下來的訊息要帶真的會話識別碼` |

四條都紅，而且每條只紅指名的那幾支。

### 護欄接上的那一刻就把作者鎖在外面（三個缺陷，都是實際踩到的）

**一、判準過寬。** 重導目標只問了「在不在管轄範圍」，而 `在管轄範圍嗎`
對任何相對路徑都成立（只要不以 `.` 開頭）——於是 `echo 說明 > 一句話`
裡那句中文也被當成受管轄的路徑。收緊成「要真的落在 `src/`、`tests/`、
`docs/` 底下」，跟 python heredoc 那條用同一份前綴表。

**二、訊息裡是字面佔位符。** 擋下來印的是 `nova 繞過 --會話 <會話識別碼>`。
hook 的 JSON 本來就有 `session_id`，`檢查編輯` 一直都接著用，只有這條漏了。

**三、繞過對 Bash 這條路完全無效。** `檢查指令` 沒有叫 `說得出理由了嗎`。

三個加起來的後果是**死鎖**：想記一次繞過理由，`nova 繞過` 那條指令自己
被擋下——因為理由裡引用了訊息中的佔位符，那個角括號命中重導樣式。
**它印給人照做的那句話，照做就被自己擋。**

解法是把理由裡的角括號換掉才記得成。三條都修了，各有測試背書。
